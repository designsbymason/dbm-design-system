<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>

<ComponentHeader title="Splitter" tier="Molecule" />

A row or column of panes divided by draggable handles, for dashboards and editors: pull a handle, or use the
arrow keys on it, to give one pane space from its neighbour. Each handle is a focusable `role="separator"`
that reports the size of the pane before it, and a pane can be allowed to collapse to a strip or to nothing.

Pane sizes are **percentages of the space the panes share** (the container less its handles), so a layout keeps
its proportions when the container is resized; a pane's limits can also be written in pixels or `rem`, and a
pane can be `fixed` to keep its length instead. The splitter
holds no content and keeps no storage: read the layout with `onLayoutChange` or `onLayoutCommit`, and hold it
yourself with `layout` when you need to.

### Import

```tsx
import { Splitter } from "@dbm-design-system/components";
```

### Placing the toggle

The splitter draws no collapse button of its own: a pane's `children` can be a function of
`{ collapsed, size, toggle }`, and `toggle()` collapses or opens the pane. Where the button goes, what it looks like
and what else the collapsed rail shows is yours.

- **Inside the pane**, anywhere in it: a header row, the bottom, the centre of the rail, an icon or a text button.
  This is the form the Collapsible story uses. It needs a pane that collapses to a strip (`collapsedSize` above
  `0`): a pane collapsed to nothing hides its content, button included. Keep the button the same element in both
  states, changing its icon and label, so it keeps keyboard focus when pressed.
- **Anywhere else** (a toolbar, a header in another pane): hold the state yourself with `collapsed` and
  `onCollapsedChange`, as the story above does, and call your own setter. This also works for a pane that
  collapses to nothing.
- **On the divider itself** is not supported: the handles hold no custom content. A button placed in the pane
  at its edge is clipped by the pane, so it can't straddle the divider.

```tsx
{/* A button in a header, for a sidebar that collapses to nothing: you hold the state. */}
const [collapsed, setCollapsed] = useState(false);

<Button onClick={() => setCollapsed(!collapsed)}>Toggle sidebar</Button>
<Splitter defaultLayout={[25, 75]}>
  <Splitter.Pane collapsible minSize="12rem" collapsed={collapsed} onCollapsedChange={setCollapsed}>
    Sidebar
  </Splitter.Pane>
  <Splitter.Pane>Content</Splitter.Pane>
</Splitter>
```

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Give the splitter's parent a size. It fills its parent, so a `vertical` splitter in a box with no height has
  nothing to share out.
- Set `minSize` on every pane that holds something that stops working when it is squeezed (a form, a table), and
  write it in `rem` where it is about the text inside (`"15rem"`): it then keeps up with the text size a person
  has chosen, which a pixel limit doesn't.
- Mark a sidebar `fixed` when it should keep its width as the window changes, and a header or footer
  `resizable={false}` when it should never be dragged.
- Give every pane an `id` (or a `key`) when panes can come and go, so the others keep their sizes.
- Give each pane a `label` when there are several handles: they are then named "Resize Sidebar", not "Resize
  panels 2 of 3".
- Use `collapsible` with a `collapsedSize` strip for a sidebar that should stay reachable, and
  `collapsedSize` of `0` for a panel that can go away entirely.
- Save the layout in `onLayoutCommit`, which fires once a drag or key press is finished, not on every step.
- Put a `ScrollArea` or a scrolling element inside a pane that holds long content: a pane clips what overflows.
- Give a pane that collapses to a strip a function as its `children`, so it can show something else once it has
  collapsed, and a button that opens it: `{({ collapsed, toggle }) => …}`. Keep that one button in the same place
  in both states (change its icon and label, not the element), or it unmounts when pressed and keyboard focus is
  lost. It only makes sense on a strip: a pane collapsed to nothing hides its content, button included.

</Callout>
<Callout tone="danger" title="Don't">

- Don't put anything but `Splitter.Pane` elements directly inside a `Splitter`: a wrapper, a fragment or text is
  ignored, with a warning.
- Don't leave panes that appear and disappear without an `id` or `key`: they are told apart by position, so
  removing the first one gives its size to the wrong pane.
- Don't use a splitter to let people resize something that is not one of two or more panes sharing space (a
  single panel's width is a plain resizable box, not this).
- Don't expect `collapsed` to be changed by a handle: on a pane you control with it, a handle only asks, through
  `onCollapsedChange`, and the pane follows when you change the prop. Leave `collapsed` off for a pane the splitter
  should look after itself.
- Don't make a pane's only way to be reached the handle of a pane that can collapse to nothing without another way
  to open it (a button, using `collapsed`).
- Don't rely on the line at rest to show that a handle exists; use `variant="grip"` where the handles need to be
  discovered.

</Callout>
</div>

## Best practices

- Write limits that mean something: a sidebar's `minSize="240px"` says what it needs; `minSize={20}` says only
  that it should not be small.
- Prefer a layout you can restore: pass what you saved to `defaultLayout` (or hold it with `layout`).
- A pane collapsed to nothing is hidden from every user, keyboard and screen reader included; if something in it
  must stay reachable, collapse to a strip (`collapsedSize="48px"`) instead.
- Tell people that a double click, or Enter, on a handle puts the panes beside it back as they were: it is the
  quickest way back from a layout that has been dragged somewhere awkward. "As they were" is how the panes were laid
  out when the splitter mounted, or when panes were last added or removed.
- Nest splitters for editor layouts (a sidebar beside a stack of editor over terminal); each handle moves only
  its own two panes.

## Accessibility

<Callout tone="info" title="The window splitter pattern: every handle is a focusable separator">

- Each handle is a `role="separator"` in the tab order, with `aria-orientation` (a vertical bar for panes side by
  side), `aria-valuenow`/`aria-valuemin`/`aria-valuemax` for the pane before it as a percentage,
  `aria-valuetext` ("30%", or "Collapsed"), `aria-controls` naming the two panes it resizes, and a name
  (`labels.handle`: "Resize Sidebar" from the `label` of the pane before it, otherwise "Resize panels", or
  "Resize panels 1 of 2" when there are several).
- A handle beside a `resizable={false}` pane is a plain `role="separator"`: not focusable, no value, no target,
  and not counted in the handle names.
- A disabled splitter keeps its handles in the tab order, marked `aria-disabled`, and moves nothing.
- A key pressed with Alt, Ctrl or Cmd is left to the browser (Alt+Left is Back); it never moves a handle.
- A pane whose content overflows it is a tab stop while it does, so a keyboard can scroll it (the way
  `ScrollArea`'s viewport is), and a named region when it has a `label`; one that fits isn't, and nor is a pane
  collapsed to a strip.
- When a pane collapses to nothing while focus is inside it, focus moves to the handle beside it, from where Enter
  opens it again.
- A pane collapsed to nothing is `visibility: hidden`, so its content leaves the tab order and the
  accessibility tree; a strip stays reachable.
- The handle's target is 24px across (WCAG 2.5.8) whatever the line's thickness. Keyboard focus draws a thicker
  line in the focus colour; forced-colours mode draws it in system colours.
- At rest the `line` variant is a divider as `Divider` is, not a control drawn to a 3:1 contrast; the `grip`
  variant's mark is (4.7:1 light, 8.2:1 dark).

| Key | Behaviour |
|---|---|
| Left / Right Arrow | Moves a vertical bar (panes side by side) by `keyboardStep`; in `rtl` text the keys follow the layout |
| Up / Down Arrow | Moves a horizontal bar (stacked panes) |
| Page Up / Page Down | Moves the bar twice as far |
| Home / End | Moves the bar as far as the limits allow, or collapses a pane that can collapse |
| Enter | Collapses or opens a collapsible pane next to the handle; with none, sets the two panes beside it back to the proportions they started in |
| Double click | The same as Enter, for the pointer |

</Callout>

## Code examples

```tsx
<div style={{ height: "24rem" }}>
  <Splitter defaultLayout={[25, 75]} onLayoutCommit={save}>
    <Splitter.Pane minSize="200px" collapsible collapsedSize="48px">
      {({ collapsed }) => (collapsed ? <SidebarRail /> : <Sidebar />)}
    </Splitter.Pane>
    <Splitter.Pane>
      <Splitter orientation="vertical" defaultLayout={[70, 30]}>
        <Splitter.Pane>
          <Editor />
        </Splitter.Pane>
        <Splitter.Pane minSize="120px">
          <Terminal />
        </Splitter.Pane>
      </Splitter>
    </Splitter.Pane>
  </Splitter>
</div>

<Splitter>
  <Splitter.Pane key="nav" id="nav" label="Navigation" fixed minSize="15rem">…</Splitter.Pane>
  <Splitter.Pane key="main" id="main" label="Content">…</Splitter.Pane>
  {showDetails && <Splitter.Pane key="details" id="details" defaultSize={25}>…</Splitter.Pane>}
</Splitter>

{/* Native div attributes pass straight through to the container */}
<Splitter title="Workspace layout" onFocus={handleFocus}>…</Splitter>

{/* Text the splitter writes, in your own words and digits */}
<Splitter labels={{ handle: (position, total) => `Cambiar tamaño ${position} de ${total}`, collapsed: "Cerrado" }}>…</Splitter>
```
