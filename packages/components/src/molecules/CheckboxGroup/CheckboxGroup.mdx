<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>

<ComponentHeader title="CheckboxGroup" tier="Molecule" />

Manages a group of `Checkbox` options sharing one multi-select array of checked values. Radix has
no group primitive for checkboxes — each `Checkbox` is already a fully standalone primitive — so
`CheckboxGroup` implements the array coordination itself via context, mirroring `RadioGroup`'s own
composition pattern. Accepts both controlled (`value`/`onValueChange`) and uncontrolled
(`defaultValue`) usage. Cascades `disabled`/`name`/`form`/`size` to every option at once — any
option can still set its own `size` (or additional `disabled`) to layer on top of the group's.

### Import

```tsx
import { CheckboxGroup, Checkbox } from "@dbm-design-system/components";
```

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Pass a distinct `value` on every `Checkbox` inside the group — that's what identifies which
  option is which.
- Pass `aria-label` (or `aria-labelledby`, pointing at a nearby `FieldLabel`) — every
  `role="group"` benefits from an accessible name of its own.
- Reach for `orientation="horizontal"` for a short set of options in a compact filter bar or
  toolbar; keep the default `vertical` for anything inside a real form.
- Set `required` directly on the one `Checkbox` that must be checked (e.g. "I agree to the Terms"
  inside an otherwise-optional list) — `required` is a per-`Checkbox` prop, not something
  `CheckboxGroup` has any notion of, and it isn't blocked while grouped the way `checked`/
  `defaultChecked`/`onCheckedChange` are. When that specific item fails validation, set `hasError`
  on that same `Checkbox` (its own red-bordered-control treatment), **not** on the `CheckboxGroup`
  — the failure belongs to one option, not the set as a whole. Reserve `CheckboxGroup`'s own
  `hasError` for a rule about the group as a whole (e.g. "choose at least 2 of these 5"), where no
  single item is individually at fault.

</Callout>
<Callout tone="danger" title="Don't">

- Don't drive `value` from a live control without a real `onValueChange` wired back — the group
  always defers to the controlled value, which freezes every option's own click handling.
- Don't set `checked`/`defaultChecked`/`onCheckedChange` on the individual `Checkbox` children —
  those are group-level concerns here; a grouped `Checkbox` reads its checked state from the
  group's own `value` array instead, and warns once in development if any of those are passed.
- Don't expect `hasError` to set `aria-invalid` here the way `RadioGroup`'s does — `role="group"`
  doesn't support it at all (see [Accessibility](#accessibility) below), so it's a visual-only
  signal; always pair it with a nearby `FieldError`.
- Don't expect `required` to set `hasError` for you — `required` only controls native HTML5 form
  validation (does the browser block submission?) and `aria-required`; it has no visual effect on
  its own. Tracking "was this required item left unchecked after a submit attempt" and setting
  `hasError` accordingly is left to you, the same as any other required field in this system.

</Callout>
</div>

## Best practices

- Reach for a plain, standalone `Checkbox` (or a `RadioGroup`, if the options are mutually
  exclusive) instead when there's genuinely only one meaningful choice to make.
- Pair with `FieldLabel`/`FieldError` for the group's own visible label and validation message —
  `CheckboxGroup` itself doesn't render either.
- Keep the option set short and scannable — a long list of independent choices usually reads
  better as a searchable list or a `Select` with multi-select support instead.
- Set `size` once on the group rather than repeating it on every `Checkbox` — reach for a
  per-`Checkbox` override only for a genuine one-off, not as the default way to size a whole group.

## Accessibility

<Callout tone="info" title="No native or Radix group primitive — CheckboxGroup owns its own coordination">

- Renders a `<div role="group">` around its `Checkbox` children, each a real `<button
  role="checkbox">` — every option keeps its own independent tab stop via `Tab`/`Shift+Tab`. Unlike
  `RadioGroup`'s `role="radiogroup"`, a set of checkboxes has no single composite widget or
  roving-tabindex/arrow-key behavior in the WAI-ARIA sense.
- `role="group"` does not support `aria-invalid` per the ARIA spec (unlike `role="radiogroup"`, which
  does) — `hasError` shows a colored left-border accent (`border.danger`) on the group itself as a
  purely visual signal instead. Always pair it with a nearby `FieldError` so the reason for the
  error is still available to assistive tech, not just sighted users. `border.danger` against
  `bg.surface` is checked against real WCAG contrast ratios, not assumed — see
  [Design tokens used](#design-tokens-used) below.
- A dev-mode console warning fires once if a `CheckboxGroup` has no `aria-label` or
  `aria-labelledby` — a group with no accessible name is confusing for screen reader users.
- `disabled` cascades to every option automatically, via the same real context each grouped
  `Checkbox` already reads from — an individual `Checkbox` can still layer its own additional
  `disabled` on top.
- Inside a `<form>` (or with an explicit `form` prop), each grouped `Checkbox` still renders its
  own independent hidden native `<input type="checkbox">`, via Radix — `name`/`form` cascade from
  the group to every option that doesn't set its own, so the whole group submits as a real native
  checkbox group (`?interests=sports&interests=music`).
- `required` is a per-`Checkbox` prop (not cascaded, and not something `CheckboxGroup` has any
  notion of) — mark just the specific option that must be checked, not the whole group, since
  there's no native browser concept of "at least N of these checkboxes." It sets that one item's
  own `aria-required` and its hidden input's native `required` attribute; it does not set
  `hasError` for you — see [Usage guidelines](#usage-guidelines) above for the full pattern.

</Callout>

## Code examples

```tsx
<CheckboxGroup aria-label="Interests" defaultValue={["sports"]}>
  <Checkbox value="sports">Sports</Checkbox>
  <Checkbox value="music">Music</Checkbox>
  <Checkbox value="travel">Travel</Checkbox>
</CheckboxGroup>

<CheckboxGroup aria-label="Interests" value={interests} onValueChange={setInterests}>
  <Checkbox value="sports">Sports</Checkbox>
  <Checkbox value="music">Music</Checkbox>
</CheckboxGroup>

<CheckboxGroup aria-label="Interests" orientation="horizontal" defaultValue={["sports"]}>
  <Checkbox value="sports">Sports</Checkbox>
  <Checkbox value="music">Music</Checkbox>
</CheckboxGroup>

<CheckboxGroup aria-label="Interests" name="interests" onFocus={() => trackFieldFocus('interests')}>
  <Checkbox value="sports">Sports</Checkbox>
  <Checkbox value="music">Music</Checkbox>
</CheckboxGroup>

{/* Every option inherits sm; one option overrides it back to md. */}
<CheckboxGroup aria-label="Interests" size="sm" defaultValue={["sports"]}>
  <Checkbox value="sports">Sports</Checkbox>
  <Checkbox value="music" size="md">Music</Checkbox>
</CheckboxGroup>

{/* One required option inside an otherwise-optional group — required and
    hasError both live on that one Checkbox, not on CheckboxGroup, since only
    that single item can fail this particular validation. */}
<CheckboxGroup aria-label="Sign-up options">
  <Checkbox
    value="agree-terms"
    required
    hasError={submitted && !agreedToTerms}
  >
    I agree to the Terms of Service
  </Checkbox>
  <Checkbox value="newsletter">Send me the newsletter</Checkbox>
  <Checkbox value="updates">Send me product updates</Checkbox>
</CheckboxGroup>
```
