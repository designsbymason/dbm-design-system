<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>

<ComponentHeader title="ProgressBar" tier="Atom" />

A horizontal progress indicator. Determinate when `value` is set — a fixed-width fill reflecting
`value`/`max`; indeterminate — an animated sliding fill — when `value` is omitted, for progress
that can't be measured yet. The bar has no visible text of its own by default, so `label` (or
`aria-labelledby`) is required for it to have an accessible name at all. `showValueLabel` adds a
visible percentage next to the bar; pair it with `formatValueLabel` to show something more
meaningful than a raw percentage (e.g. `"3 of 5 files"`), and `aria-valuetext` to give screen
reader users the matching description. `ProgressCircle` is this component's ring-shaped
counterpart, sharing the same `value`/`max`/`size`/`tone`/`label` API.

### Import

```tsx
import { ProgressBar } from "@dbm-design-system/components";
```

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Always pass `label` or `aria-labelledby` — ProgressBar warns once in development if neither is
  set, since it has no visible text of its own and would otherwise have no accessible name at all.
- Use `showValueLabel` (optionally with `formatValueLabel`) whenever a visible number adds real
  value to sighted users, not as a default — many bars communicate progress fine through fill
  width alone.
- Pair `aria-valuetext` with a matching `formatValueLabel` whenever the raw percentage doesn't
  convey the real unit of progress (e.g. `"3 of 5 files"`), so sighted and screen-reader users get
  the same story, not two different ones.
- Switch from indeterminate (omit `value`) to determinate as soon as a real value is measurable —
  indeterminate conveys strictly less information and should be a brief bridging state, not the norm.

</Callout>
<Callout tone="danger" title="Don't">

- Don't pass an invalid `max` (`0`, negative, or `NaN`) expecting it to silently work — ProgressBar
  falls back to the default of 100 and warns once in development, rather than producing broken CSS
  (`width: "Infinity%"`).
- Don't expect `formatValueLabel` to do anything without `showValueLabel` — it's never called
  unless the value label is actually shown, and ProgressBar warns once in development if it's
  passed alone.
- Don't try to override `role`, `aria-valuenow`, `aria-valuemin`, or `aria-valuemax` yourself —
  ProgressBar computes and always applies these itself, so a same-named prop is silently ignored
  (found and fixed during review — see Accessibility below).
- Don't reach for `aria-valuetext` alone when the unit genuinely matters to sighted users too —
  pair it with `formatValueLabel` instead of leaving sighted users with only the bare percentage.

</Callout>
</div>

## Best practices

- Match `size` to context — thin (`xs`/`sm`) for a compact inline indicator alongside other UI,
  larger (`lg`/`xl`) when the bar is the primary focus of the view (a dedicated upload/loading screen).
- Keep `tone` consistent with what the fill's color communicates elsewhere in the same view (e.g.
  `danger` once a quota is exceeded) — treat it as meaningful status, not decoration.
- For file/step/byte counts, prefer `aria-valuetext` + `formatValueLabel` together over a bare
  percentage — `"3 of 5 files"` is more actionable than `"60%"` when the underlying unit matters
  to the user's task.
- `ProgressCircle` shares this component's API — reach for it instead when the ring shape fits the
  layout better (e.g. a compact dashboard tile), not as a visually-different alternative requiring
  a different mental model.

## Accessibility

<Callout tone="info" title="role and aria-value* are computed for you, never overridable">

- **`role="progressbar"` with `aria-valuenow`/`aria-valuemin`/`aria-valuemax`** are always computed
  internally from `value`/`max` — a same-named prop passed by the caller is silently ignored, even
  though TypeScript's JSX checker permits `aria-*`/`role` attributes on any component regardless of
  its declared prop type (a real gap found and fixed during review: enforced via JSX attribute
  order, not the type system, since the type system alone can't stop it for `aria-*` names).
- **Indeterminate mode omits `aria-valuenow` entirely**, per the ARIA APG progressbar pattern — the
  fill's own animation is the only "still working" signal, not a numeric value implying false
  precision.
- **`aria-valuetext`** lets you pair the numeric value with a meaningful description for screen
  readers, independent of whatever `formatValueLabel` shows sighted users visually.
- **Three development-mode warnings** (stripped in production, each fires once per instance): no
  accessible name (neither `label` nor `aria-labelledby`), an invalid `max`, and `formatValueLabel`
  provided without `showValueLabel`.
- **Respects `prefers-reduced-motion`** — the indeterminate sliding-fill animation slows to 12x its
  normal duration rather than stopping outright, staying visible as an in-progress signal.
- The track's own `bg.track` fill is a deliberate, documented exception to this system's usual 3:1
  non-text contrast floor, chosen at explicit direction — see [Design tokens
  used](#design-tokens-used) below and the Color Foundations page for the full rationale and the
  real numbers. Every other pairing here is contrast-verified per this system's WCAG methodology.

</Callout>

## Code examples

```tsx
<ProgressBar value={40} label="Uploading file.zip" />
<ProgressBar value={40} label="Uploading file.zip" showValueLabel />
<ProgressBar
  value={3}
  max={5}
  label="Uploading files"
  aria-valuetext="3 of 5 files uploaded"
  showValueLabel
  formatValueLabel={(value, max) => `${value} of ${max} files`}
/>
<ProgressBar tone="success" value={100} label="Upload complete" />
<ProgressBar label="Loading" />
```
