<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>

<ComponentHeader title="Container" tier="Atom" />

The standard top-level wrapper for page/section content — centers its children horizontally
(`margin-inline: auto`) and constrains them to a max-width breakpoint step, with token-driven
horizontal padding. **Polymorphic** (see [`Box`](/?path=/docs/atoms-layout-box--docs) for the full
explanation of what that means): renders a `div` by default, but `as` lets it render any other
element or component — useful here in particular, since a top-level page wrapper often needs to be
a real landmark element (`main`, `section`), not a generic `div`. `paddingInline` accepts a single
spacing step or a mobile-first responsive map keyed by breakpoint (e.g. `{ base: 2, lg: 8 }`) —
the same responsive shape [`Bleed`](/?path=/docs/atoms-layout-bleed--docs)'s own `inset` uses to
counteract it.

### Import

```tsx
import { Container } from "@dbm-design-system/components";
```

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Use `Container` as the standard top-level wrapper for page or section content — it's the one
  place `size`/`paddingInline` should come from, rather than reinventing max-width/padding
  per-page.
- Pass `as="main"` (or another real landmark element) for a page's actual top-level content
  wrapper — `Container` composes cleanly with real semantics, it doesn't fight them.
- Pass the identical `paddingInline` map to a paired [`Bleed`](/?path=/docs/atoms-layout-bleed--docs)
  when something inside needs to bleed back out to the viewport edge — see the Responsive
  paddingInline variant above.

</Callout>
<Callout tone="danger" title="Don't">

- Don't nest `Container` inside `Container` — max-widths don't compose usefully, and the inner
  one's own padding just doubles up against the outer one's.
- Don't reach for `Container` to center a single child on both axes — that's
  [`Center`](/?path=/docs/atoms-layout-center--docs), which has no max-width concept of its own.
- Don't hardcode a page's max-width/padding in `style` when `size`/`paddingInline` already express
  it — `Container` exists specifically so this is a shared, token-driven decision.

</Callout>
</div>

## Best practices

- Treat `size` as a small set of real breakpoint decisions, not a per-page tuning knob — pick the
  step that matches the content's actual density (a form reads better at `md`/`lg`, a dashboard at
  `2xl`/`3xl`), and default (`xl`) unless there's a real reason to deviate.
- When a page's content needs a full-bleed section (a hero image, a banner) alongside otherwise
  padded content, keep `Container` wrapping the page and use `Bleed` locally around just that
  section — don't drop `Container` for the whole page to work around one full-width element.
- Treat `as` the same way you'd treat choosing a native HTML tag directly — `Container` imposes no
  semantics of its own beyond layout.

## Accessibility

<Callout tone="info" title="No built-in semantics — as is what makes this accessible">

`Container` sets no ARIA attributes and imposes no accessibility semantics of its own — the same
as `Box`/`Center`. Accessibility is entirely a function of which element `as` renders; a real
top-level content wrapper should almost always use `as="main"` (or another landmark element)
rather than the default `div`.

</Callout>

## Code examples

```tsx
<Container as="main" size="lg">
  <PageContent />
</Container>
```

```tsx
// Responsive padding, tight on mobile, roomy on wide screens
<Container size="xl" paddingInline={{ base: 2, lg: 8 }}>
  <PageContent />
</Container>
```

```tsx
// A native <div> attribute (title) passed straight through
<Container title="Main content area" size="md">
  <PageContent />
</Container>
```
