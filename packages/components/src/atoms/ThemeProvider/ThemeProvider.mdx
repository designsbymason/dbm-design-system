<ComponentHeader title="ThemeProvider" tier="Atom" />

Applies a DBM Design System brand + color mode by setting `data-theme` (e.g. `data-theme="purple-light"`)
on `document.documentElement` — matching the `:root[data-theme="..."]`-scoped CSS custom properties
`@dbm-design-system/tokens` emits. Theming is applied document-wide, not scoped to this component's
own DOM subtree, so portaled content (dialogs, tooltips, toasts mounted on `document.body`) inherits
the theme correctly too. `mode="system"` follows `prefers-color-scheme` and updates live if the OS
preference changes while mounted. Descendants can read the resolved brand/mode reactively via
`useTheme()` instead of reaching into the DOM directly.

<Callout tone="info" title="Live demos live on their own standalone story pages, not embedded here" />

### Import

```tsx
import { ThemeProvider, useTheme } from "@dbm-design-system/components";
```

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Mount exactly one `ThemeProvider` near the root of your app — it's meant to own the whole
  document's theme, not scope a small region of the page.
- Use `mode="system"` (the default) unless the product has its own explicit light/dark toggle —
  it keeps the app in sync with the user's OS preference automatically, including live updates if
  they change it while the app is open.
- Read the active theme via `useTheme()` in any descendant that needs to branch on it (an icon that
  swaps for light vs. dark, an image with separate light/dark source assets) instead of reaching
  into `document.documentElement.dataset.theme` directly — `useTheme()` is reactive and re-renders
  the consumer when the resolved value changes; a direct DOM read doesn't.

</Callout>
<Callout tone="danger" title="Don't">

- Don't nest a second `ThemeProvider` inside the first expecting a scoped sub-theme — theming
  applies document-wide regardless of where in the tree a `ThemeProvider` sits, so an inner one
  simply takes over the *whole* document for as long as it's mounted, then hands control back to
  the outer one's own value on unmount (useful for test/Storybook isolation, not for theming one
  region of a page differently from the rest).
- Don't call `useTheme()` outside a `ThemeProvider` — it throws
  (`useTheme must be used within a ThemeProvider`) rather than silently returning a default, so a
  missing provider fails loudly during development instead of rendering with the wrong colors.
- Don't read `document.documentElement.dataset.theme` directly in a descendant when `useTheme()` is
  available — a direct read only reflects whatever was true at that exact render, and won't update
  when the theme changes afterward.

</Callout>
</div>

## Best practices

- Place `ThemeProvider` above anything that portals to `document.body` (dialogs, tooltips, toasts)
  — since theming applies to the whole document rather than a DOM subtree, this is automatic as
  long as `ThemeProvider` is mounted anywhere in the tree, portaled content included.
- Let the brief color transition (on a *change*, never on the initial mount) do its job — it's
  already skipped under `prefers-reduced-motion: reduce` and timed from
  `--dbm-motion-duration-base`, so there's usually nothing to configure.
- On a server-rendered app, expect the very first paint to briefly show `light` if `mode="system"`
  resolves to `dark` — `ThemeProvider` intentionally renders `light` on the first render (matching
  what the server produced) and corrects to the real OS preference in a layout effect immediately
  after mount, avoiding a React hydration mismatch at the cost of that brief first-paint flash. A
  fully flash-free experience needs a blocking pre-hydration script outside this component's
  control (the same tradeoff documented by comparable SSR theming libraries).

## Accessibility

<Callout tone="info" title="No ARIA role of its own — a document-wide styling mechanism">

- **Renders no semantic role or accessible name.** `ThemeProvider` only ever changes *which colors*
  `--dbm-*` tokens resolve to — it has no effect on the accessibility tree.
- **Every semantic color pairing this system ships already clears WCAG AA contrast** in all four
  brand/mode combinations (`03-token-system-spec.md`'s own contrast methodology) — switching
  theme never trades away contrast, in either direction.
- **The brief post-change color transition respects `prefers-reduced-motion: reduce`** — skipped
  entirely for a user with that preference set, matching how every other motion in this system
  behaves.

</Callout>

## Code examples

```tsx
// Mounted once, near the app root
<ThemeProvider brand="purple" mode="system">
  <App />
</ThemeProvider>
```

```tsx
// A fixed brand/mode, no OS-preference following
<ThemeProvider brand="emerald" mode="dark">
  <App />
</ThemeProvider>
```

```tsx
// A descendant reactively reading the resolved theme
import { useTheme } from "@dbm-design-system/components";

function ModeToggleIcon() {
  const { resolvedMode } = useTheme();
  return resolvedMode === "dark" ? <MoonIcon /> : <SunIcon />;
}
```

## Design tokens used

`ThemeProvider` itself references two motion tokens, applied only for the brief transition after a
brand/mode *change* (never on the initial mount):

<TokenRow token="motion.duration.base" usage="duration of the color transition on a theme change" />
<TokenRow token="motion.easing.standard" usage="easing curve for the same transition" />

Every other visual token in this system (`--dbm-bg-*`, `--dbm-text-*`, `--dbm-border-*`, and the
rest) is what `ThemeProvider` actually *switches* the resolved value of, by setting `data-theme` —
it doesn't reference them directly itself.
