<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>

<ComponentHeader title="CloseButton" tier="Atom" />

A dedicated dismiss control — a small, icon-only button with a fixed brand-colored icon and a
default `aria-label` of "Close". Styled to match `IconButton`'s own `tertiary` variant exactly
(transparent at rest, `icon.brand` icon color, `bg.brand-subtle-hover` on hover, the same box
sizing), not a context-adaptive one. **Reserved for surfaces where a modal-style overlay is
involved** — Dialog, Drawer, lightbox, and similar cards/panels that present over the rest of the
page — which have no local tone of their own to track. Any component whose own tone/color varies
per instance (Tag, Alert, Toast) implements its own local remove/dismiss button instead, following
`Tag`'s own established pattern — see [Tag](#related-components) below for a real example. **Default
to that local, component-specific pattern unless `CloseButton` is explicitly what's wanted** —
it isn't the default building block for every dismissible component.

### Import

```tsx
import { CloseButton } from "@dbm-design-system/components";
```

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Use `CloseButton` for dismiss affordances on modal-style surfaces — Dialog, Drawer, lightbox, and
  similar cards/panels — where a fixed, brand-colored icon is the right, consistent choice.
- Pass `hasBackground` when placing it over unpredictable external content (a photo, a busy hero
  image) so the icon stays grounded regardless of what's behind it.
- Reach for `rounded` for a circular treatment, matching `IconButton`'s own `rounded` prop and
  default exactly.
- Override the default `aria-label="Close"` with something more specific when it helps — "Dismiss
  notification", "Remove filter" — but leave it as-is when "Close" is already unambiguous.

</Callout>
<Callout tone="danger" title="Don't">

- Don't reuse `CloseButton` inside a component whose own dismiss affordance needs to match a
  *local*, varying tone — `Tag`, `Alert`, `Toast`, and any future tone-driven component — build a
  small, local, tone-aware implementation instead, the way `Tag`'s own removable variant does.
  `CloseButton`'s icon color is fixed, not context-adaptive, even though these components can be
  visually "standalone" (floating above other content) in the same loose sense Dialog/Drawer are —
  the deciding factor is whether the component has its own varying tone to track, not whether it
  floats.
- Don't reach for `CloseButton` by default just because a component needs *some* dismiss
  affordance — it's an opt-in choice for the modal-surface case specifically, not the standard
  building block every removable/dismissible component should start from.
- Don't rely on `hasBackground` for a guaranteed contrast outcome — there's no fixed WCAG pairing
  possible here, since what it composites over is arbitrary, external content by design.
- Don't pass a custom `aria-label` that no longer describes a dismiss action — assistive tech users
  rely on it to know what the button actually does.

</Callout>
</div>

## Best practices

- Match `size` to the density of the modal-style surface it's dismissing — `sm`/`xs` for compact
  cards and panels, `md` (the default) for standard Dialog/Drawer headers, `lg`/`xl` for
  high-emphasis contexts (a full-screen lightbox, for example).
- `rounded` and `hasBackground` compose freely — the translucent grounding layer automatically
  follows whichever shape is active (`border-radius: inherit`), so there's no separate
  square/circle variant of it to reach for.
- `hasBackground`'s scrim color is mode-specific (white in light mode, a dark neutral in dark mode)
  but not otherwise configurable — if a different grounding treatment is needed for a specific
  surface, compose a wrapper around `CloseButton` rather than extending this prop.

## Accessibility

<Callout tone="info" title="Keyboard support comes from the native button; a label is always present">

- Renders a native `<button type="button">` by default — full keyboard support (`Tab` to focus,
  `Enter`/`Space` to activate) comes for free from the browser, not from custom key handling.
- Always has an accessible name: `aria-label` defaults to `"Close"` when omitted, so — unlike
  `IconButton`, whose `aria-label` is required by the type with no fallback — `CloseButton` never
  ships with no accessible name at all.
- `icon.brand`'s rest-state legibility against a typical `bg.surface` card, and its hover-state
  legibility against `bg.brand-subtle-hover`, are both checked against real WCAG contrast ratios,
  not assumed — see [Design tokens used](#design-tokens-used) below for the exact tokens.
- `hasBackground`'s translucent layer is purely decorative (`pointer-events: none`) — confirmed
  live, not just from the CSS declaration, that it never intercepts clicks or keyboard focus.
  There's no fixed contrast guarantee for it, since what it composites over is arbitrary by design.

</Callout>

## Code examples

```tsx
<CloseButton onClick={() => setOpen(false)} />
<CloseButton size="sm" aria-label="Dismiss notification" onClick={onDismiss} />
<CloseButton rounded aria-label="Close" onClick={() => setOpen(false)} />
<CloseButton hasBackground aria-label="Close" onClick={() => setOpen(false)} />
```
