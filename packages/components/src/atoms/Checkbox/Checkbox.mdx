<ComponentHeader title="Checkbox" tier="Atom" />

A tri-state checkbox — checked (`true`), unchecked (`false`), or indeterminate (a visual
"some, but not all" state, rendered as a dash instead of a checkmark) — built on Radix UI's
Checkbox primitive, with a token-driven visual box and an optional inline label. Accepts both
controlled (`checked`/`onCheckedChange`) and uncontrolled (`defaultChecked`) usage, mirroring the
same pattern as a native `<input type="checkbox">`.

### Import

```tsx
import { Checkbox } from "@dbm-design-system/components";
```

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Use `checked="indeterminate"` for a parent "select all" checkbox when some but not all of its
  children are checked — see the Select-all pattern above for the full three-state wiring.
- Pass `aria-label` (or `aria-labelledby`) whenever there's no visible `children` label, e.g. a
  table row's own selection checkbox.
- Pair `hasError` with a nearby `FieldError` so the reason is visible, not just the red border and
  `aria-invalid`.

</Callout>
<Callout tone="danger" title="Don't">

- Don't drive `checked` from a live control without a real `onCheckedChange` wired back — Radix
  always defers to the controlled value, which freezes the checkbox's own click handling.
- Don't expect changing `defaultChecked` after mount to update an already-rendered checkbox — it
  only sets the value at mount time, exactly like a real `<input defaultChecked>`.
- Don't override `icon`/`indeterminateIcon` without a concrete reason — the shared glyphs are what
  make checkboxes instantly recognizable across every DBM product surface.

</Callout>
</div>

## Best practices

- Reach for `Switch` instead when the action takes effect immediately (e.g. toggling a setting) —
  reserve `Checkbox` for choices that stay pending until an explicit submit/save, which is the
  convention most users already associate with the checkbox shape.
- Match `size` to the surrounding form/table density — the default `md` suits standalone forms;
  drop to `sm`/`xs` inside dense tables or compact filter lists.
- Let `Checkbox` generate its own `id` (via `useId`) unless something else — a test, a router, an
  external `aria-describedby` — needs a stable, predictable value to point at.

## Accessibility

<Callout tone="info" title="Keyboard and ARIA state come from Radix's own checkbox primitive">

- Renders a `<button role="checkbox">` (not a native `<input type="checkbox">`) — `Tab` focuses
  it, and `Space` toggles it, per the WAI-ARIA checkbox pattern. Unlike `Button`, `Enter` isn't
  part of that pattern's keyboard contract.
- `aria-checked` reflects the real state directly: `"false"`, `"true"`, or `"mixed"` for
  indeterminate — screen readers announce indeterminate distinctly from both checked and
  unchecked, not just as a visual dash.
- `aria-invalid="true"` is set automatically while `hasError`, in addition to the visual red
  border — the two can't drift out of sync.
- A dev-mode console warning fires once if a `Checkbox` has no `children`, `aria-label`, or
  `aria-labelledby` — a checkbox with no accessible name is invisible to screen reader users.
- The inline `children` label is a real `<label>` associated via `htmlFor`/`id`, so clicking the
  label text toggles the checkbox too, not just the box itself.
- A `disabled` checkbox uses the native `disabled` attribute, so it's skipped by `Tab` entirely —
  not just visually dimmed while remaining reachable.
- `required` sets `aria-required` and marks the checkbox required for real HTML5 form validation —
  inside a `<form>`, Radix automatically renders a hidden native `<input type="checkbox">` that
  actually participates in submission (including an uncontrolled form with no JS handler), using
  `name`/`value` as its own name/value.
- `bg.brand`/`icon.on-brand` (the checked-state fill and glyph color) is checked against real
  WCAG contrast ratios, not assumed — see [Design tokens used](#design-tokens-used) below.

</Callout>
