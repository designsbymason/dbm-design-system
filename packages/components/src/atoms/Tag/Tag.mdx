<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>

<ComponentHeader title="Tag" tier="Atom" />

A labeled pill for categorization or active filters, with an optional leading/trailing icon, an
optional removable ("×") affordance, and an optional clickable/selectable interactive mode. Shares
`Badge`'s six-tone scale but at larger, touch-friendly sizes suited to interactive contexts like
filter bars — its own variant scale adds `outline` (a bordered, no-background style) on top of the
`subtle`/`solid` pair `Badge` also has. Passing `onClick`, `selected`, `defaultSelected`, or
`onSelectedChange` makes the whole tag focusable and keyboard-activatable, not just visually
styled; `removable` adds its own independent remove control that composes cleanly with either mode
— clicking the tag body toggles selection while clicking the "×" removes it, neither triggering the
other.

### Import

```tsx
import { Tag } from "@dbm-design-system/components";
```

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Use `variant="subtle"` (the default) for low-emphasis categorization labels, `solid` for
  high-emphasis status, and `outline` for a bordered style with no background — selecting an
  outline tag fills it in, converging toward `solid`'s own look.
- Pass `onRemove` whenever `removable` is set — Tag warns once in development if `removable` is
  set without it, since the button would render but do nothing on click.
- Reach for `tone` for feedback-type meaning (`danger`/`warning`/`success`/`info`) independent of
  `variant`'s emphasis level — the two are separate axes, not a combined scale. Reserve `brand` for
  the system's own identity (e.g. "New"/"Beta"), not a status.
- Combine `removable` with `selected`/`onSelectedChange` freely — the two interactions are
  independent by design (clicking the body toggles selection, clicking "×" removes), confirmed via
  a dedicated interaction test.

</Callout>
<Callout tone="danger" title="Don't">

- Don't rely on `removeLabel`'s default (`Remove ${children}`) when `children` isn't descriptive
  text — pass an explicit `removeLabel` so the remove button's accessible name still makes sense
  (e.g. an icon-only tag, or a tag whose label is itself an abbreviation).
- Don't set `disabled` on a plain, non-interactive tag expecting a visual effect — it only does
  anything once the tag is already interactive (`onClick`/`selected`/`defaultSelected`/
  `onSelectedChange`); Tag warns once in development otherwise.
- Don't expect a bare `selected` toggle without `onSelectedChange` to do anything — controlled mode
  requires the pairing, the same controlled/uncontrolled split every other stateful component in
  this system uses.
- Don't nest another interactive element inside `children` — once `onClick`/`selected` make the tag
  itself a `role="button"`, a second focusable control inside it (beyond Tag's own remove
  affordance, which is deliberately handled as a non-nested decorative glyph) creates the same
  ARIA nested-interactive violation Tag's own implementation avoids for its remove button.
- Don't use `Tag` for a primary page action — its focus/hover treatment and touch-target sizing are
  tuned for compact, filter-bar-style density, not a `Button`'s call-to-action prominence.

</Callout>
</div>

## Best practices

- Match `size` consistently within one filter bar or toolbar row rather than mixing sizes, so the
  row reads as one coherent scale.
- For a live filter list, compose `removable` tags with your own local state that removes the item
  on `onRemove` (see "Removable filter list" above) — Tag never removes itself from the DOM on its
  own, since the caller usually needs to update a backing list too.
- For a toggleable filter group with several tags, `selected`/`onSelectedChange` (controlled) is
  usually the better fit over `defaultSelected` (uncontrolled) — a filter's selected state is
  normally driven by, and needs to stay in sync with, application state elsewhere (see "Selectable
  filter group" above).
- `outline`'s selected state deliberately reuses the exact `solid`-fill tokens `variant="solid"`
  itself uses — treat outline-selected and solid as visually equivalent "committed" states, not two
  different looks that happen to look similar.

## Accessibility

<Callout tone="info" title="Interactive semantics are computed for you, not opted into piecemeal">

- **Dev-mode warning** (stripped in production): `removable` set without `onRemove` warns once via
  `console.warn`, since the remove button would otherwise render but silently do nothing.
- **`role="button"` and `tabIndex={0}`** are applied automatically once any of `onClick`/`selected`/
  `defaultSelected`/`onSelectedChange` are passed — a purely read-only tag (none of these) renders
  with no interactive role at all, matching its actual behavior.
- **`aria-pressed`** reflects the live selected state whenever the tag is selectable, so assistive
  tech announces the toggle correctly on every change, controlled or uncontrolled.
- **Enter/Space activates** the tag (toggling selection and/or firing `onClick`) whenever it's
  interactive — standard `role="button"` keyboard behavior, implemented directly rather than relying
  on a native element.
- **The remove affordance avoids a real nested-interactive violation.** When the tag is also
  interactive, a genuine focusable `<button>` nested inside its own `role="button"` would be an ARIA
  violation (confirmed via a live `axe` run — the "nested-interactive" rule) — so in that combined
  mode the "×" renders as a non-focusable, `aria-hidden` decorative glyph instead, and
  Delete/Backspace on the already-focused tag itself becomes the keyboard path for removal, flagged
  to assistive tech via `aria-keyshortcuts="Delete Backspace"`. In the non-selectable-but-removable
  case, the remove affordance is a real, independently focusable `<button>` instead, since no
  nesting conflict exists there.
- **Mouse and keyboard removal never also toggle selection**, and vice versa — the remove click
  handler stops propagation, and the tag's own keydown handler ignores events that bubbled up from
  a focused descendant, both confirmed via dedicated interaction tests.
- **`disabled` marks `aria-disabled` and blocks activation, but doesn't remove the tag from the tab
  order.** The tag's own element is always a `<span>`, never a native `<button>`, so there's no
  native `disabled` attribute to apply — `aria-disabled` plus blocked click/keyboard handlers keeps
  it focusable and perceivable to assistive tech instead of silently vanishing from Tab order,
  matching WAI-ARIA's own recommended pattern for a custom-role disabled control. Only has an
  effect once the tag is interactive; Tag warns once in development otherwise.
- **Focus ring** uses the shared `border.focus` token at a `radius.full` outline, matching the
  pill's own shape, offset outward rather than overlapping the fill.
- Every `tone` × `variant` × state background/text/icon/border pairing is contrast-verified per
  this system's WCAG methodology — see [Design tokens used](#design-tokens-used) below for the
  exact tokens.

</Callout>
