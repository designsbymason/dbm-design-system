# Shadows

Five elevation steps (`xs`–`xl`), each with **separate light- and dark-mode values** — dark-mode
shadows are higher-opacity black, not a naive inversion of the light set, since a soft, low-opacity
shadow that reads clearly on a white surface all but disappears on a dark one.

<Callout tone="info" title="Not yet consumed by any shipped component">

No component currently references `shadow.*` — these tokens exist and are fully defined, but
nothing in the library has needed elevation yet (candidates: `Card`, `Dialog`, `Popover`, once
built). When a component does start using them, it will need its own light/dark selection logic
(e.g. a `[data-theme*="dark"]` CSS selector switching which shadow custom property applies) —
there's no automatic semantic indirection for shadows the way there is for color, since `shadow.*`
sits at the primitive layer only. Revisit this note once a real consumer exists, and consider
whether a semantic `shadow.raised`/`shadow.overlay` layer (mirroring the color architecture) is
worth adding at that point.

</Callout>

## Usage guidelines

<div style={{ display: "grid", gridTemplateColumns: "1fr 1fr", gap: "var(--dbm-space-4)" }}>
<Callout tone="success" title="Do">

- Pair a raised shadow with `bg.surface-raised` and a subtle border in dark mode — dark-mode
  shadows alone read weakly against a dark canvas; a hairline border helps define the edge.
- Match elevation to genuine z-axis meaning — `xs`/`sm` for barely-raised surfaces (cards), `lg`/
  `xl` for content that floats above everything else (modals, popovers).

</Callout>
<Callout tone="danger" title="Don't">

- Don't invert light-mode shadow values for dark mode by just lowering opacity uniformly — use the
  dedicated `shadow.dark.*` set, which was calibrated separately, not derived mechanically.
- Don't stack multiple elevation tokens on one element ("just to be safe") — each step is already
  a layered multi-shadow value; pick the one step that matches the intended elevation.

</Callout>
</div>
