<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>

<ComponentHeader title="Toast" tier="Organism" />

A short message that appears at the edge of the screen, tells the person something happened, and goes
away by itself: "Saved", "Link copied", "Conversation archived · Undo". It never takes focus and never
blocks the page, so it is for news that can wait, not for a decision. A toast is raised from code: put
a `Toast.Provider` once near the root of the app, and call `toast()` from `useToast()` anywhere under
it. Toasts queue (`limit` show at once, the rest wait their turn), pause while the pointer is over them
or focus is inside them, can be swiped away or dismissed, and offer "Clear all" once there are several; a
message raised again while it shows is merged into one with a count. The same thing can be drawn as parts
(`Toast`, `Toast.Title`, `Toast.Description`, `Toast.Action`) when the message belongs to your own state.

### Import

```tsx
import { createToaster, Toast, useToast } from "@dbm-design-system/components";
```

### With an action

The action runs its handler and then closes the toast. `altText` is required: it is read out in place
of the button and says how to do the same thing without the toast, because a toast goes away by
itself.

<Canvas of={ToastStories.WithAction} />

### An action that takes a promise

Return a promise from `onClick` and the toast stays open while it runs: the button shows a spinner and
can be pressed once, the toast doesn't time out (and Escape, a swipe and the dismiss button do nothing),
and it closes when the promise resolves. A rejection keeps it open and the button available again, and
goes to `onError` (`onClickError` on `Toast.Action`); with none it is left unhandled so it is never lost.

<Canvas of={ToastStories.PromiseAction} />

### Placements

`start` and `end` are logical: the left and right in left-to-right text, swapped in right-to-left. In the
list the newest toast is at the top and "Clear all" at the bottom, whichever edge it is against. A list
against the top edge grows downward, so a toast that leaves lets the ones below it move up; against the
bottom edge it grows upward, so a new toast appears above the others, and one that leaves lets the ones
above it glide down to the edge. "Clear all", below the oldest, opens and closes its own room the same
way, so the toasts above it move by that room when it comes and goes.

<Canvas of={ToastStories.Placements} />

### A placement that changes with the screen

A mobile-first map, as `Stack` and `Grid` take. Below the `sm` breakpoint a toast spans the screen less a
gutter whatever its horizontal placement, so only whether it is at the top or the bottom matters there.
This demo is drawn inside a box, so resize the window to see it change.

<Canvas of={ToastStories.ResponsivePlacement} />

### Following a promise

`toast.promise()` shows a loading toast, then replaces it, in the same place, with the success or the
error one. It returns the promise itself, so it can still be awaited, and a rejection is still yours
to handle: the toast only reports it.

<Canvas of={ToastStories.Promise_} />

### Kept until it is dismissed

`duration: null` keeps a toast until it is dismissed. Use it for a state that is still true, such as
being offline, and not for something that happened once.

<Canvas of={ToastStories.Persistent} />

### A fanned stack

`stack="fan"` shows the newest toast in full at the edge with the older ones peeking out behind it, up to
three layers, so a handful of toasts take about one toast's height. The pointer over the toasts, or focus
in them, spreads it into the list (and holds the time, as it does in the list); it folds back a moment
after both go. A mobile-first map such as `{ base: "fan", md: "list" }` gives a phone the fan and a
desktop the list. "Clear all" is drawn only while it is spread out.

<Canvas of={ToastStories.Fan} />

### A limit, with the rest waiting

`limit` is the most showing at once. The rest wait and appear as room is made, each starting its own
time when it appears.

<Canvas of={ToastStories.Queue} />

### Updated in place

Calling `toast()` again with the same `id` replaces what is showing instead of adding another, and
`update()` changes some of it and keeps the rest. A replacement is drawn afresh, so its time starts
again and a screen reader reads the new text; `update()` changes it without either.

<Canvas of={ToastStories.Updating} />

### The same message, once, with a count

A plain message raised again while it is still showing (the same tone, title and description, with no
`id`) is one toast with a count, and its time starts again. An action and callbacks have to be the very
same functions to merge, since the second call's own would be lost: a handler written inline at each
call is a different function and keeps the toasts apart. `mergeDuplicates={false}` turns it off.

<Canvas of={ToastStories.Merged} />

### Clear all

Once more than one toast is showing, a "Clear all" button appears at the bottom of the list, drawn as a
small ghost button. It closes every toast and drops the ones waiting. It is in the region's tab order like a toast of its own, so F8
and `Tab` reach it.

<Canvas of={ToastStories.ClearAll} />

### Raised from plain code

`createToaster()` makes a queue outside React, for an API client's error handler or a service module.
Give it to one provider as its `toaster`; what is raised before the provider mounts waits for it.

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Use a toast to confirm something the person just did, or to report something that finished in the
  background: "Saved", "Copied", "Export ready".
- Say what happened in a few words, and put detail in `description` only when it helps.
- Pair a destructive action with an `Undo` action and its `altText`, so a mistake is cheap.
- Use `toast.promise()` for work the person started and is waiting on, so the same toast shows the
  outcome.
- Give a repeated message an `id` so it stays one toast.
- Put one `Toast.Provider` near the root of the app, around everything that may raise a toast.

</Callout>
<Callout tone="danger" title="Don't">

- Don't use a toast for something the person must answer, or that blocks their work: that is an
  `AlertDialog` or a `ConfirmDialog`.
- Don't make a toast the only place something can be done or read. It goes away by itself, and a person
  using a screen reader or a keyboard may never reach it in time.
- Don't use it for a message that belongs in the page (a form's error, a plan's expiry): that is an
  `Alert`, which stays.
- Don't raise a toast for every small thing, or several at once: a person can read about three.
- Don't catch a failure inside an action's `onClick` and return normally: the toast reads that as success
  and closes. Let the promise reject, or handle it in `onError`.
- Don't put a long message, a form or a link list in one. If it needs more than a sentence and one
  action, it is not a toast.

</Callout>
</div>

## Best practices

- Leave `duration` at its default unless there is a reason. Time is paused while the pointer is over the
  toasts or focus is inside them, and while the window is in the background, so a person who is reading
  is never raced.
- Use `duration: null` sparingly, with a way to dismiss it, for a state that stays true.
- Keep `limit` low. Past about three, toasts hide the page; raise fewer rather than more.
- A toast raised from a handler that also changes the page (archiving a row) should say what changed,
  since the person's eyes are on the thing that moved.
- Report the outcome with `toast.promise()` or `update()` rather than a second toast, so one piece of
  work is one message.
- A fan is for a small screen, or an app whose toasts are short. Keep the list for toasts that carry an
  action or a sentence of detail, since an older toast is only half visible until the stack is spread out.
- Hovering one toast holds the time of all of them, so the stack doesn't change under a pointer that is
  moving between them. Leaving the toasts (and focus leaving them) lets every time carry on.
- A message that is raised again from a button pressed twice becomes one toast with a count. Give a toast
  an `id` when it must not merge, or when it should be replaced with something else instead. Declare a
  handler once and reuse it if a toast with an action should merge too.
- In a module that has no component to call `useToast()` from, make one `createToaster()` and give it to
  the provider; keep one provider per toaster.
- `onOpenChangeComplete` says it is gone (its exit has finished); `onOpenChange` says it started to go,
  with the reason: `timeout`, `dismiss`, `action`, `swipe`, `escape` or `programmatic`.
- A toast sits above a modal dialog's scrim and answers a click, whether it was raised before the
  dialog opened or after. The dialog still holds keyboard focus, so a keyboard user can't tab to the
  toast's action while it is open: keep the action available in the dialog's own flow too, and say how
  in `altText`. With focus inside the dialog, `Escape` closes the newest toast first and the dialog on
  the next press.

## Accessibility

<Callout tone="info" title="A live region, not a dialog: announced, never given focus">

- Each toast is announced through a live region that is already in the page when its text arrives.
  `danger` and `warning` use an assertive announcement that interrupts; the other tones are polite and
  wait for a pause. `role="alert"` or `role="status"` overrides the tone.
- The text read out is the notification label, the title and description, and, in place of the action
  button, its `altText`.
- The toasts live in a region named "Notifications (F8)". F8 (the `hotkey` prop) moves focus into it;
  `Tab` then moves through each toast and its buttons, and `Escape` dismisses the toast that has focus.
  When the toasts are gone, focus goes back to where it was before it entered the region, if it is still
  there.
- A toast never takes focus when it appears, and never moves it when it closes while focus is elsewhere.
- In a fan the toasts are in the same document and tab order as in the list, and focus in the region
  spreads it out, so a toast that has focus is whole and its buttons are reachable. A toast behind
  another still announces itself when it appears.
- "Clear all" is in the same tab order as the toasts, so F8 and `Tab` reach it; it is announced when it
  appears with the second toast, and a screen reader reads a replaced toast's new text again.
- While an action's promise runs, its button is marked `aria-busy` and `aria-disabled` and stays
  focusable, so focus isn't lost from a button the person has just pressed.
- The time is paused while the pointer is over the toasts, while focus is inside them and while the
  window is in the background, and a toast can be kept until it is dismissed (`duration: null`).
- The dismiss button and the action are at least 24 by 24 pixels at every size.
- A swipe toward the edge the toast sits against dismisses it; it is a convenience, and the dismiss
  button and `Escape` always work.
- Under `prefers-reduced-motion` a toast fades in and out instead of sliding. In forced-colours mode,
  where a shadow isn't drawn, every toast keeps a border in a system colour.
- The tone is never conveyed by colour or icon alone: put what matters in the text.

</Callout>

## Code examples

```tsx
// Once, near the root of the app
<Toast.Provider placement="bottom-end" limit={3}>
  <App />
</Toast.Provider>

// Anywhere under it
const { toast, update, dismiss } = useToast();

toast({ tone: "success", title: "Saved", description: "Your changes are live." });

{/* An action, with how to do the same thing without it */}
toast({
  title: "Conversation archived",
  action: { label: "Undo", altText: "Undo from the Edit menu", onClick: undoArchive },
});

{/* The same toast again replaces it; update() changes part of it */}
const id = toast({ id: "sync", title: "Syncing…", loading: true });
update(id, { loading: false, tone: "success", title: "Up to date", duration: 3000 });

{/* Follow a promise. It is returned, so it can still be awaited. */}
toast.promise(saveChanges(), {
  loading: "Saving…",
  success: (file) => ({ title: "Saved", description: file.name }),
  error: "Could not save",
});

{/* Until it is dismissed */}
toast({ tone: "warning", title: "You are offline", duration: null });

{/* An action that takes a promise: the toast waits for it, and a failure keeps it open */}
toast({
  title: "Conversation deleted",
  action: {
    label: "Undo",
    altText: "Restore it from Trash",
    onClick: () => restoreConversation(),
    onError: () => toast({ tone: "danger", title: "Could not restore it" }),
  },
});

{/* From plain code, with no component: make a toaster and hand it to the provider */}
export const toaster = createToaster();
toaster.toast({ tone: "danger", title: "Could not reach the server" });
<Toast.Provider toaster={toaster} clearAll mergeDuplicates>
  <App />
</Toast.Provider>

{/* Declared as parts, from your own state */}
<Toast tone="success" open={open} onOpenChange={setOpen}>
  <Toast.Title>Saved</Toast.Title>
  <Toast.Action altText="Open the file from your recent files">View</Toast.Action>
</Toast>

{/* Right to left, and a native attribute passed straight through to the toast */}
<Toast.Provider dir="rtl" placement="bottom-start" />
<Toast aria-describedby="what-was-saved" title="Saved" />
```
