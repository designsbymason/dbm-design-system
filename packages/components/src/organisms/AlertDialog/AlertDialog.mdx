<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>

<ComponentHeader title="AlertDialog" tier="Organism" />

A modal that interrupts for something that has to be answered: a destructive action to confirm, an
error to acknowledge, a decision that can't be left half made. Like a `Dialog`, the page behind it is
dimmed by a **scrim** (a translucent layer over the page), can't be scrolled or clicked, and keyboard
focus is held inside. Unlike a `Dialog`, a press on the scrim does nothing, there is no close button
in the corner, and focus starts on the safest choice, so the alert can only be answered with one of its
own buttons (or Escape, which counts as a cancel). A compound component, meaning it is made of named
sub-parts you compose together: `AlertDialog.Trigger`, then `AlertDialog.Content` holding a `Header`,
an optional `Body` and a `Footer` with `Cancel` and `Action`.

### Import

```tsx
import { AlertDialog } from "@dbm-design-system/components";
```

## Properties

`AlertDialog` itself renders no DOM element of its own: it is a plain context provider around its
sub-parts, so it has no `className`/`style`/`id`/`data-testid`/`ref` of its own to accept.

### AlertDialog.Trigger properties

The element that opens the alert on click. Also accepts any other native `<button>` attribute beyond
what's listed here (e.g. `onFocus`, `disabled`), passed straight through.

<PropertiesTable of={AlertDialogTriggerStories} order={triggerPropOrder} />

### AlertDialog.Content properties

The alert panel with its scrim. Also accepts any other native `<div>` attribute beyond what's listed
here (e.g. `onKeyDown`, `dir`), passed straight through to the panel. `role`, `aria-modal` and
`data-state` are set by the alert and can't be replaced.

<PropertiesTable of={AlertDialogContentStories} order={contentPropOrder} />

The top section: the tone's icon beside a `Title` and a `Description`. Also accepts any other native
`<div>` attribute beyond what's listed here.

<PropertiesTable of={AlertDialogHeaderStories} order={headerPropOrder} />

### AlertDialog.Title properties

The alert's question or statement, rendered as a heading. Takes no `id`: the alert generates one and
points its `aria-labelledby` at it. Also accepts any other native heading attribute beyond what's
listed here.

<PropertiesTable of={AlertDialogTitleStories} order={titlePropOrder} />

### AlertDialog.Description properties

What the choice will do and what can't be undone. An alert needs one. Takes no `id`, for the same
reason as the title. Also accepts any other native `<p>` attribute beyond what's listed here.

<PropertiesTable of={AlertDialogDescriptionStories} order={descriptionPropOrder} />

### AlertDialog.Body properties

Content between the header and the footer: a list of what is affected, say. A scroll region that takes
the height left over. Also accepts any other native `<div>` attribute beyond what's listed here.

<PropertiesTable of={AlertDialogBodyStories} order={bodyPropOrder} />

### AlertDialog.Footer properties

The bottom section holding the buttons. Below `sm` they stack full width with the action on top.
Also accepts any other native `<div>` attribute beyond what's listed here.

<PropertiesTable of={AlertDialogFooterStories} order={footerPropOrder} />

### AlertDialog.Action properties

The choice the alert exists to ask for: a `Button` that closes the alert after its `onClick`. Its look
follows the content's `tone`. It also accepts every other `Button` property (`leadingIcon`, `fullWidth`
and the rest) and any native `<button>` attribute.

<PropertiesTable of={AlertDialogActionStories} order={buttonPropOrder} />

### AlertDialog.Cancel properties

The safe way out: a `Button` that takes focus when the alert opens and closes it as a cancel. It
also accepts every other `Button` property and any native `<button>` attribute.

## Usage guidelines

<div className="dbm-do-dont-grid">
<Callout tone="success" title="Do">

- Use an `AlertDialog` when the person has to choose before anything else can happen: confirming a
  destructive action, acknowledging an error, deciding what to do with unsaved work.
- Write the title as the question ("Delete project?") and the buttons as the answers ("Keep it",
  "Delete"), not "OK" and "Cancel", so each button says what it does on its own.
- Set `tone="danger"` for something that can't be undone: it colours the icon and makes the action
  destructive. Every tone has an icon (a note for `neutral`); pass `icon={false}` to remove it.
- Keep a `Cancel` beside the action, so there is a safe way out and focus has somewhere safe to start.
- Say in the description what can't be undone, not only that something will happen.
- For an unsaved-changes alert with three answers, give each `Action` a `value` ("save", "discard")
  and read it from `onOpenChange`'s `details.value`; put Cancel first and the main choice last.
- For something that can't be recovered, make the person type the name before the action enables, and
  point `initialFocus` at the field.

</Callout>
<Callout tone="danger" title="Don't">

- Don't use an `AlertDialog` for a task with fields to fill in or content to read: that is a
  `Dialog`, which can also be dismissed with a press outside.
- Don't use it for a message that needs no answer. A banner (`Alert`) or a toast says it without
  stopping the person.
- Don't leave out the description: it is what a screen reader reads after the title, and the title
  alone is rarely enough to decide by.
- Don't turn `closeOnEscape` off to make the alert harder to leave. Escape is a cancel; turn it off
  only when closing without an answer would leave the app in a state it can't handle.
- Don't stack alerts: one confirmation opened from a dialog is fine, a second from the first is not.
- Don't turn `nudge` off to hide that a press did nothing: it is the only sign the alert is waiting for
  an answer. Turn it off only where a pulse would be noise (a screenshot test, say).
- Don't add a third choice that closes the alert without a clear label: "Don't save" says what it does,
  "Other" does not.

</Callout>
</div>

## Best practices

- Keep the title to a few words and the description to one or two sentences. An alert that needs a
  paragraph needs a `Dialog` with the content in it, or a page.
- Put the `Cancel` first in the footer and the `Action` last. From `sm` up they sit in a row with the
  action at the end; on a phone they stack with the action on top, which is why the DOM order matters.
- While the action works (a request), set `busy` on the content and `isLoading` on the action, and call
  `event.preventDefault()` in the action's `onClick` so the alert waits. Close it yourself when the
  work is done.
- Use `onOpenChange`'s `reason` to tell a decision (`"action"`, `"cancel"`) from a dismissal
  (`"escape"`), for analytics or to confirm a walk-away.
- Open an alert from a `Dialog` freely, and lighten its scrim (`scrimOpacity={40}`), since the two scrims
  stack.

## Accessibility

<Callout tone="info" title="The alertdialog pattern: named, described, and focus on the safe choice">

- `AlertDialog.Content` is `role="alertdialog"` with `aria-modal="true"`. `AlertDialog.Title` names it
  and `AlertDialog.Description` describes it, wired with `aria-labelledby` and `aria-describedby`
  automatically, so a screen reader reads the question and then what it will do.
- Focus moves to `AlertDialog.Cancel` when the alert opens (to the `Action` when there is no Cancel;
  choose another element with `initialFocus`), so Enter or Space can't confirm by accident.
  `Tab` and `Shift+Tab` loop inside, and focus returns to the trigger on close.
- `Escape` closes the alert as a cancel. A press on the scrim does nothing, with no prop to change that.
- While the alert is open the rest of the page is hidden from assistive technology and can't be
  scrolled or clicked. An alert opened from a dialog hides that dialog too, and `Escape` answers only
  the alert.
- A busy alert is `aria-busy`, and its buttons are `aria-disabled` and dimmed but still focusable, so
  focus isn't dropped from them.
- The tone icon is decorative (`aria-hidden`): the tone is carried by the words, never by the icon or
  colour alone. Each icon is at least 3:1 against its disc in every theme.
- A press on the scrim, or Escape while the alert can't close, gives the panel a short pulse so the
  alert doesn't read as broken. Under `prefers-reduced-motion` the border flashes the focus colour
  instead of the panel moving; the pulse is not announced (the alert is already announced), and turns
  off with `nudge={false}`.
- On a phone the buttons are full width, a comfortable touch target. Under `prefers-reduced-motion`
  the alert fades without moving.

</Callout>

## Code examples

```tsx
<AlertDialog>
  <AlertDialog.Trigger asChild>
    <Button variant="destructive">Delete project</Button>
  </AlertDialog.Trigger>
  <AlertDialog.Content tone="danger">
    <AlertDialog.Header>
      <AlertDialog.Title>Delete project?</AlertDialog.Title>
      <AlertDialog.Description>
        This removes the project and all of its files for good. It cannot be undone.
      </AlertDialog.Description>
    </AlertDialog.Header>
    <AlertDialog.Footer>
      <AlertDialog.Cancel>Keep it</AlertDialog.Cancel>
      <AlertDialog.Action>Delete</AlertDialog.Action>
    </AlertDialog.Footer>
  </AlertDialog.Content>
</AlertDialog>

{/* Three answers: each Action reports its own value */}
<AlertDialog onOpenChange={(open, { reason, value }) => !open && reason === "action" && finish(value)}>
  …
  <AlertDialog.Footer>
    <AlertDialog.Cancel>Keep editing</AlertDialog.Cancel>
    <AlertDialog.Action value="discard" variant="tertiary">Don't save</AlertDialog.Action>
    <AlertDialog.Action value="save">Save</AlertDialog.Action>
  </AlertDialog.Footer>
</AlertDialog>

{/* Wait for a request: the alert stays open while it runs */}
<AlertDialog.Content tone="danger" busy={deleting}>
  …
  <AlertDialog.Action
    isLoading={deleting}
    onClick={(event) => {
      event.preventDefault();
      deleteProject().then(() => setOpen(false));
    }}
  >
    Delete
  </AlertDialog.Action>
</AlertDialog.Content>

{/* Know what answered it */}
<AlertDialog
  onOpenChange={(open, { reason }) => {
    if (!open && reason === "cancel") track("kept project");
  }}
>
  …
</AlertDialog>

{/* A native <div> attribute, passed straight through */}
<AlertDialog.Content aria-describedby="what-is-lost" dir="rtl">
  …
</AlertDialog.Content>
```
