## Post-Finalization follow-up (2026-09-20, at explicit direction) — `rounded` prop

**What was added.** An optional `rounded` boolean (default `false`), the same name and meaning `IconButton` and `CloseButton` already have: fully rounded ends (`radius.full`) — a pill, or a circle when the button is as wide as it is tall. It works with every variant and size, `asChild`, `fullWidth`, icons and the loading state; height, padding and gap don't change. The focus ring follows the shape (`.rounded:focus-visible` sets `radius.full`, the case `05-component-api-conventions.md` §6 names for it), placed after `.root:focus-visible` so it wins on source order, as in `IconButton` and `CloseButton`. No new token — `radius.full` was already used by the spinner. It's declared right after `size` on `ButtonProps` and in the docs' prop order, so the raw Controls panel and the Properties table both read `size, rounded, leadingIcon, …`.

**Finalized status unchanged.** Under the `06-engineering-standards.md` §9 three-question test this is purely additive: with `rounded` unset every existing prop, default, DOM output and token renders exactly as before. The new surface still got its own scoped pass: JSDoc on the prop and the component's `@example`, unit tests (the token on all five variants, an `asChild` link, `rounded={false}` staying on `radius.md`, combined with `fullWidth`/icon/loading, `className` kept), an axe check of a rounded button, a `Rounded` Docs story with a hand-written "Show code" snippet, a Playground control, and a Docs section, usage note, code example and token row.

**Verified in a real browser, not just jsdom.** A hidden `Rounded — interaction test` story (`tags: ["!dev"]`, so it stays out of the sidebar and Docs but runs as a test) checks all 25 size × variant combinations have a corner radius of at least half their height, that a plain button keeps its standard corners, that a full-width pill keeps round ends, and that the keyboard focus ring is round on a rounded button and keeps the standard ring corner on a plain one (`:focus-visible` is asserted to match, so the check can't pass vacuously). Mutation-checked: dropping the `.rounded:focus-visible` rule fails only that story (jsdom can't see it); making `.rounded` use `radius.md` fails the story and the unit tests; never applying the class fails both. Live-checked in Storybook after a dev-server restart (docgen needs one for a changed types file): the `rounded` row is in the Properties table in the right position, the three demo buttons compute `9999px`, and the Playground switch flips a button between `8px` and `9999px` and back.

**Used by `Pagination` (2026-09-20).** `Pagination` passes this prop to its page numbers and arrows instead of styling them itself; see `Pagination.md`.

## Reads an optional `ButtonGroup` context, 2026-09-26 (additive; stays Finalized)

At explicit direction ([ADR-0025](../adr/0025-buttongroup-shares-settings-through-a-context-read-by-button-and-iconbutton.md)), `Button` reads an internal context that `ButtonGroup` provides: inside a group its `variant`, `size` and `rounded` default to the group's (its own props win) and a disabled group disables it; it also emits `data-variant` there, so the group can draw the separator that suits its variant. Outside a group the context is `null` and nothing changes: same output, same classes, no extra attribute. That is purely additive (question 1 of `06-engineering-standards.md` §9's three-question test), so `Button` stays Finalized; the new surface got its own scoped pass in `ButtonGroup`'s suite (props reaching it, own props winning, no leak outside a group, `disabled` OR-ed, `data-variant` only inside a group), each test failing when its behaviour is removed, and all of `Button`'s own tests, its stories and the visual baselines pass unchanged. **One side effect, fixed:** the three props are no longer destructuring defaults, so docgen stopped supplying the Properties table's Default column for `variant`, `size` and `rounded` (found live: "—"); each now states its default in its stories' argTypes.

## `asChild` guard moved to the capture phase, 2026-09-26 (defect fix; stays Finalized)

At explicit direction. Found in `ButtonGroup`'s final review: a link rendered `asChild` on a disabled or loading `Button`, or inside a disabled `ButtonGroup`, set `aria-disabled` but still ran its **own** `onClick` (a router's navigation, say), because the guard was a bubble-phase `onClick` and Radix `Slot` runs the child's own handler first — the bug `05-component-api-conventions.md` §3 documents for `Link`. Confirmed with a probe before the fix, and the existing test hadn't caught it because it only checked `Button`'s *own* `onClick`. The guard is now `onClickCapture` (a caller's own `onClickCapture` still runs when the click isn't blocked), and the bubble-phase branch, now unreachable, is gone. Under `06-engineering-standards.md` §9's three-question test it corrects a genuine defect (question 2), so `Button` stays Finalized. Four new tests: the slotted child's handler and `Button`'s own are both blocked when disabled, the child's handler is blocked and the link not followed while loading, the child's handler, `onClick` and a caller's `onClickCapture` all run in that order when not blocked, and a caller's `onClickCapture` doesn't run on a blocked click — all fail on the old guard (checked), as does a new `ButtonGroup` test for a disabled group.
