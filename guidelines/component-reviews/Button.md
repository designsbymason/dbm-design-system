# Button — Storybook/component review findings

*(Migrated from `07-storybook-and-documentation-standards.md` §6 during the guidelines retrofit pass, 2026-08-31 — this file's own content is unchanged from what was there, just relocated. See `07`'s own status table for this component's current Docs-page/Finalized status.)*

2. Button — ✅ done (Docs page: 2026-07-27, out of the original Phase A sequence). **Comprehensive `06-engineering-standards.md` §9 review pass completed 2026-08-23**, worked one finding at a time, closing the `style` gap previously logged here plus eight more real findings:
   1. `loadingText ?? children` → `||` — an explicit `loadingText=""` (the Storybook meta's own default, to keep the control interactive) silently won over `children`, leaving the button with no visible/accessible label while loading. Same fold-in bug on `disabled ?? isLoading` → `||`, so an explicit `disabled={false}` no longer overrides `isLoading`'s own disabling. Root-caused a previously-mislabeled "Button suppresses children while isLoading" a11y finding (originally surfaced when `@storybook/addon-vitest` was first wired in — `guidelines/adr/0003`) — the real cause was this `??`/`||` bug, not suppressed children.
   2. Confirmed 5th instance of the JSX-attribute-ordering bug (`05-component-api-conventions.md` §3) — `{...props}` now spreads before the computed `aria-disabled`/`aria-busy`/`disabled`/`onClick`/`className`.
   3. Disabled-`asChild` hover leak — every variant's hover rule now guards `:not(.disabled)` alongside `:not(:disabled)`, since `:disabled` can never match a non-form slotted element.
   4. Six stories (`AllVariants`/`AllSizes`/`WithIcons`/`FullWidth`/`AsChild`/`AsChildDisabled`) had `render` functions ignoring `args` entirely — fixed to accept and spread them, matching the Tag/Badge/ProgressBar precedent.
   5. Two dev-mode warnings added: no accessible name, and `leadingIcon`/`trailingIcon`/`isLoading` silently ignored under `asChild`.
   6. `style?: CSSProperties` added, closing the gap this entry previously flagged.
   7. Focus-ring radius standardized to `radius.sm` (`.root:focus-visible`), overriding `.root`'s own `radius.md` — Button has no separate wrapper the way Avatar does, so this slightly tightens the button's own visible corners while focused, accepted as a documented trade-off.
   8. `isLoading`'s JSDoc corrected to state the spinner/label-swap doesn't render at all in `asChild` mode (only dimming/`aria-disabled` do) — also fixed a stale `Button.mdx` code snippet left over from finding #1's `??`→`||` fix.
   9. (Feature-completeness note only, deliberately deferred, not built: Chakra's spinner-customization escape hatch — `isLoading`/`loadingText` already cover the real need.)
   10. Playwright hover-regression pair added for finding #3 (jsdom can't exercise `:hover`), plus a stale story ID (`atoms-core-button--all-variants`, pre-dating the sidebar taxonomy correction) fixed in the same file.

   Also restyled at explicit direction, same review window: `secondary` (transparent fill → `border.brand` border, `text.brand` label, `icon.brand` icon, `bg.brand-subtle-hover` on hover — `border.brand`'s first real consumer, unused since Phase 22), `tertiary` (`text.primary`→`text.brand`, `bg.neutral-subtle`→`bg.brand-subtle-hover` on hover), and `ghost` (`text.secondary`→`text.brand`, transparent→`bg.brand-subtle` at rest, `bg.brand-subtle-hover` on hover) — see `03-token-system-spec.md`'s Contrast verification section (the `border.brand`/`text.brand`/`icon.brand`/`bg.brand-subtle-hover` rows) for the full token rationale. Every variant's icon now gets an explicit tone (`iconToneForVariant` no longer has an `undefined` case). Found along the way: the checked-in `e2e/visual.spec.ts` screenshot baseline didn't reliably catch any of the three color-only recolors (confirmed empirically — passed against the stale pre-restyle baseline every time, `ghost`'s included, despite a real fill-color change) — added real-browser computed-style Playwright tests for `secondary`/`tertiary`/`ghost` instead of relying on the screenshot diff, which stays useful for structural regressions but isn't sensitive enough for this class of change. Two smaller fixes in the same window: the `asChild` anchor's default browser underline removed (`text-decoration: none` on `.root` — a native `<button>` never has one, so Button shouldn't look different depending on which element it renders onto), and `xl`'s `padding-block` nudged from `space.5` to `space.4` at explicit direction (now identical to `lg`'s — `xl` still reads larger via its bigger font-size/gap/padding-inline).

Fixed by explicitly redeclaring `disabled`/`onClick` directly on `ButtonProps` (real JSDoc, positioned to match `propOrder`) and swapping `fullWidth`/`asChild`'s interface order to match `propOrder` too (a pre-existing minor mismatch, same fix). Zero behavioral/DOM/token change — pure type/doc reorganization — so per `06-engineering-standards.md` §9's three-question test this **stays finalized**. Full self-verification: `tsc`, `eslint`, `tsup` build, both Vitest projects (`unit`: 715/715, `storybook`: 274/274) all clean; live-reconfirmed the raw Controls panel and the Docs page's own Properties table both now read `children, variant, size, leadingIcon, trailingIcon, isLoading, loadingText, fullWidth, asChild, type, disabled, onClick, aria-label, aria-labelledby, id, className, style, data-testid` — an exact match to `propOrder`. **Regression caught and fixed, 2026-08-24 (found live by direct user report, same day):** redeclaring `onClick` with a concrete `MouseEventHandler<HTMLButtonElement>` type (above) had a side effect the ordering fix didn't anticipate — Storybook's control-type inference now resolved a real object-shaped type for it and defaulted its Controls-panel row to an inert "Set object" placeholder, instead of the "–" a function prop should show per `07-storybook-and-documentation-standards.md` §5's own rule (a real control or `control: false`, never an inert placeholder). Fixed with an explicit `control: false` on `onClick`'s `argTypes` entry in `Button.stories.tsx` (documented inline with the same root cause). This is a real, general side effect of the redeclare-for-ordering fix pattern above — **any prop redeclared this way whose resolved type is a function or otherwise not a plain primitive/enum needs an explicit `control` check afterward**, not just an order check; noted in `07-storybook-and-documentation-standards.md` §4.1's shared root-cause note too. No dev-server restart needed for this part — `control` overrides are picked up live, unlike the ordering fix itself. Verified: `eslint`, both Vitest projects (`unit`: 715/715, `storybook`: 274/274), `tsup` build, and a live re-check showing `onClick` back to `–`.
