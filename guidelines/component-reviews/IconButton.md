IconButton — ✅ done (2026-08-24 — comprehensive `06-engineering-standards.md` §9 review, worked one finding at a time across 15 findings): (1) Playground story added (icon/type controls fixed from broken placeholders, every prop given a real default). (2) Fixed a confirmed recurring bug: disabled `asChild` hover leak (missing `:not(.disabled)` guard on hover rules) — Playwright regression pair added. (3) Fixed the JSX-attribute-ordering bug (`{...props}` now spreads before computed `aria-*` attributes, matching Button/ProgressBar/Spinner's own fix). (4) Explicitly redeclared `className`/`style`/`id`/`data-testid`/`onClick`/`type`/`disabled`/`aria-labelledby` for Storybook Properties-table and Controls-panel visibility. (5) Fixed a token-category violation: `secondary`/`tertiary`/`ghost` were coloring themselves via `text.*` tokens instead of `icon.*` ones — this component renders nothing but an icon, so it should never have used a text token. (6) Fixed the `AllVariants`/`AllSizes` stories' dead Controls panel (`render` ignored `args`). (7) Resolved as a side effect of #1. (8) Added the standardized focus-ring `border-radius` (`sm` / `full` for `rounded`). (9) Added dev-mode warnings (no accessible name; `asChild` ignoring `icon`/`isLoading`). (10) Fixed `disabled ?? isLoading` and `loadingLabel ?? ariaLabel` — both switched to `||`, since an explicit `false`/`""` shouldn't silently win over the computed value. (11) Added toggle/pressed-state support (`pressed`/`defaultPressed`/`onPressedChange`, mirroring Radix `Toggle`'s own naming per `05-component-api-conventions.md` §3). (12) Ported Button's brand-colored restyle (see `border.brand`/`text.brand`/`icon.brand` in `03-token-system-spec.md`'s Contrast verification section) to `secondary`/`tertiary`/`ghost`, matching Button's own visual identity. (13)/(14) Found moot/redundant once the box-size-matching work (below) landed: `IconButton` gained an `iconSizeForButtonSize` lookup map early in the review to bridge its own size scale to `Icon`'s, but once `size` was matched 1:1 to `ButtonSize` (a literal subset of `Icon`'s own size type), the map became a same-key-to-same-key no-op — removed, `size` now passes straight through to `Icon`. (15) `IconButton.mdx` Docs page added from scratch, full 10-section template mirroring Button's.

  Additional work beyond the numbered findings, at explicit direction: matched `IconButton`'s box size (all 5 steps, square and rounded) to Button's real rendered height at the equivalent step — new `packages/tokens/src/component/icon-button.json` component-layer tokens, since none of the 5 measured pixel values land on the shared `space.*` scale (same precedent as `Avatar`'s own size tokens); and redesigned the pressed-state treatment per tone family — `primary`/`destructive` invert to that tone's own `-subtle` tint, `secondary`/`tertiary`/`ghost` converge to a solid `bg.brand`/`icon.on-brand` fill, and the icon switches to Phosphor's "fill" weight while pressed, reinforcing the toggle state visually beyond color alone (contrast pairings logged in the final review pass below).

  Writing the Docs page (finding #15) surfaced a real layout bug in the shared `TokenRow` block (`.storybook/blocks/TokenRow.tsx`, consumed by 10 components' own Docs pages) via `IconButton`'s own long `icon-button.size.xs–icon-button.size.xl` token — two rounds of real fixes, not one: a first attempt (wrapping `<code>` in a `<span>` so it could hug short tokens) reverted `<code>` to native `display: inline`, which fragments its background per line — wrapped continuation lines lost their left padding and visually overlapped the row above (caught live via a user-provided screenshot). Reverting to a direct-flex-item `<code>` with `maxWidth` fixed the fragmentation but introduced a second bug — short tokens like `radius.sm` started wrapping unnecessarily, because the default `flex-shrink: 1` lets the flex algorithm squeeze a `break-word`-enabled item's width down toward its (now much smaller) min-content size any time the row is remotely tight. Root-caused via live `getBoundingClientRect` measurements, not guessed. Fixed with `flexShrink: 0` (letting `maxWidth` alone do the capping/wrapping, since max-width clamps the used width regardless of shrink factor). Then, per explicit follow-up feedback that pill sizes read "unbalanced" against each other, changed from a `maxWidth` cap (pills hug their own content, so a page mixing short and long token names doesn't line up) to a fixed `13.5rem` width sized to the longest real semantic token found across every `TokenRow` usage in the codebase (`motion.easing.emphasized`, 24 characters, measured live via canvas `measureText` against the pill's actual computed font/padding/border) — every pill in a component's token section is now the same size and the `usage` description column lines up in a straight edge, while longer component-layer/range tokens (`icon-button.size.xs–icon-button.size.xl`, `badge.size.xs–badge.size.xl`, etc.) still wrap cleanly within the fixed-width pill instead of overflowing or fragmenting. Verified live across all 10 `TokenRow` consumers (IconButton, Button, Checkbox, Skeleton, Spinner, ProgressBar, Avatar, Tag, ProgressCircle, Badge) with zero non-uniform pill widths.

  **Final review pass** (2026-08-24, same day): re-verified the full checklist end to end rather than assuming the 15 findings plus extra work already covered everything, the same discipline as Button's/Checkbox's own final passes — combined live verification (theming across Purple/Emerald × Light/Dark, responsiveness at mobile width, keyboard-focus/native-button-semantics confirmation) with a fresh, skeptical static-code audit, and found three more real gaps, each independently re-verified before being trusted. (1) **Real accessibility violation, confirmed live via a scoped jest-axe check before fixing:** `aria-pressed` was set unconditionally, including in `asChild` mode — `aria-pressed` is only a valid ARIA attribute on a role that supports it (e.g. `button`), not on every element `Slot` might render onto (a native `<a>`'s `link` role disallows it), so `<IconButton asChild defaultPressed><a>...</a></IconButton>` — a real, already-tested combination — rendered an anchor with an `aria-allowed-attr` violation (impact: critical), invisible to the existing test suite since the one test covering this combination checked the attribute's value but never ran it through axe, and the only pressed-state axe test used a native `<button>`, not `asChild`. Same bug class this section's own precedent already named (Avatar's `role="img"` + `as="button"`, `06-engineering-standards.md` §9). Fixed: `aria-pressed` now withheld whenever `asChild` is set (`isToggle && !asChild`), with a new dev-mode warning explaining why and how to work around it (mirroring the existing `asChild`-ignores-`icon` warning pattern), the previously-wrong test corrected, a new test confirming the pressed *visual* class still applies regardless, the missing axe test added (zero violations now), and 3 tests covering the new warning's gating. (2) `AsChild`/`AsChildDisabled` stories had the same dead-Controls-panel bug already fixed once in this same review (finding #6, `AllVariants`/`AllSizes`) and on Button/Checkbox/Tag/ProgressBar before it — both used a bare `render: () => (...)`, hardcoding `icon`/`aria-label` and ignoring every other arg. Confirmed live (setting `size` to `xl` via a URL-args override left the canvas at `md`, unchanged) before fixing; fixed by mirroring Button's own already-fixed `AsChild`/`AsChildDisabled` pattern exactly (`render: (args) => <IconButton {...args} asChild>...`), then re-confirmed live via the same URL-args technique (size/variant/rounded all now drive the canvas correctly). (3) The pressed-state redesign's own new color pairings had no logged contrast ratio, despite `IconButton.mdx`'s own Accessibility section already claiming every state pairing was checked — computed directly from the built primitive values rather than assumed: `icon.brand` on `bg.brand-subtle` (`primary`'s pressed state) turned out to already be covered by an existing log entry under a different name (`icon.brand`/`text.brand` share the exact same primitive value in every theme/mode, confirmed Phase 39, and `text.brand`/`bg.brand-subtle` was already logged in full, Phase 11); `icon.danger` on `bg.danger-subtle` (`destructive`'s pressed state) was genuinely new and unlogged — **4.86:1 light, 10.32:1 dark** — both logged here, with the tight light-mode margin flagged explicitly — this specific pairing (icon.danger *on* bg.danger-subtle, not bg.danger-subtle's own primary pairing) is finer-grained than `03-token-system-spec.md`'s own current-state table tracks, so this entry is its record. Full self-verification, whole package: `tsc` (package + `.storybook`), `eslint`, `tsup` build, both Vitest projects (`unit`: 756/756, `storybook`: 275/275), Playwright (8/8), and the Foundations token-coverage check (in sync) all clean. **Finalized 2026-08-24** — per that section's own note, don't make further changes to IconButton (code, stories, docs, or its tokens) without asking first.

  **Real defect found and fixed, 2026-08-30, at explicit direction (Storybook/docs only — `IconButton.tsx` itself untouched, so per the three-question test in `06-engineering-standards.md` §9 this stays finalized):** every single story in `IconButton.stories.tsx` — not just the Playground — rendered in toggle mode (`aria-pressed` set, pressed styling reachable) by default, because the shared `meta.args` set `defaultPressed: false`. `isToggle`'s own check is `defaultPressed !== undefined`, not a truthiness check — `false` is still a defined value, so this silently forced toggle semantics onto `AllVariants`/`AllSizes`/`Loading`/`Disabled`/`Rounded`/`AsChild`/`AsChildDisabled` too, none of which had anything to do with toggling. No story anywhere demonstrated the component's actual, real default (non-toggle) appearance — found via direct user observation of the Playground, confirmed by reading the code rather than assumed. `IconButton.mdx`'s own Code examples section had the identical bug baked into a real snippet: `<IconButton ... defaultPressed={false} />` was presented as if it were the plain/non-toggle example, when it actually opts into toggle semantics (starting unpressed) — corrected to a genuine non-toggle example (no `pressed`/`defaultPressed`/`onPressedChange` at all) plus a clarifying uncontrolled-toggle example alongside the existing controlled one.

  Fixed by porting Tag's own "Interaction mode" synthetic-select pattern (`06-engineering-standards.md` §9 precedent, `Tag.stories.tsx`'s `Playground`) rather than just deleting the default: `defaultPressed: false` removed from the shared `meta.args` entirely (so every story's real default is now genuinely non-toggle, not just the Playground's), `pressed`/`defaultPressed`/`onPressedChange` all set to `control: false` at the meta level (a bare boolean can't represent "not a toggle at all" — true and false both keep `isToggle` true, the actual root cause), and the Playground story gained a Playground-only `interactionMode: "Non-toggle" | "Toggle"` select (not a real `IconButtonProps` field) that composes `defaultPressed`/`onPressedChange` into the render only when "Toggle" is selected, defaulting to "Non-toggle" — IconButton's real zero-extra-props default. `IconButton.mdx`'s `PlaygroundControls.exclude` updated to add `defaultPressed` alongside the already-excluded `pressed`/`onPressedChange`. The dedicated `Toggle` story (unchanged, sets its own local `defaultPressed`/`onPressedChange` args) still correctly demonstrates toggle mode independent of any of this.

  Live-verified, not just typechecked: `Playground` with "Non-toggle" selected renders zero `aria-pressed` attribute; switching to "Toggle" live-adds `aria-pressed="false"` and clicking the canvas button visibly applies the pressed fill + `onPressedChange` firing (Actions panel count incrementing); `AllVariants`'s 5 buttons all confirmed `aria-pressed: null` post-fix (previously all toggle-mode); the dedicated `Toggle` story unaffected (`aria-pressed="false"` on load, as before). The Playground's own raw `interactionMode` control (undecorated camelCase label, since `PlaygroundControls` doesn't read `argType.name` the way Storybook's native Controls panel does) is expected, matching the exact same already-shipped, already-accepted characteristic on Tag's own finalized Docs page — confirmed by checking Tag's page live, not assumed to match.
