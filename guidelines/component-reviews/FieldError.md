# FieldError — Storybook/component review findings

*(Migrated from `07-storybook-and-documentation-standards.md` §6 during the guidelines retrofit pass, 2026-08-31 — this file's own content is unchanged from what was there, just relocated. See `07`'s own status table for this component's current Docs-page/Finalized status.)*

FieldError — ✅ done (2026-08-28 — comprehensive `06-engineering-standards.md` §9 review, worked one finding at a time across 8 findings): (1) `Default` story renamed to `Playground`, every prop wired live via `args`/`argTypes` (`children`, `icon`, `disabled`), replacing the old non-interactive story. (2) Confirmed 7th instance of the JSX-attribute-ordering bug (`05-component-api-conventions.md` §3) — `{...props}` now spreads before the computed `role`/`className` (previously spread *after* them, the only reviewed component found with the ordering already backwards rather than merely undeclared). (3) Destructuring order corrected to `children` first, matching every other reviewed component's own parameter-list convention (previously `icon, className, children`). (4) Added `disabled?: boolean`, matching `FieldLabel`'s/`FieldHelperText`'s own identical prop and direct-token-swap mechanism (`text.disabled`, not the opacity-composited mechanism other components use) — the new `Disabled` story's own live a11y scan correctly caught `text.disabled`'s already-accepted WCAG exemption for disabled-state text (`03-token-system-spec.md`'s Contrast verification section, Methodology), resolved with the same `parameters: { a11y: { test: "todo" } }` annotation `FieldLabel`/`FieldHelperText` already carry. (5) Feature-completeness gap, proposed and confirmed before building rather than added silently: `icon` extended from a bare `boolean` to `boolean | PhosphorIcon`, matching `Checkbox`'s/`ListItem`'s own override convention — `false` hides it, a component reference overrides the glyph, wired into a curated `argTypes.mapping` select (`Default`/`Hidden`/`Star`/`Heart`, same pattern as `Checkbox`'s `icon`) and a new `CustomIcon` story. (6) No micro-interaction on mount — added a one-shot fade/slide-in (`motion.duration.fast` / `motion.easing.emphasized`), reasoning the component's own mount *is* its state change (a field going invalid), the same relationship `Tooltip`'s fade has to its own open transition; outside `06-engineering-standards.md` §4's `prefers-reduced-motion` requirement (one-shot, not looping — same carve-out as `Badge`'s pop and `Tooltip`'s own fade). (7) Regression test added proving a consumer-supplied `role` can't override the computed `role="alert"` (`ProgressBar`'s own exact precedent for this bug class) — verified the test actually catches a regression by temporarily reverting finding #2's fix, confirming the test failed as expected, then restoring it. (8) `FieldError.mdx` Docs page added from scratch, full 10-section template mirroring `CloseButton.mdx`.

  Writing the Docs page (finding #8) surfaced a real, previously-invisible CSS bug, found live by direct user report ("shouldn't the playground instance... be color danger instead of gray?"): every non-`disabled` `FieldError` instance embedded in a `<Canvas>` rendered `text.secondary` gray instead of `text.danger` red — only the `Disabled` story looked correct, by coincidence (its own `.disabled` class rule happened to still out-rank the competing selector on its own). Root cause: `FieldError`'s root element is a bare `<p>`, and `.storybook/docs.css`'s own markdown-prose rule (`.sbdocs-content p, .sbdocs-content li` — added 2026-08-10 for `Callout`'s Do/Don't lists) has higher specificity (0,1,1) than `FieldError`'s own single-class color rule (0,1,0); every `<Canvas>`-embedded live story renders inside `.sbdocs-preview`, itself a descendant of `.sbdocs-content` — nothing before `FieldError` had a bare `<p>`/`<li>` root to collide with it on tag name. Fixed by excluding `.sbdocs-preview` descendants from that rule (`:not(.sbdocs-preview *)`) rather than trying to out-rank it, so a live component's own CSS module is always the only thing setting its own text styling inside a Canvas. Verified via computed-style checks: `text.danger` now resolves correctly on all 4 non-disabled instances; `text.disabled` still correct on `Disabled`; real MDX prose (the Intro paragraph, `Callout` list items) unaffected; `CloseButton.mdx` re-checked for regression, unaffected. **This same bug is latent for `FieldHelperText`**, since it also roots on a bare `<p>` — resolved automatically once that component gets its own Docs page, no additional fix needed there.
