# CloseButton — Storybook/component review findings

*(Migrated from `07-storybook-and-documentation-standards.md` §6 during the guidelines retrofit pass, 2026-08-31 — this file's own content is unchanged from what was there, just relocated. See `07`'s own status table for this component's current Docs-page/Finalized status.)*

CloseButton — ✅ done (2026-08-25 to 2026-08-27 — comprehensive `06-engineering-standards.md` §9 review, worked one finding at a time across the 11-item list established at the start of the pass): (1) Playground story added — every prop wired live via `args`/`argTypes` (`size`, `iconSize` at the time, `aria-label`, `type`, `disabled`, `onClick`), replacing the old non-interactive `Default` story. (2) Unified `size`/`iconSize` into a single `size: ButtonSize` prop — dropped `iconSize` entirely, box always equals the icon 1:1; traced `Tag`'s own call site first (it already passed the same value to both props) and confirmed zero visual regression via live `getBoundingClientRect` checks in the real preview iframe before committing to the change.

  **Mid-review architectural pivot, at explicit direction (2026-08-25):** `CloseButton`'s original design inherited `currentColor` from context specifically so it could double as `Tag`'s own remove-button implementation. Direct feedback that the resulting style didn't match `IconButton`'s own `tertiary` variant (background/hover/icon-color/padding all different) surfaced the real conflict underneath: `Tag` needed tone-adaptive coloring, `IconButton`-parity needed a fixed brand color — one component could no longer serve both. Resolved by **detaching `Tag` from `CloseButton` entirely**: `Tag`'s non-interactive removable path now renders a small, locally-implemented `<button>` (`Tag.module.css`'s own `.removeButton` class + a 3-step size scale mirroring the old box dimensions exactly), colored via the same `iconTone` mechanism its interactive decorative-span path already used — not `currentColor` inheritance. Verified live: box/glyph sizing (20×20, zero padding, matching leading/trailing icons), tone-matched color (`icon.danger` confirmed on a `danger` tag), hover fill, and the focus-visible ring all identical to the pre-detachment behavior; every stale `CloseButton` reference in `Tag`'s own comments/JSDoc/`.mdx` updated. This produced a new standing rule, not a one-off: `05-component-api-conventions.md` §10 — `CloseButton` is reserved for modal-style surfaces (Dialog, Drawer, lightbox); any tone-varying component (Tag, Alert, Toast) implements its own local remove control by default, `CloseButton` only when explicitly requested.

  With `Tag` decoupled, restyled `CloseButton` to match `IconButton`'s `tertiary` variant exactly: `icon.brand` icon color (fixed, no longer `currentColor`), `bg.brand-subtle-hover` on hover, and box sizing switched from the tight `icon-size-*` scale to `IconButton`'s own `icon-button-size-*` component tokens (previously visibly smaller than `IconButton`'s hover footprint at a matching size, per direct report) — verified live, side-by-side against `IconButton` tertiary at `size="md"`: identical box, icon position/size, rest state, and color.

  (3) Added `rounded?: boolean` (default `false`), matching `IconButton`'s own prop, default, and CSS mechanism exactly, including its standardized `sm`/`full` focus-ring radius block. (4) Added `hasBackground?: boolean` — an optional translucent grounding layer for use over unpredictable external content (a photo, a busy hero image) — backed by a **new token, `bg.scrim`** (mirrors `bg.overlay`'s own pattern: an opaque color, opacity composited separately at the CSS layer via a `::before` pseudo-element rather than baked into the token). **Real bug found and fixed during live verification:** the scrim was completely invisible despite every computed style reading correctly (background-color, opacity, position) — `.hasBackground` had `position: relative` but no explicit stacking context, so the pseudo-element's `z-index: -1` escaped to the *parent's* stacking context instead of staying local; fixed with `isolation: isolate`. `bg.scrim` was later revised at explicit direction to be mode-specific (white in light mode, `gray.800` — the same step `bg.surface` itself uses — in dark mode, not a flat white everywhere) with its opacity lowered from `opacity.80` to `opacity.40`; verified live across all 4 theme combinations. (5) Redeclared `type`/`disabled`/`onClick`/`aria-label`/`aria-labelledby`/`id`/`className`/`style`/`data-testid` on `CloseButtonProps` with full JSDoc — required a dev-server restart to see the raw Controls-panel reorder take effect (this project's own documented docgen-cache gotcha), confirmed live afterward: all 12 props render in the declared order, `data-testid` now visible, `onClick` correctly shows `-` rather than an inert placeholder.

  **Collateral fixes found while checking for stale references, all `CloseButton`-adjacent, not part of the numbered list:** `Icon.types.ts`'s JSDoc cited `CloseButton` as its canonical currentColor-inheritance example (now false post-restyle, generalized); two broken `RelatedCard` links to `CloseButton` in `Button.mdx`/`IconButton.mdx` (one pointed at a Docs page that never existed, one at the `--default` story renamed to `--playground` in finding #1 — a regression from this same review, caught before wrapping up) — both fixed and, once `CloseButton.mdx` itself existed, updated again to point at the real `--docs` route.

  (6) Fixed `AllSizes`'s dead Controls panel (`render` ignored `args`) — matching `IconButton`'s own already-fixed precedent; `size`/`aria-label` fixed per instance (the whole point of the grid), every other prop live and shared. Verified live: toggling `rounded` in the Controls panel switched all 5 instances from `radius.md` to `radius.full` simultaneously. (7) `CloseButton.mdx` Docs page added from scratch, full 10-section template mirroring `IconButton.mdx` — verified section by section live (all 10 `h2`s present, Properties table's 12 rows all populated, `PlaygroundControls` correctly excludes the 6 non-editable props, all 3 `RelatedCard`s render valid live previews with no nested-interactive HTML issues, dark mode renders correctly).

  **Final review pass** (2026-08-27, same day as finalization): re-verified the full checklist end to end rather than assuming the incremental findings already covered everything, the same discipline as Button's/Checkbox's/IconButton's own final passes — found two more real gaps. (1) `jest-axe` had only ever run against the bare default render — `disabled`, `rounded`, and `hasBackground` were each only assumed safe by inference, the same gap class Checkbox's own final review closed for its `hasError`/`disabled` states. Added 3 new axe tests covering all three; all pass. (2) Never checked at mobile viewport — verified live at 375px: title/badge wraps cleanly, the Playground controls grid collapses to 1 column, the Properties table's own horizontal scroll is contained (confirmed the *page* itself never overflows, not just eyeballed), the card grid collapses to 1 column, zero overflow on `AllSizes`/`OnBusyBackground`. Also re-confirmed live, beyond what individual findings already checked: the full theming matrix (Emerald had only been spot-checked via Purple's own precedent until this pass — confirmed `emerald-light`/`emerald-dark` icon colors and hover fills resolve correctly, and `bg.scrim`'s dark value is brand-agnostic, `gray.800` in both `purple-dark` and `emerald-dark`), and `OnBusyBackground`'s Controls panel (a custom `render`, the exact bug class this whole review kept finding elsewhere) genuinely drives its canvas.

  **`asChild` explicitly considered and declined, at explicit direction:** checked precedent (MUI has no dedicated `CloseButton`, Chakra's has nothing equivalent, Radix's `Dialog.Close` is behavior-only) and flagged per the checklist's own scope-creep guardrail rather than silently deciding either way — declined; `CloseButton`'s role is narrow enough (a fixed dismiss action, not a general trigger) that no concrete forcing use case was named.

  Full self-verification, whole package, repeated after every finding: `tsc` (package + `.storybook`), `eslint`, `tsup` build, both Vitest projects (`unit`: 768/768, `storybook`: 276/276), and the Foundations token-coverage check (78/78 in sync) all clean throughout. **Finalized 2026-08-27** — per that section's own note, don't make further changes to CloseButton (code, stories, docs, or its tokens) without asking first.
