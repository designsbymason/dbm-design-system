# FieldHelperText — Storybook/component review findings

FieldHelperText — ✅ done (2026-08-28 to 2026-08-29 — comprehensive `06-engineering-standards.md` §9 review, worked one finding at a time across 6 findings): (1) `Default` story renamed to `Playground`, every prop wired live via `args`/`argTypes` (`children`, `disabled`) — confirmed live first: `disabled`'s Controls-panel row rendered an inert "Set boolean" placeholder (no default in the old `args`), not a live toggle. (2) `children` had no JSDoc at all — added (`/** The helper/hint text content. */`, matching `FieldError`'s own one-line style for its content prop). (3) `id`/`className`/`style`/`data-testid` redeclared on `FieldHelperTextProps` with full JSDoc — previously only worked via native inheritance, invisible/undocumented in the type itself, the same gap already fixed on `FieldError`/`FieldLabel`/`Checkbox`. (4) `children`/`disabled` reordered to content-first in both the type interface and the component's own destructuring (previously `disabled` before `children` in both places) — matches `FieldError`'s own Finding #3 precedent. (5) Judgment call, explicitly declined rather than built: proposed the same one-shot mount fade-in `FieldError` got, flagged with a weaker rationale (helper text is typically static/always-present, not a discrete state change the way an error message appearing is) — **declined at explicit direction**, no animation added. (6) `FieldHelperText.mdx` Docs page added from scratch, full 10-section template mirroring `FieldError.mdx`.

  Live mobile-width verification during finding #6 caught a **real, previously-undetected bug in shared infrastructure**: `ComponentHeader`'s title (`FieldHelperText`, 15 characters — longer than every previously-tested title, e.g. `ProgressBar`'s 11) overflowed the page horizontally at 375px. The 2026-08-22 `flexWrap` fix only solved title+badge wrapping onto two lines; it didn't help once the title *alone*, as one unbreakable CamelCase word, was wider than the viewport — flex items default to `min-width: auto`, which floors their shrink at the unbreakable content width. Fixed in `.storybook/blocks/ComponentHeader.tsx` with `minWidth: 0` + `overflowWrap: "break-word"` on the `<h1>` itself (the same property already used for this exact failure mode on `.sbdocs-content p`/`li`). Shared infrastructure, so it benefits every future long-named component too; confirmed no regression on `FieldError`'s shorter title.

  Found live by direct user report, after finding #6 shipped: `FieldHelperText.mdx`'s own Related Components card previewing `FieldError` rendered `text.secondary` gray instead of `text.danger` red — a second, distinct instance of the exact bug class `FieldError.mdx`'s own review had already found and fixed (line 184 above), but in a *different* embedding mechanism this time. Root cause: `RelatedCard`'s preview slot (`.storybook/blocks/RelatedCard.tsx`) is a plain div, not a real Storybook `<Canvas>` block, so it never inherited `sb-unstyled` (Storybook's own internal marker exempting live-rendered content from the Docs page's base MDX typography) the way a `<Canvas>`'s own `.sbdocs-preview` wrapper already does for free — leaving it exposed to *two* competing rules: this project's own `.sbdocs-content p` prose rule, and a second, previously-undiscovered one, Storybook's own base MDX typography (which carries the identical `:not(.sb-unstyled, .sb-unstyled p)` exemption). Fixed by adding `sb-unstyled` directly to `RelatedCard`'s preview slot — the same marker a `<Canvas>` already carries — and simplifying `docs.css`'s own prose-rule exclusion from the bespoke `.sbdocs-preview`-only clause down to one unified `:not(.sb-unstyled *)`, covering both embedding mechanisms (and any future one that reuses the same convention) with no further docs.css changes needed. Verified no regression on `FieldError`'s own Docs page, `FieldError`'s own Related Components section, and `CloseButton`'s Docs page.

  Found live by direct user report, same day: `FieldHelperText.mdx`'s own Properties table had its "Value options" header wrap onto two lines, while `FieldError.mdx`'s copy of the same shared table stayed on one — `table-layout: auto` sizes every column purely from that page's own row content, and `FieldHelperText`'s narrow `true`/`false` pills gave the column less natural width than `FieldError`'s wider icon-name pills, squeezing the two-word header. Fixed with `white-space: nowrap` on every `.dbm-proptable th` (a column header should never wrap regardless of a given component's row content — the same reasoning the pre-existing `td:first-child` fix already applied to the Name column's `<code>` values, generalized to every header). This surfaced a second, related question directly from the user: given `PropertiesTable` is shared across every Docs page, shouldn't its column *widths* also be visually consistent page to page, the same way `TokenRow`'s pill column already was fixed to be? Confirmed via live measurement, not assumption — at the same 812px table width, Name/Value options/Default varied meaningfully across 14 sampled Docs pages (Name 124–172px, Value options 119–216px, Default 74–140px), while Description silently absorbed whatever was left. Fixed the same way `TokenRow`'s pill width was: fixed widths sized to the longest real content already found in the codebase (not a guess) — `10.75rem` for Name (`Checkbox`'s `indeterminateIcon`), `13.5rem` for Value options (`Box`'s `as` prop, 9 wrapped element-name pills — coincidentally the exact value `TokenRow`'s own pill column already uses), `8.75rem` for Default (`Badge`'s own default value) — leaving Description as the one column that still flexes. This directly reverses the 2026-08-15 Name-column comment's own "no guessed fixed pixel value... regardless of how long any given prop's name is" reasoning; documented as a deliberate revision in `docs.css`, not a silent overwrite. Verified live: every sampled table (`FieldHelperText`, `FieldError`, `Box`) now measures identically; `Box`'s own 9-pill `as` column (the widest real case) still wraps cleanly with zero overflow/truncation; mobile-width still degrades correctly (table scrolls within its own container, zero page-level overflow). Shared infrastructure — every other component's Properties table, reviewed or not, reads consistently now too.
