# Tag — Storybook/component review findings

*(Migrated from `07-storybook-and-documentation-standards.md` §6 during the guidelines retrofit pass, 2026-08-31 — this file's own content is unchanged from what was there, just relocated. See `07`'s own status table for this component's current Docs-page/Finalized status.)*

Tag — ✅ done (2026-08-22 — comprehensive Docs page added, modeled on Avatar's/Badge's own template: Playground, Properties table, Variants gallery, Usage guidelines, Best practices, Accessibility, Code examples, Design tokens, Related components). A full `06-engineering-standards.md` §9 review pass followed the same day and found two real gaps: (1) Feature-completeness, against this project's own `05-component-api-conventions.md` §8 definition of done ("...including error and disabled states") as well as MUI Chip's comparable `disabled` prop and this repo's own `Avatar` precedent — Tag had no `disabled` state at all. Added `disabled?: boolean`, scoped to "only meaningful once interactive" (mirrors `Avatar`'s own gate, generalized for a component with no `as`/native-button branch at all — see `05-component-api-conventions.md` §3's new bullet on this), blocking `onClick`/keyboard toggle/remove and applying `aria-disabled` while staying focusable (WAI-ARIA APG pattern, not native `disabled`, since Tag's root is always a `<span>`); also redeclared `aria-label`/`aria-labelledby` explicitly on `TagProps` (`05-component-api-conventions.md` §3's "redeclare component-relevant aria-* props" rule — functionally already passed through via native prop inheritance, but wasn't documented/visible in the Properties table or Playground before this). Both shipped with full JSDoc, CSS (`.disabled` class, `:not(.disabled)` added to all 24 hover rules), a new "Disabled (interactive)" story plus an interaction-test story, 8 new unit tests, and Docs-page coverage (Properties/Playground/Variants/Accessibility/Design tokens all updated) — live-verified across both brand themes × both color modes, Storybook's own Accessibility addon (0 violations), and the `storybook` Vitest project (every play function, including the new one, in a real browser). (2) Responsiveness, caught live via the viewport check required by this same review pass: the "All sizes" story's demo container was missing `flexWrap: "wrap"` (present on every sibling multi-instance story — `AllTones`/`Solid`/`Outline`) — at mobile widths its last tag clipped off-screen instead of wrapping. Fixed to match its siblings; confirmed live at 375px. Full self-verification after both fixes: `tsc`, `eslint`, `tsup` build, and both Vitest projects (`unit`: 644/644, `storybook`: 265/265) all clean. **Finalized 2026-08-22** — per that section's own note, don't make further changes to Tag (code, stories, docs, or its tokens) without asking first. **Per-variant CSS/token redesign, same day, at explicit direction (migrated here 2026-08-31 from `03-token-system-spec.md`, where it had landed without a proper home — token-adjacent but really component-CSS work, not a token decision):** a full pass across all three variants (`subtle`, `solid`, `outline`), one at a time, converting every variant to real `border`/`background`/`text`/`icon` properties with **no `box-shadow` anywhere** except where explicitly confirmed correct as-is. `subtle` gained a real decorative `border.{tone}-subtle` (previously none), its selected state moved from a shared `box-shadow` ring to a real `border-color` change (4.51–7.03:1 light / 7.45–10.68:1 dark, all clear the 3:1 floor with margin), and hover was fixed to apply while selected too (the original box-shadow-based exclusion no longer applied once selected used `border-color` instead). `solid` was reviewed and confirmed correct as-is (its offset-halo `box-shadow` stays, by design) — same hover-while-selected fix applied. `outline` got the same border conversion, plus its default-state icon decoupled from `text.{tone}` for the first time (own `icon.{tone}`, matching the `subtle`/solid-fill fixes already applied elsewhere — `guidelines/adr/0005`'s general fill/text-decoupling principle) and a genuinely new selected-hover state (previously nothing happened on hover at all). Across every variant, `icon.{tone}` decoupling from `text.{tone}` closes the same category violation already fixed elsewhere in the system (icons and text are independently-tracked token categories, deliberately not the same value via `currentColor` inheritance).

Two real, separately-found bugs in the removable "×" icon, both confirmed by direct measurement, not visual inspection: (1) the non-interactive path (rendered via `CloseButton` at the time) had its icon size double-remapped — `Tag`'s own correct size was being re-remapped a second time by `CloseButton`'s internal scale, producing a `×` visibly smaller than the leading/trailing icons (12px vs 20px at `xl`); fixed with a `CloseButton` `iconSize` override prop (since superseded — `Tag` no longer calls `CloseButton` at all, see `05-component-api-conventions.md` §10). (2) The *interactive* (selectable/clickable) removable path renders the `×` through a separate, undecorated `<span>`, not `CloseButton` — that span was missing `display: inline-flex; align-items: center`, producing a real, reproducible 1.7px vertical offset against the leading/trailing icons; fixed by adding the missing flex properties. Both paths verified matching pixel-for-pixel across all 5 sizes afterward. Full self-verification throughout this pass: `tsc`, `eslint`, the full unit/Storybook test suites, and live checks (computed styles, not just visual) across both brand themes/both modes for every variant/state combination — no re-opening of Tag's own Finalized status needed per `06-engineering-standards.md` §9's three-question test (design-quality refinement to already-compliant surface, not a defect fix, but scoped to this component's own files only).
