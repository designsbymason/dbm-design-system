# Textarea — Storybook/component review findings

*(Migrated from `07-storybook-and-documentation-standards.md` §6 during the guidelines retrofit pass, 2026-08-31 — this file's own content is unchanged from what was there, just relocated. See `07`'s own status table for this component's current Docs-page/Finalized status.)*

Textarea — ✅ done (2026-08-30 — comprehensive `06-engineering-standards.md` §9 review, worked one finding at a time across 14 findings, matching `Input`'s own process): full native `<textarea>` props audit (`readOnly`/`autoFocus`/`autoComplete`/`maxLength`/`minLength`/`name`/`form` redeclared with JSDoc), `aria-*` props redeclared, `className`/`style` both routed to the wrapper rather than the bare inner `<textarea>` (matching `Input`'s own wrapper/inner-element split, including the same "`style` silently fell through and had no visible effect" bug class), the JSX-attribute-ordering fix confirmed on `aria-invalid` (`05-component-api-conventions.md` §3), `showCount` added (a live current/max character count below the box, guarding on `maxLength` — `Input`'s own later `showCount` addition explicitly credits this component's implementation as its model), `onClear` added (a locally-implemented clear button in the top-inline-end corner, following `Tag`'s/`Input`'s own precedent rather than reusing `CloseButton`), and — the component's own signature feature-completeness addition — `autoResize` with optional `minRows`/`maxRows` bounds (matching MUI `TextField multiline`'s and Ant Design `TextArea`'s own bounded auto-grow), including dev-mode warnings for `minRows`/`maxRows` passed without `autoResize` and for an inverted `minRows > maxRows`. `Textarea.mdx` Docs page added from scratch as the final finding.

  **Horizontal-resize bug fixed (2026-08-30, direct user report with a screenshot — "the drag icon is moved, but the textarea does not resize"):** root cause was `resize` living on the borderless, backgroundless inner `<textarea>` rather than the bordered wrapper — dragging the handle genuinely widened the textarea's own box (confirmed via `getBoundingClientRect()`), but the wrapper, fixed at `width: 100%` and the only element with a visible border/background, never grew to match, so the resized textarea silently overflowed past the wrapper's own right edge instead of visibly resizing. Fixed by moving `resize` to the wrapper (`overflow: hidden` added, required for `resize` to take effect per spec) and making the inner `<textarea>` fill it at `width/height: 100%` with `resize: none` permanently, so there's a single resize handle on the one element a resize can actually make visible. A follow-up cosmetic request (~4px space between the resize icon and the border) was investigated, found genuinely infeasible — the native resize glyph paints in its own browser compositing layer, unpositionable/unmaskable via border, padding, or DOM-overlay tricks, confirmed via an isolated test page — and fully reverted at explicit direction after an initial claimed fix turned out to be based on a misread test.

  Two out-of-scope, separately-authorized fixes landed alongside this review, each scoped and flagged rather than expanding it: `Checkbox.test.tsx`'s real-form-submission test fixed a `tsc` failure (a `let` reassigned only inside a closure narrows to its initializer type at the outer read site — wrapped in an object to sidestep it; no behavior change) and `Input.mdx`'s own Accessibility section had the identical internal-guideline-path-reference violation just caught in this component's new `Textarea.mdx` (both copied from the same original text) — fixed in `Input.mdx` too, on explicit request, since it's finalized.
