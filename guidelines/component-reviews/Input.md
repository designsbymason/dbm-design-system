# Input — Storybook/component review findings

*(Migrated from `07-storybook-and-documentation-standards.md` §6 during the guidelines retrofit pass, 2026-08-31 — this file's own content is unchanged from what was there, just relocated. See `07`'s own status table for this component's current Docs-page/Finalized status.)*

Input — ✅ done (2026-08-29 — comprehensive `06-engineering-standards.md` §9 review, worked one finding at a time across 9 findings, then a substantial amount of follow-up work driven by direct live testing/user report before finalizing): (1) `Default` story renamed to `Playground`, every prop wired live via `args`/`argTypes`. (2) Confirmed 9th instance of the JSX-attribute-ordering bug (`05-component-api-conventions.md` §3) — `{...props}` now spreads before the computed `aria-invalid`. (3) Five stories' dead Controls panels fixed (`AllSizes`/`WithPrefixIcon`/`WithSuffix`/`Clearable`/`NarrowViewport` all used a bare `render` ignoring `args`). (4) Stray `parameters.chromatic` removed from `NarrowViewport` — Chromatic is a paid SaaS tool this project never adopted (`02-tech-stack-and-structure.md` picked Playwright's own self-hosted visual regression instead); found to be present on 12 other components too and cleaned up project-wide at explicit follow-up direction, including the already-finalized `Avatar` (separately confirmed). (5) `disabled`/`id`/`className`/`style`/`data-testid` redeclared with full JSDoc — while writing `style`'s own JSDoc, found and fixed a real inconsistency: `className` targeted the wrapper (the visible box, border/background live there) but `style` was un-destructured and fell through onto the bare native `<input>` (no visible border/background of its own), so `style={{ border: ... }}` silently had no visible effect — fixed to route `style` to the wrapper too, matching `className`. (6) `aria-label`/`aria-labelledby`/`aria-describedby` redeclared — `aria-invalid` deliberately excluded (it's computed from `hasError`, not consumer-settable, matching `Checkbox`'s/`Select`'s own precedent) — plus a follow-up Controls-panel audit (direct user report) that found and fixed several new escape-hatch/`aria-*` props showing inert "Set string" placeholders instead of a live control or "–". (7) `.wrapper:focus-within` given the standardized `sm` focus-ring `border-radius` (`05-component-api-conventions.md` §6), overriding its own `md` resting radius. (8) Two `play`-function interaction stories added (`TypingInteraction`, `ClearButtonInteraction`). (9) `Input.mdx` Docs page added from scratch.

  **Height parity with `Button` (2026-08-29, direct user report — "the Full width Button instance doesn't extend the full width of the container," which surfaced this as a *separate*, then-unnoticed issue on `Input`'s own Docs page while diagnosing it):** `Input` and `Button` share the same `size` scale and font-size tokens but rendered at visibly different heights per step. Root cause was two-fold: the native `<input>` doesn't inherit `line-height` from its own wrapper (`Input`'s own UA stylesheet gives it a non-inherited `normal`, confirmed live), and `Input`'s own border (`Button` has none) wasn't accounted for in its padding. Fixed by setting `line-height: var(--dbm-line-height-tight)` explicitly on both the wrapper and the input (`line-height: inherit`, forcing it through), and changing each `.sizeX`'s `padding-block` from a bare space token to `calc(<Button's own padding for that step> - border-width.1)` — composing tokens via `calc()` still traces every value to a token, not a raw number. Verified live: all 5 sizes now match `Button`'s own real rendered height to the sub-pixel (confirmed against actual computed `getBoundingClientRect()` values, not assumed from the CSS alone).

  **Clear button redesigned from `IconButton` to a dedicated local control (2026-08-29, direct user report — "the hit area is small" and "there is overlap in smaller input sizes"):** the original implementation reused the shared `IconButton` atom at a fixed `size="xs"`, but `IconButton`'s own size steps are self-contained boxes calibrated to match `Button`'s/`Input`'s own *full* outer height — even its smallest step (30px) was taller than this row's own text content at every `Input` size, so it always dominated the flex row and reinflated `.wrapper` past the just-fixed `Button`-matched height, and its box/icon never scaled with `Input`'s own `size` at all. A first fix (negative `margin-block` compensating for the icon's own fixed box) solved the height-overflow problem but not the hit-area complaint. Redesigned entirely, following `Tag`'s own established precedent for the identical problem (its 2026-08-25 review, dropping `CloseButton` for the same reason): a locally-implemented `<button>` + `<Icon>`, with the icon one size step down from `Input`'s own `size` (same principle as `Tag`'s `iconSizeForTagSize`) and real `padding` around it for a comfortable, independently-computed hit area, each keyed by `Input`'s own size (not the icon-size step, since `xs`/`sm` share an icon size but need their own font-size-driven envelope) with its own compensating negative margin so the padded box still doesn't inflate the row. Verified live at all 5 sizes: height parity with `Button` holds (sub-pixel exact at `xs`/`sm`/`md`, ~0.1–0.3px at fluid `lg`/`xl`, matching `Button`'s own documented viewport variance), and the padded, hoverable box sits fully inside `.wrapper`'s own padding with room to spare — confirmed via direct `getBoundingClientRect()` comparison, not assumed. Colors corrected in the same pass, per explicit spec: `icon.brand` at rest with no background (previously `IconButton`'s own `ghost` variant, a ` bg.brand-subtle` chip look), `bg.brand-subtle` on hover.

  **Full native-props audit (2026-08-29, following a direct exchange about which native `<input>` types/attributes this atom should support):** `required` added first (JSDoc + Controls-panel wiring), then a broader audit against `Checkbox`'s own already-redeclared set plus what's genuinely relevant to a text field found 12 more undocumented-but-functional native props — `type` (curated to the plain text-like types this atom is actually built for, with `password`/`number` noted as working but intended for the future `PasswordInput`/`NumberInput` molecules), `value`, `defaultValue`, `readOnly`, `autoFocus`, `autoComplete`, `maxLength`, `minLength`, `pattern`, `inputMode`, `name`, `form` — all redeclared with full JSDoc and given a genuine live control or `control: false` with a stated reason (never a bare inert placeholder). `appearance: none` added to `.input` in the same window (direct user report, following up on which native `type`s this atom supports) — `type="search"` combined with `onClear` could otherwise show a second, browser-drawn clear icon in WebKit alongside `Input`'s own, verified via the established revert-and-confirm-failure test discipline.

  **`guidelines/06-engineering-standards.md` §9 checklist extended, and all 14 then-finalized components' Docs pages retrofitted (2026-08-29, direct user question — "how would developers know they can pass native props?"):** found that no Docs page anywhere in the project stated a component also accepts native attributes beyond its own curated Properties table. Added a standing checklist requirement (one sentence, worded per component's own underlying element, directly above `<PropertiesTable>`) plus a requirement that Code examples include at least one genuine native-prop usage snippet — both retrofitted onto every then-finalized component's own `.mdx` (`Avatar`, `Badge`, `Box`, `Button`, `Checkbox`, `CloseButton`, `FieldError`, `FieldHelperText`, `FieldLabel`, `IconButton`, `ProgressBar`, `ProgressCircle`, `Skeleton`, `Spinner`, `Tag`), each with explicit go-ahead first per the finalized-component rule. Separately, sourcing `Input.mdx`'s own `RelatedCard` hrefs surfaced stale `--default` links on `Checkbox.mdx`/`FieldError.mdx`/`FieldHelperText.mdx` pointing at story names renamed to `Playground` during those components' own reviews; fixed all 5 occurrences after an exhaustive sweep confirmed no other stale links existed project-wide.

  **`showCount` added for parity with `Textarea`** (2026-08-29, a named feature-completeness gap flagged during the final review pass and built at explicit follow-up direction): a live `current/max` character count, only rendering when `maxLength` is also set — same guard and update logic as `Textarea`'s own `showCount` (a `useLayoutEffect` recalculating on externally-driven controlled-value changes, not just typing), but positioned inline after `suffix` rather than below the box, since this component is a single-line row rather than a multi-line block.   **Two real defects found and fixed (2026-09-14), during `SearchInput`'s own "consumed-atom defect handling" checkpoint (`06-engineering-standards.md` §9) — both stay Finalized (three-question test: genuine pre-existing defects, not preference changes).**

  1. **Clear button was never natively disabled when the input itself was `disabled` or `readOnly`.** Unlike every sibling same-row control (`NumberInput`'s stepper, `PasswordInput`'s toggle — both already guard `:hover:not(:disabled)` and style `:disabled`), `.clear` had no disabled handling at all: `disabled`/`readOnly` weren't even threaded to the button, so a "disabled" or "read-only" field's value could still be reset via a fully clickable clear button. Fixed: `Input.tsx` now destructures `readOnly` explicitly (previously flowed through `...props` untouched, unused for anything) and passes both `disabled={disabled}`/`readOnly={readOnly}` to the native `<input>` (previously only `disabled` was) and `disabled={disabled || readOnly}` to the clear `<button>`; `Input.module.css` gets `.clear:hover:not(:disabled)` (was unconditional `:hover`) and a new `.clear:disabled { cursor: not-allowed; }`, matching the sibling pattern exactly. Two new regression tests added to `Input.test.tsx`. `PasswordInput`/`NumberInput` inherit the fix automatically — both render this exact same `<button>` internally via their own `onClear` pass-through, no changes needed in either file.
  2. **`type="search"` still showed WebKit/Blink's own native "×" cancel-button icon, undetected because every existing consumer's own clear/toggle control sits in the same trailing position and visually masked it.** `appearance: none` on `.input` (already present, added for this exact stated reason) resets the *input box's* own native searchfield chrome but never reached the `::-webkit-search-cancel-button` pseudo-element specifically — confirmed via a direct screenshot in a live Chromium build (`SearchInput`, the first consumer with a demo showing `type="search"` and no clear control of its own, is what exposed it). Fixed with the standard `::-webkit-search-decoration`/`::-webkit-search-cancel-button`/`::-webkit-search-results-button`/`::-webkit-search-results-decoration` reset, scoped to `.input`. **No automated regression test** — `getComputedStyle` against these pseudo-elements proved unreliable (kept reporting `display: block` even once the fix was confirmed visually working via screenshot), and Playwright's own bundled Chromium doesn't render this native decoration at all regardless of the fix being present (verified directly: a deliberately-broken build of the fix still passed a `toHaveScreenshot` check) — added, then removed, rather than keep a test that would pass unconditionally either way. See `Input.module.css`'s own comment on the fix for the full empirical trail.

  **Authorized post-finalization change (2026-09-14): prefix/suffix icon color moved to `icon.default`.** Follow-up to the clear-button recoloring above, formalized into a standing rule the same day (`05-component-api-conventions.md` §6 — "icons used inside an input field use neutral colors"). `.affix` (the shared wrapper for both `prefix` and `suffix` content) had its own `color` changed from `var(--dbm-text-tertiary)` to `var(--dbm-icon-default)` — the two tokens share an identical resolved value in every theme (`03-token-system-spec.md`), so this is a semantic correction, not a visual one: a plain decorative icon passed as `prefix`/`suffix` (inheriting this color via `currentColor`) now reaches the correct `icon.*` token family, matching the same principle already documented for `Image`'s fallback icon. No hover background added — a plain prefix/suffix icon isn't itself interactive. **Three-question finalization test:** (1) changes rendered output — no, zero visual difference (identical resolved color in all 4 themes); (2) a semantic/correctness fix, not a preference change; (3) blast radius scoped to `.affix` alone. **Result: stays Finalized, no new re-verification needed** even under the stricter reading — confirmed anyway via live Storybook check (`With prefix icon` story, prefix icon renders identically to before) and zero Accessibility-panel violations.
