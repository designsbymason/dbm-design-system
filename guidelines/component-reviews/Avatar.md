# Avatar — Storybook/component review findings

*(Migrated from `07-storybook-and-documentation-standards.md` §6 during the guidelines retrofit pass, 2026-08-31 — this file's own content is unchanged from what was there, just relocated. See `07`'s own status table for this component's current Docs-page/Finalized status.)*

**Data Display:** Avatar — ✅ done (2026-08-12–2026-08-16, out of sequence — pulled ahead of Phase A's own remaining items and the rest of this queue at explicit direction, and went considerably deeper than the standard Docs-page pass). Built: `name`/`colorful` (deterministic per-identity color, 5 AA-verified families plus their own hover step — see `bg.brand-subtle`/`bg.brand-subtle-hover` in `03-token-system-spec.md`'s Contrast verification section), responsive `size` (the first component-tier prop to use `Responsive<T>` outside the original layout-primitive set), polymorphic `as` (interactive-trigger support — the `as`-vs-`asChild` pattern this established is documented in `05-component-api-conventions.md` §3; the decision not to adopt `@radix-ui/react-avatar` for the underlying image-load state machine is `guidelines/adr/0001`), `disabled`/hover/focus states for that interactive mode, and the component-token layer's first-ever population (`component/avatar.json` — `03-token-system-spec.md`). Also produced two durable cross-component outputs: the focus-ring border-radius convention (`05-component-api-conventions.md` §6) and two Storybook/MDX bugs fixed at the shared-tooling level (Properties table Name-column wrapping, MDX's lack of backslash-quote-escaping support — see `07-storybook-and-documentation-standards.md` §4.1). **A second pass (2026-08-16)** made `as` a real interactive Storybook control and, in doing so, caught two truthiness bugs the raw prop check had (`isInteractive`/`canUseImgRole` used `as`'s own truthiness instead of the resolved element, breaking on an explicit `as="span"`); added a decorative `border.brand-subtle` ring plus family-matched `colorful` borders and the matching state-family `border.{warning,success,info}` tokens (see `03-token-system-spec.md`'s `border.*-subtle` rows for all of these); and a full story-controls audit surfaced a whole failure class this project hadn't checked for before — a `render` that doesn't accept `args` makes every Storybook control a silent no-op — now a standing checklist item (`06-engineering-standards.md` §9) with its own CI-enforced Foundations-token-coverage check (`07-storybook-and-documentation-standards.md` §10). **Finalized 2026-08-16** — a full review pass (`06-engineering-standards.md` §9's checklist) confirmed clean; per that section's own note, don't make further changes to Avatar (code, stories, docs, or its tokens) without asking first. **Raw Controls-panel order fixed, 2026-08-24 (same fix pattern as Button/Checkbox — see `07-storybook-and-documentation-standards.md` §4.1's shared root-cause note; this was the gap flagged, then fixed at explicit direction, while diagnosing Button's own version of it):** `onClick` rendered at the very end of the raw per-story Controls panel instead of right after `disabled` (its `propOrder` position) — purely inherited via the polymorphic `& Omit<ComponentPropsWithoutRef<E>, "as" | "children">` intersection, never redeclared on `AvatarProps` itself. Fixed by redeclaring `onClick?: (event: MouseEvent<HTMLElement>) => void` directly on `AvatarProps`, typed generically against `HTMLElement` rather than the polymorphic `E` (matching the same widened type `Avatar.tsx`'s own internal `onClickProp` cast already uses, so this doesn't introduce a second, competing type) and Omitting `"onClick"` from the intersected native props first, same pattern as `Checkbox`'s `checked`/`defaultChecked`/`onChange`. Checked for the control-inference regression found on Button's own `onClick` fix (`07-storybook-and-documentation-standards.md` §4.1) — not an issue here, since `Avatar.stories.tsx`'s `onClick` argType already had `control: false` set from Avatar's original review. `Avatar.tsx` itself untouched — zero behavioral/DOM/token change, so per `06-engineering-standards.md` §9's three-question test this **stays finalized**. Full self-verification: `tsc`, `eslint`, `tsup` build, unit tests (715/715, including existing `onClick`-fires/blocked-when-disabled coverage — confirming runtime behavior, not just types) all clean; live-reconfirmed (after a required dev-server restart) the raw Controls panel and Docs page Properties table both now read `as, src, alt, onError, loading, initials, name, colorful, size, shape, status, disabled, onClick, aria-label, id, className, style, data-testid` — an exact match to `propOrder`. **Actions-panel gap fixed, 2026-08-24 (found live by direct user report — clicking the Playground's `as="button"` avatar logged nothing in Actions — same day as the ordering fix above, pre-existing since Avatar's original 2026-08-16 review, unrelated to it):** `Avatar.stories.tsx`'s meta-level `args` wired `onError: fn()` but never `onClick: fn()`, so no spy existed for the Actions panel to log regardless of story or click target. Fixed by adding `onClick: fn()` alongside `onError: fn()`. Zero component change — `Avatar.tsx` untouched, stays finalized. Live-verified: switched the Playground's `as` control to `"button"`, clicked the real rendered `<button>`, Actions panel went from no count to `Actions 1` showing the logged click event object; re-confirmed the `AsButtonDisabled` story's click still logs nothing (disabled correctly still blocks it, no regression). Full self-verification: `eslint`, both Vitest projects (`unit`: 715/715, `storybook`: 274/274), `tsup` build all clean. **Real accessibility defect found and fixed, 2026-08-24 (found live by direct user report while testing the just-fixed Actions-panel wiring above — clicking the *default, non-interactive* avatar also logged a click, which shouldn't have been possible at all):** `Avatar.tsx` wired `onClick={isInteractive ? handleClick : onClickProp}` — the non-interactive branch still attached the raw handler directly to the default `<span>` regardless of `isInteractive`, so a consumer-provided `onClick` fired on mouse click even though the element carried `role="img"` and no `tabIndex`/keyboard handling — a real WCAG 2.1.1 (Keyboard) violation (clickable by mouse, no keyboard equivalent, and actively mislabeled as a static image to assistive tech), inconsistent with `disabled`'s own already-documented "no effect on the default span" gate on this exact component, and never covered by any existing test (every prior `onClick` test used `as="button"`) or the Docs page (whose own code example already always paired `onClick` with `as="button"`, just never enforced it). Per `06-engineering-standards.md` §9's three-question test: **this is a genuine pre-existing defect, not a preference change** (the original 2026-08-16 finalization pass's own Accessibility/keyboard-navigation checklist item would have failed here had it caught this specific scenario), so it **stays finalized** despite changing existing behavior. Fixed by changing the wiring to `isInteractive ? handleClick : undefined` (`onClick` now genuinely does nothing on the default span, matching `disabled`'s own gate exactly) and adding a matching dev-mode warning (`hasWarnedIgnoredOnClickRef`, same pattern as the two existing `src`/name warnings) so a consumer who passes `onClick` without an interactive `as` is told why it's a no-op rather than silently losing it. `onClick`'s own JSDoc (added earlier the same day) corrected to describe this accurately instead of the aspirational wording it had before the code actually matched it; `Avatar.mdx`'s Accessibility section and `Avatar.stories.tsx`'s `onClick` argType description updated to match. Three new tests added: `onClick` doesn't fire on the default span even when provided, the new dev-mode warning fires once, and it doesn't fire when `as="button"` makes the avatar genuinely interactive. Full self-verification: `tsc`, `eslint`, `tsup` build, both Vitest projects (`unit`: 718/718, `storybook`: 274/274) all clean; live-reconfirmed — default span click no longer appears in Actions at all, `as="button"` still logs `Actions 1` correctly, the new console warning fires in a real running Storybook instance (not just the test suite), and the Docs page renders the updated Accessibility text.
