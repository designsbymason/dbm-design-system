# DBM Design System — Storybook & Documentation Standards

**Status: v1 draft.** Companion to `05-component-api-conventions.md` (the API contract) and `06-engineering-standards.md` §9 (the atom review rubric) — this doc covers a third, Storybook-specific dimension: how a component's *documentation and interactive showcase* meet the same "premium, comprehensive, agent-legible" bar the component code itself must meet. Established 2026-07-26, at the start of the post-Phase-4.75 Storybook refinement pass, so the plan and processing order survive a context reset.

---

## 1. Why this pass exists

Phase 4.5 and 4.75 verified every atom's code (props, tokens, a11y, responsiveness, stability) and shipped a Storybook story file per component. But a spot-check of `Button.stories.tsx` — one of the most mature stories in the library — surfaced real gaps common to *every* component, not just a few:

- No documentation/autodocs infrastructure exists at all — only `@storybook/addon-a11y` is installed. No `@storybook/addon-docs`, no `tags: ["autodocs"]`, no MDX. There is currently no "Docs" page for any component.
- Controls are inconsistently interactive. Enum props (`variant`, `size`) often have proper `select` controls, but component-reference props (`icon`) have no `argTypes` entry at all (Storybook renders a useless control for these unless explicitly disabled with `control: false`). Showcase stories like `AllVariants`/`AllSizes` use `render: () => (...)` with hardcoded values — they don't respond to the Controls panel at all.
- No Playground story exists anywhere — nowhere can a user drive every prop of a component live, in one place.
- The Storybook sidebar taxonomy has quietly diverged from `04-component-inventory.md`'s 9 functional categories — an inherited-from-Phase-3 "Atoms/Core" catch-all mixes components that the inventory actually splits across Inputs and Data Display.

None of this is a per-component bug; it's a systemic gap in what "done" meant for Storybook when Phases 3/4.5/4.75 shipped. This pass closes it, one component at a time, applying a consistent standard.

## 2. Storybook infrastructure additions (one-time, done before any component work)

Approved 2026-07-26:

- **`@storybook/addon-docs`** — enables the "Docs" tab / autodocs page per component. Required for §4 below.
- **`@storybook/addon-viewport`** — replaces the ad-hoc one-off "NarrowViewport" stories several components have with a proper, systematic responsive-testing toolbar control.
- **Interaction/play-function testing** — Storybook's `play` function support (via whatever the current Storybook 10 package/import path is for `expect`/`userEvent`/`within` — verify the exact package name at install time, since Storybook 8+ consolidated a lot of this into the core `storybook` package's subpath exports rather than separate npm packages) — in scope for this pass, not deferred. Every interactive component gets at least one `play`-function story scripting its core interaction (click, keyboard nav, focus) so behavior is verified visually in Storybook, not only in Vitest.

All are first-party Storybook packages (same tool already approved in `02-tech-stack-and-structure.md`), registered in `.storybook/main.ts`'s `addons` array alongside the existing `@storybook/addon-a11y`.

## 4. The Docs page template

One hand-authored `ComponentName.mdx` file per component (via `@storybook/addon-docs`), set as the **first entry** in that component's Storybook group (before Playground and every other story). Auto-generated docs (`tags: ["autodocs"]` alone) can't produce the prose sections below, so every component gets a real MDX file that embeds live `<Canvas>`/`<PlaygroundControls>` blocks from the Playground story where useful, interleaved with hand-written content. Sections, in order:

1. **Intro** (added 2026-07-27, revised same day; renamed from "Overview" 2026-08-08 — "Overview" collided in meaning with the `Foundations/Overview` *page*, and "Intro" reads more accurately as "the top of this page" for both component and Foundations docs once §7 adopted the same pattern) — title + tier badge via `<ComponentHeader>`, then the one-paragraph description, with **Import as a nested `### Import` subsection right underneath it** (not its own top-level section — folded in since it's a single code block, not substantial enough to earn its own tab). The section needs a heading for the TOC (§4.1) to produce an "Intro" entry at all, but an actual visible `## Intro` label reads as redundant directly under the big `<ComponentHeader>` title — resolved by keeping a real `## Intro` heading in the DOM but visually hiding it via `<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>` (the same real, tested atom used for icon-only labels elsewhere), placed *before* `<ComponentHeader>` so the TOC's "Intro" entry scrolls all the way to the top of the page, title included. tocbot (the TOC's underlying library) reads heading text directly from the DOM regardless of visibility, so this costs nothing functionally.
2. **Interactive Playground** — the Playground story's live canvas, then **below it** a single-card, controls-only panel laid out in **2 columns** of label+control pairs (not a full Description/Default table, and not beside the canvas — see §4.1's `PlaygroundControls` entry). **Exclude any prop whose control isn't actually editable** (i.e. anything with `control: false`, explicit or inferred — `onClick` and other function props, `asChild`, `id`, `className`, `data-testid`, etc.) via `<PlaygroundControls exclude={[...]}>` — these still show up in the Properties table below with a full description, but a row reading just "–" in the Playground is dead space with nothing for the reader to actually do, per the whole point of a *Playground* being interactive. `exclude` needs to be listed explicitly (a plain `string[]`, no predicate-function support) and kept in sync by hand with whichever props end up with `control: false` — there's no automatic way to detect this from the story file's own unresolved `argTypes` object, since some props (bare function args like `onClick`) only get `control: false` via Storybook's own implicit inference, not anything explicitly written in the story.
3. **Properties table** — prop name, **value options**, description, default, required/optional — via the custom `<PropertiesTable>` block (§4.1), not the stock `<ArgTypes>` doc block, which has no "value options" column. Sourced from the component's TypeScript types + JSDoc (the same JSDoc that feeds the future manifest generator — this is a second, immediate payoff for keeping it complete). **Every prop needs a real, non-empty description — no exceptions, including "obvious" native props** (`children`, `onClick`, `disabled`, `style`, etc.) — confirmed on `Button`/`Box`: several purely-native props docgen extracts with an empty `description` rather than dropping the row, which reads as broken/incomplete now that the table makes blanks visible via an em dash. Fix via an explicit `description` in the story file's `argTypes` (§4.1's `<PropertiesTable>` entry has more on why this is the reliable mechanism), not by hoping JSDoc alone gets picked up. **Row order must read sensibly** — content prop first, then core visual props (`variant`/`size`), then behavioral/state props, then advanced/escape-hatch props (`asChild`, `className`, `id`, `data-testid`) last — passed explicitly via `<PropertiesTable>`'s `order` prop, not left to whatever order docgen happens to produce (confirmed unpredictable — see §4.1). Check this deliberately for every component, don't assume the default order is already sensible. **One sentence, directly above `<PropertiesTable>`, stating that the component also accepts any other native `<element>` attribute beyond what's listed (established 2026-08-29, via `Input`)** — every component that `extends ComponentPropsWithoutRef<'element'>` (§5's own architectural rule) passes through dozens of native attributes the curated table will never enumerate (`onFocus`, `onKeyDown`, `spellCheck`, etc.), and nothing on the rendered Docs page said so until this was added — a real, confirmed gap (checked every existing Docs page at the time: none had it). Word it for the component's own actual native element (e.g. "`Badge` also accepts any other native `<span>` attribute beyond what's listed here (e.g. `onClick`, `title`) — passed straight through to the underlying element."); for a polymorphic component (`Avatar`/`Box`, rendering whichever element `as` picks), phrase it around `as` instead of one fixed element name.
4. **Variants / states gallery** — a static visual reference of every variant × size × state combination (distinct from the interactive Playground — an at-a-glance comparison). **Every story in this section gets its own `###` subheading** (the story's display name) directly above its `<Canvas>` — bare, unlabeled Canvas blocks in sequence give the reader no way to tell what they're looking at without reading source, and unlabeled subheadings also mean the TOC can't show them either.
5. **Usage guidelines** — Do's and Don'ts, concrete not generic ("Do use `destructive` for irreversible actions" not "use variants appropriately").
6. **Best practices** — the judgment-level guidance a senior designer/engineer would give a newcomer using this component.
7. **Accessibility** — keyboard interaction table, ARIA attributes the component sets and why, screen reader behavior notes, any contrast pairings worth calling out.
8. **Code examples** — copyable snippets for the common real-world usage patterns, beyond what the props table alone conveys.
9. **Design tokens used** — which semantic tokens this component consumes (a DBM-specific addition beyond generic DS docs — doubles as a visible, honest confirmation of "no hardcoded values" for anyone auditing the component).
10. **Related components** — cross-links (e.g. `Input` ↔ `Textarea`, `FieldLabel`, future `FormField`).

**Editorial bar (confirmed on `Box`, 2026-07-26):** the Docs page is a reference source a complete newcomer to DBM — human or agent — should be able to read and fully understand, not just a props reference for people who already know the system. Concretely: **define any technical/jargon term the first time it's used**, not just deployed as if the reader already knows it (caught in practice: "polymorphic" appeared in `Box.mdx`'s opening sentence with no definition, even though the whole rest of the paragraph explained the *mechanism* — fixed by defining the term inline on first use). When a concept is foundational to the whole system rather than one component (e.g. the polymorphic-`as` pattern, used by `Box`, `Stack`, `Text`, `Heading`, `Center`, and others), define it thoroughly once in whichever component is most foundational to it — `Box` for polymorphism — and have every other component's docs cross-link to that explanation via Related Components instead of re-explaining it each time.

**Never reference an internal `guidelines/*.md` path in visible page content** (component Docs pages or Foundations pages alike) — those documents are internal-only working notes for building this library, not something a consumer of the published package or hosted Storybook should see cited as a source. Caught on the Foundations Color page (2026-07-27): its Contrast verification section cited `guidelines/03-token-system-spec.md` by path directly in reader-facing prose — removed, since the underlying claim ("checked against real WCAG ratios") stands on its own without pointing at an internal doc the reader can't access. This is distinct from source-code comments (`.storybook/**/*.ts(x)`, `.css`) citing a guideline for a future maintainer's benefit — those are fine, since they aren't rendered to a Storybook visitor.

### 4.1 Visual presentation layer (confirmed on `Box`/`Button`, 2026-07-26)

Beyond content and structure, the Docs page has a dedicated visual-polish layer — a custom Storybook theme, global CSS, and a small set of reusable MDX-only components — so every component's Docs page reads as a premium, cohesive reference rather than Storybook's default unstyled autodocs output. None of this ships in the published `@dbm-design-system/components` package; it lives entirely under `packages/components/.storybook/` and is wired in via `preview.tsx`'s `docs` parameter.

**Shared infrastructure (one-time, applies to every component automatically):**
- **`.storybook/theme.ts`** — two `create()`-based Storybook themes (light/dark, mirroring the same semantic step selections as the design system's own `--dbm-*` tokens), applied reactively: `.storybook/manager.ts` listens for the Mode toolbar global via the addons channel and re-calls `addons.setConfig({ theme })` on change; `.storybook/DbmDocsContainer.tsx` (wired via `parameters.docs.container`) does the same for the Docs addon's own wrapper/typography. Manager chrome and the Docs wrapper now track the same Brand/Mode toggle that themes previewed components, rather than staying fixed light.
- **`.storybook/docs.css`** — global typography/table/Canvas styling scoped to Storybook's real, DOM-confirmed class names (`.sbdocs-content`, `.sbdocs-preview`, `.docblock-argstable*`) — do not guess class names; verify them in the rendered DOM first, since Storybook styles most elements via hashed CSS-in-JS classes with no stable selector.
- **`parameters.docs.toc: { headingSelector: "h2" }`** (in `preview.tsx`) — enables the built-in sticky table of contents automatically for every Docs page; no per-component setup needed. **Restricted to `h2` only** (the library default is `h2, h3`) so the TOC reflects just the template's fixed section list (§4's 10 items — note "Import" isn't one of them; it's nested under Intro as an `h3` and deliberately has no TOC entry of its own) — identical across every component — rather than also indexing each component's own `h3` variant subheadings (item 4), which differ per component and would turn the TOC into a per-component variant list instead of a consistent, reusable page nav. This is what makes "the same tab labels on every Docs page" actually true, rather than aspirational — verify it by comparing two different components' rendered TOCs side by side, not just one.
- **`minHeight` in the shared `withTheme` decorator is conditional on `context.viewMode === "docs"`** (undefined there, `100vh` in standalone story view) — without this, every Canvas block embedded in a Docs page gets a huge empty-space bug below the actual component.
- **`.sbdocs-content h2`'s `margin-block` needs `!important` on the top value** (found 2026-07-27, auditing section-spacing consistency): Storybook's own MDX stylesheet has a `:first-of-type` rule (`margin-top: 0`) that's genuinely *more specific* than `.sbdocs-content h2` (not a tie, unlike the code-pill case below), so it silently won margin-top for whichever `##` section happened to be first in a page's DOM — collapsing that one section's gap to ~16px instead of the intended 40px used everywhere else. Invisible on every `ComponentName.mdx`, since the actual first h2 there is the visually-hidden "Intro" heading (§4 item 1) absorbing the zeroed margin harmlessly — and, since 2026-08-08, every Foundations page has the equivalent hidden heading too (§7.2), so this is no longer a Foundations-specific gap either. Confirmed via computed `margin-top` (`0px` vs `40px`) across multiple Foundations pages before fixing, and re-measured all 10 Foundations pages plus Button/Box afterward (every section gap exactly 40px) rather than assumed from one instance.

**Per-component MDX building blocks (import from `.storybook/blocks`, use in every `ComponentName.mdx`):**
- **`<ComponentHeader title="X" tier="Atom|Molecule|Organism|Template" />`** — replaces the plain `<Title />` doc block. Renders the component name plus a tier badge (using DBM's own `Badge` atom) so a reader immediately knows where the component sits in the atomic hierarchy. Use in place of `<Title />` at the top of every Docs page. **Mobile-width bug fixed 2026-08-22 (found during `ProgressBar`'s Docs page, live mobile-viewport check):** the title+badge flex row had no `flexWrap`, so at narrow widths the badge was pushed fully off-screen instead of wrapping beneath the title — invisible on every prior component, since none had a name long enough to trigger it (`ProgressBar`, 11 characters, was the first; `Skeleton`, 8 characters, the next-longest, still fits on one line at 375px). Fixed with `flexWrap: "wrap"` on the container; confirmed live at mobile width with zero visual change on `Tag`/`Skeleton`'s own pages (they never had room to overflow in the first place).
- **`<Callout tone="success|danger|info" title="...">...markdown children...</Callout>`** — styled callout box (icon + tinted background) replacing plain markdown for: the Do/Don't pair under Usage guidelines (`success/danger`, laid out as a 2-column grid — see Box/Button for the exact grid wrapper), and the Accessibility section (`info`, wrapping the whole section body, with a specific descriptive title rather than the generic word "Accessibility" — e.g. Box's "No built-in semantics — as is what makes this accessible").
- **`<TokenRow token="bg.brand" usage="..." />`** — replaces the old plain markdown token table. One row per token. Color-category tokens (`bg.*`/`text.*`/`border.*`/`icon.*`) render a live swatch resolved from the actual CSS custom property, so it reflects the current theme; non-color tokens (`space.*`, `radius.*`, `font-*`, `motion.*`, `opacity.*`) render with no swatch since a colored square wouldn't mean anything for them. Split any compound "token A / token B" table row from the old format into one `<TokenRow>` per distinct token — each color token should get its own swatch. Non-color token *ranges* (e.g. `space.1`–`space.6` for a per-size scale) may stay combined in one row, since there's no swatch to lose by doing so.
- **`<RelatedCard name="..." description="..." href="...">...live mini-preview...</RelatedCard>`** — replaces the old plain markdown related-components link list. Each card is a small live rendering of the related component (real components, not screenshots) plus its name/description, laid out in a `repeat(3, 1fr)` grid (see Box/Button for the exact grid wrapper). The mini-preview should be small and representative (a few colored squares for a layout primitive, one real instance for an interactive atom) — not a full demo.
  **The preview slot must never render its own top-level `<a>`/`<button>` unwrapped by something else (fixed 2026-08-17, via Button→Link):** the card's navigation link only wraps the name/description text, not the preview slot — confirmed live as a React hydration warning ("`<a>` cannot be a descendant of `<a>`") when Button.mdx's "Link" card previewed a real `<Link>`, whose own rendered `<a>` landed inside the card's then-single outer `<a>`. The same invalid-nesting problem applies to any interactive preview, not just anchors — nesting a real `<button>` (`IconButton`, `CloseButton`, a removable `Tag`) inside an `<a>` is equally invalid HTML, it just doesn't throw a hydration warning the way anchor-in-anchor does. Don't re-wrap the whole card (preview included) in one clickable element to "simplify" the click target — the preview slot must stay a plain, non-interactive container so any live component's own interactive elements render validly.
  **The preview slot's height must be fixed, not just floored (found 2026-09-05, via Tooltip, user-reported with a screenshot):** it originally used `minHeight: space.12` (48px) — a floor, not a ceiling — so a preview taller than that (a `Button`, measured live at ~68px even at its own established `size="sm"` convention for these cards, vs. the ~48px most other previews render at) grew the slot to fit, leaving the name/description directly below it starting at a visibly different Y position from an adjacent card in the same grid row. Changed to a fixed `height: space.20` (80px, `overflow: hidden` as a safety net) — chosen by measuring real `RelatedCard` previews live across several existing Docs pages first (Badge/Backdrop/Collapse/Textarea/ProgressCircle/Image/Button all sit at the 48px floor; `Button size="sm"` at ~68px was the tallest real instance found) rather than guessing a value, so it's the first scale step that comfortably fits the tallest known real case with room to spare. A fixed height was deliberately chosen over dynamically matching "the tallest card in this specific row" (CSS Grid's own default row-stretch already equalizes each card's *outer* height across a row, but not this *inner* slot without further work) — a single sitewide constant keeps every card's preview height consistent not just within one row but across every Docs page and every possible row composition, which a per-row-only match wouldn't guarantee once a page has enough related cards to wrap onto a second row of different composition.
  **A RelatedCard preview's plain-text children must be written on one line, not split across lines inside the JSX tag (found 2026-09-05, via Tooltip, user-reported with a screenshot — a second, distinct bug from the fixed-height one just above, caught while fixing it):** `<Button variant="secondary" size="sm">\n  Hover me\n</Button>`-style formatting (opening tag, bare text on its own line, closing tag) gets its text child auto-wrapped in a `<p>` by the MDX compiler — confirmed live by inspecting the actual rendered DOM (`<p>Hover me</p>` instead of a plain text node) — while the exact same component written on one line (`<Button ...>Hover me</Button>`) renders the plain text directly, no `<p>`, confirmed by checking an already-correct instance (`Icon.mdx`'s own "Pay" button). The inserted `<p>` carries the browser's own default `1em` top/bottom margin, which nothing in this system's CSS resets (nor should it need to, for a tag no live component is expected to ever receive as a child) — on `Button`, this added ~27px of invisible margin *inside* an inline-flex, single-line, `white-space: nowrap` element, nearly doubling its rendered height (a `size="sm"` `Button` measured at 68px instead of its real ~41px) with no visual indication anything was wrong beyond the resulting misalignment. Found via a **systematic sweep of every `RelatedCard` block in every Docs page** (a small Python script flagging any bare-text line sandwiched between JSX tag lines) after the first instance surfaced, rather than assuming it was a one-off — three more turned up (`Collapse.mdx`, `Affix.mdx`, `BackToTop.mdx`), all fixed by collapsing the children back onto one line. **Keep every future `RelatedCard` preview's plain-text children on the same line as its tag** — multi-line JSX formatting is fine for props, just not for bare text content.
  **The preview slot must be `inert`, not just a plain non-`<a>` container (found 2026-09-07, via Link, user-reported):** a preview can itself render a real interactive element with a real destination — `Link.mdx`'s own "Text" card renders `<Link href="/docs">`, its "Button" card renders `<Button asChild><a href="/next">` — and clicking straight into it (not the card) navigated the whole Docs page to that route, bypassing the card's own name/description link entirely (a blank/404 page, since the route doesn't exist in Storybook's static build). This is distinct from the earlier "no top-level `<a>`/`<button>`" fix above, which was about HTML validity (nested anchors), not about the rendered content being independently clickable — `Link` is simply the first component whose preview happens to render something with a real working destination for a plain click to trigger; most earlier previews (`Badge`, a non-removable `Tag`, `Code`) have no default action a click would even do anything with. Fixed by adding the `inert` HTML attribute to the preview slot itself (`RelatedCard.tsx`) — blocks both pointer clicks *and* keyboard Tab-then-Enter activation, confirmed live with a **real simulated mouse click, not `element.click()`** (verified directly that `.click()` bypasses `inert` entirely, since it isn't a real hit-tested user event — a `pointer-events: none`-only fix would also have missed the keyboard-activation case). The card's own name/description link is unaffected and still navigates normally. Applies to every `RelatedCard` on every Docs page automatically (shared block); spot-checked against `Tag.mdx`'s own two interactive previews (`Badge`, `Button`) to confirm no regression — both correctly inert, full opacity, no visual side effect.
- **`<PropertiesTable of={ComponentStories} order={[...]} />`** (added 2026-07-27) — replaces `<ArgTypes of={ComponentStories} />` for the "Properties" section. A fully custom table (`.storybook/blocks/PropertiesTable.tsx`), not a themed version of Storybook's own — **the stock `<ArgTypes>` doc block has no supported way to add a custom column**, confirmed by reading its actual prop type (`ArgTypesProps` only accepts `of`/`include`/`exclude`/`sort`); adding "Value options" required resolving the raw argTypes data ourselves via the officially-exported `useOf(of, ["meta"])` hook and rendering our own `<table>`. Columns: Name, **Value options** (the literal set of values a prop accepts — enum members as `<code>` pills, `true`/`false` for booleans, an em dash for freeform/function props — computed from `argType.options` and `argType.type.name`, not shown anywhere in the stock table), Description, Default. The `order` prop is a plain string array forcing display order explicitly (see the row-order requirement in §4 item 3) — every prop should be listed, in the sequence the checklist calls for. Alternating row background is the primitive `--dbm-color-purple-200`, not a gray. **Revised 2026-07-27:** originally used the semantic `bg.brand-subtle` (purple-100), which is technically on-brand but reads as plain gray at that lightness once spread across a whole stripe — purple-200 is the first step that's actually recognizable as a light primary tint on screen. This is a deliberate, documented exception to "semantic tokens only" (`CLAUDE.md`) — there's no semantic step between `bg.brand-subtle` and the much stronger `bg.brand-hover`, and this is presentational Storybook docs chrome, not shipped component code.
  **Name column wrapping (fixed 2026-08-15, via Avatar):** `.dbm-proptable`'s `table-layout: auto` sizes columns from content, so a long Description column squeezed the Name column until longer `<code>` prop names (e.g. `aria-labelledby`) wrapped onto a second line. `white-space: nowrap` on `.dbm-proptable td:first-child` alone did *not* fix it — `.sbdocs-content code`'s own base rule sets `white-space: normal` directly on the `<code>` element itself, at higher specificity than a `td`-level rule can reach. Fixed by adding `white-space: nowrap` (plus `overflow-wrap: normal`) directly to `.dbm-proptable code`'s own `!important` block instead — confirmed live (computed `white-space` was still `normal` on the code element after the `td`-only fix, despite the `td` itself correctly showing `nowrap`).
- **`<PlaygroundControls of={PlaygroundStory} exclude={[...]} order={[...]} />`** (`.storybook/blocks/PlaygroundControls.tsx`, added 2026-08-09 — **replaces the original Storybook-`<Controls>`-based Playground panel described in earlier drafts of this section**, not a themed wrapper around it). Same `of`/`exclude`/`order` API as `<PropertiesTable>` for a consistent call site, but resolves the target story's own live args (`usePlaygroundArgs`, backed by the Docs addon's `DocsContext`) and renders each row itself, using this design system's own form atoms (`FieldLabel` + a dispatched `Switch`/`Select`/`Input` per `argType.control.type`) rather than Storybook's Controls widgets — real, controlled, two-way-bound inputs, not a re-skin. Includes its own "Reset to defaults" control, wired to `resetArgs()` — a `Button` (`variant="tertiary"`, `size="xs"`) sitting outside/below the card, left-aligned (moved 2026-09-06, at explicit direction, from a top-right icon-only `IconButton` inside the card — mirrors how the Canvas block's own native "Show code"/"Copy code" controls sit below *its* box rather than inside it; the visible label also means a `Tooltip` restating the same text is no longer needed), styled to match those same native buttons' real computed style (color/size/spacing/border-radius/hover — see `PlaygroundControls.tsx`'s own doc comment for the full value-by-value readout and the two real CSS bugs found getting there, both only catchable by live browser verification, not by reading the code):
  - **An inline `style` override can't express `:hover` at all** — the component's own first pass set `color` via `style`, which (correctly, per CSS spec) meant a stylesheet `:hover` rule could never win regardless of specificity, since an inline style's specificity always beats an external rule. Fixed by moving every overridden property to a real class (`.dbm-playground-reset-button`, `docs.css`) instead.
  - **An `!important` rest-state rule needs an `!important` hover rule too, not just higher specificity** — `!important` declarations form their own priority tier above all normal-priority declarations, so a `:hover` rule without `!important` can never beat a plain rest-state rule that has it, no matter how much more specific the `:hover` selector is. Found live via the real, previously-shipped bug this exact block hit: `.dbm-playground-reset-button:hover { color: ... }` (no `!important`) silently lost to `.dbm-playground-reset-button { color: ... !important }` even while genuinely hovered — confirmed via `document.querySelectorAll(':hover')`, not by reading the CSS and assuming cascade order. Fixed by adding `!important` to the hover rule too.
  - The icon is composed into `children` rather than passed as `Button`'s own `leadingIcon` prop, and given no explicit `tone` — `Button` always colors a `leadingIcon` via a variant-locked `tone` regardless of any `style`/`className` override on the button itself (confirmed by reading `Button.tsx`), while `Icon` with no `tone` inherits `currentColor` from its parent, which is exactly what makes the icon track the button's own hover-color change automatically with no separate override needed.

  Renders nothing at all — no card, no "Reset to defaults" — when a component has zero genuinely live-editable props left after `exclude`/`control: false` filtering (added 2026-09-06, at explicit direction, found via Spacer's own Docs page): previously an empty, contentless bordered card plus a reset button with nothing to reset still rendered, which is dead UI rather than a legitimate empty state. `PlaygroundControls` now returns `null` when its computed `rows` array is empty, same early-return pattern as the existing `if (!story) return null;` guard.

  Switched away from the original `<Controls>`-based panel because Storybook's own ArgsTable renders every row as two separately-boxed table cells, which no CSS override could turn into "one border around the whole panel" once `border-collapse` no longer applied to the CSS-multi-column reflow that approach needed — a from-scratch React implementation sidesteps the whole class of table-layout/CSS-hack bugs that approach kept hitting. Layout is `.dbm-playground-controls-grid` (`docs.css`) — a real 2-column CSS grid (`grid-template-columns: repeat(2, minmax(0, 1fr))`), collapsing to 1 column under `40rem` (a literal pixel match to `breakpoint.sm`, since `@media` conditions can't reference CSS custom properties) — not a table at all, so there's no alternating-row striping here the way `PropertiesTable` has.

**`PlaygroundControls`' own `mapping`-backed select needs a reverse look-up, not a naive `String()` (root-caused 2026-09-03, via Icon).** `usePlaygroundArgs`'s `args` (backed by `context.getStoryContext(story).args`) turn out to already hold the *resolved*, post-`mapping` value for a `mapping`-backed control (e.g. `icon` — a real component reference), not the raw option key a now-corrected comment in that file previously assumed. `ControlField`'s select/radio branch previously just did `String(value)` to compute the widget's displayed selection, which produces something matching none of `argType.options` for a non-primitive resolved value — the Docs-page Playground's own embedded dropdown silently showed its unselected placeholder even though the Canvas rendered the correct value the whole time (the *native* Storybook Controls-panel select, a separate mechanism, was unaffected). Fixed by reverse-looking-up the display key through `argType.mapping` (`Object.entries(mapping).find(([, mapped]) => mapped === value)`) whenever it's present, falling back to the previous `String()` behavior otherwise — `onChange` itself needed no change, since it already sent the raw option key. Confirmed no regression on `Button`'s/`IconButton`'s own already-shipped `mapping` controls. Any future component whose Playground has a `mapping`-backed control (an icon-reference prop, following `05-component-api-conventions.md` §5) is covered by this fix automatically — nothing to special-case per component.

**`PlaygroundControls`' own widgets visibly lagged behind typing/toggling by roughly a second (found 2026-09-07, via `GridItem`, direct user report — "I'm changing the value for order in playground and nothing happens").** Every widget's displayed value was driven directly off `usePlaygroundArgs`'s own `args`, which only updates after a full round-trip through Storybook's event channel (`updateArgs` emits `UPDATE_STORY_ARGS`; the hook only calls `setArgs` once `STORY_ARGS_UPDATED` echoes back) — not instant. The Canvas itself updated correctly and immediately (it reads the same channel through a separate, faster path), but the input/select/switch a reader was actually looking at kept showing its *previous* value for that whole round-trip window, reading as "the control does nothing" even though it was wired correctly the entire time — confirmed on both a `number` control (`GridItem`'s `order`/`colSpan`) and, once found, suspected to affect every control type equally, since none of them read from anything but that same round-tripped `args`. Fixed by giving `ControlField` its own optimistic local echo (`draft`, plus a separate `rawText` buffer for the `number` widget specifically, so an in-progress non-numeric state like a bare `-` while typing a negative value isn't clobbered) that updates synchronously on every interaction and only re-syncs from the external value when *that* changes for some other reason (the round-trip finally landing, "Reset to defaults", another control's `resolveDisplayValue` cascading). That sync is done *during render* (comparing against a same-render "previous value" and calling `setState` conditionally), not from inside a `useEffect` — this repo's lint config (`react-hooks/set-state-in-effect`) flags the effect-based version of this exact pattern as a real anti-pattern, not a style nit, since it costs an extra commit/paint the during-render version doesn't. Confirmed no regression on `Heading`'s own `mapping`-free select cascade (`size`'s `resolveDisplayValue` following a `level` change) and on the boolean/select paths generally, not just the number path that surfaced this. Applies automatically to every component's Docs page — nothing to special-case per component.

**`PlaygroundControls` now supports a per-argType `placeholder` (added 2026-09-07, via `GridItem`, direct user request — "make sure interactive prop input fields have a default value... I see colStart/rowStart input fields are empty").** Some props genuinely have no *safe* real default to show — `GridItem`'s `colStart`/`rowStart` specifically: unlike `colSpan`/`rowSpan` (safe to default to their own real CSS-initial value of `1`, since a span never fights auto-placement), an explicit line number spread across more than one grid item in the same story pins them all to the same line, overlapping — the exact collision bug documented in `component-reviews/GridItem.md`. Leaving the field with no value at all read as broken/empty rather than intentional. Added `placeholder?: string` to `ArgTypeLike`, passed straight through to the underlying `Input`'s native HTML `placeholder` attribute on both the `number` and `text`/fallback widget branches — cosmetic guidance only: it's never sent through `onChange`, never becomes a real arg, and disappears the instant a reader types anything. `GridItem`'s own `colStart`/`rowStart` argTypes now set `placeholder: "auto"`, communicating what leaving them unset actually means. Available to any future component whose Playground has a prop in this same "no safe default, but a real value would collide" category — nothing to special-case per component beyond setting that one `placeholder` string.

**A story whose own render relies on real `window` scroll breaks once embedded in a Docs page (found 2026-09-05, via `BackToTop`, direct user report).** Every story's `<Canvas>` on a Docs page shares one real underlying document — there's no per-story iframe sandboxing `window` scroll to just that Canvas's own section. A story that measures/sets `window.scrollY`/`window.scrollTo` as part of its own persistent render behavior (not just inside a `play` function used for scripted testing) stretches the *entire Docs page* to that demo's own content height, and a click-driven "scroll to top" inside it resets the *whole page's* scroll, not a contained section. `BackToTop`'s original `Playground`/`Visible` stories hit this directly; fixed by rendering them against a confined, `scrollContainerRef`-driven box instead (`BoundedScrollDemo`, `BackToTop.stories.tsx`) — the same technique `Affix`'s own embedded `HorizontalScrollInteraction`/`WithinTable` stories already used for a different reason, which is why `Affix` never hit this despite also being a scroll-driven component. **The rule going forward: any embedded (Docs-page) story demonstrating scroll-driven behavior must scope its own scroll to a confined container (`scrollContainerRef` or equivalent), never rely on real `window` scroll for its own render logic.** A `play` function scripting a real end-to-end `window`-scroll test is fine specifically *because* it lives on a story kept out of the Docs page's embed list entirely (`BackToTop`'s own `ScrollInteraction`, `Affix`'s `ScrollInteraction`/`BottomScrollInteraction` — all three reachable only via the sidebar/Interactions tab).

**A story with an implicit/`{...args}`-driven render and a non-primitive resolved arg breaks the "Show code" panel (found 2026-09-03, via Icon).** Storybook's own `<Canvas>`/`<Source>` doc block reconstructs its displayed code from the story's actual *resolved* args at runtime when the render spreads `args` (`docs.source.type`'s dynamic-mode fallback) rather than showing literal file source — for a non-primitive value (a real icon component reference), that reconstruction is the object's own runtime shape (`{ $$typeof: Symbol(react.forward_ref), render: () => {} }`), not anything a reader could paste and reuse. Every gallery story that was already a literal, args-free `render: () => (...)` (`AllSizes`/`AllWeights`/etc. in any component's own `*.stories.tsx`) never hits this, since Storybook shows real literal source text instead whenever a story's render doesn't reference `args` at all. The fix for a non-interactive static-reference story (Icon's own `Default`, which already had every control disabled via `argTypes`) is the same one already in use elsewhere: convert to a literal, args-free `render`. **A genuinely interactive Playground story can't take this fix** — driving every prop live via `{...args}` is the entire point — so a component whose Playground's own *default* `icon`/similarly-non-primitive arg triggers this is an accepted, inherent limitation of Storybook's own source-generation, not a gap to design around.

**Playground layout:** wrap the Canvas and controls as two siblings — `<div className="dbm-playground-canvas"><Canvas .../></div>` then `<PlaygroundControls of={PlaygroundStory} exclude={[...]} order={[...]} />` (no wrapping div needed — the block renders its own card) — directly in the MDX flow, no outer flex wrapper (see Box/Button/Avatar for the exact markup, including the blank lines MDX needs around nested JSX to keep parsing `<Canvas>`/`<PlaygroundControls>` as components rather than literal text; and see §4 item 2 for what `exclude` should contain and why). The controls panel renders **below** the Canvas, not beside it — a side-by-side split was tried first and reverted, since a 2-column control grid needs the full content width to stay readable.

**MDX doesn't support backslash-escaped quotes inside JSX attributes (found 2026-08-15, via Avatar)** — `usage="status=\"online\" dot color"` on a `<TokenRow>`/similar block broke the whole page (`storybook dev` failed to even start: "Unexpected character `\`"). Plain JS/TSX allows this; MDX's own JSX-in-Markdown parser doesn't. Use single quotes for the inner text instead (`usage="status='online' dot color"`) — there's no escape sequence needed, and it renders identically.

**Verification requirement:** after writing/retrofitting any `ComponentName.mdx`, visually verify it in a running Storybook instance (via the browser preview tools, not just `tsc`/lint) — confirm the TOC appears, every Callout renders with the correct tone/icon, every RelatedCard's live preview actually renders (not a broken import), and the Properties/token tables are styled — before considering that component's Docs page done. `tsc --noEmit` passing only proves the MDX compiles; it does not prove the page renders correctly.

**The raw per-story Controls addon panel's row order is a separate mechanism from the Docs page's own `PropertiesTable`/`PlaygroundControls`, with its own fix pattern (root-caused 2026-08-24, via Button/Checkbox).** The custom blocks take an explicit `order` prop and always read correctly; the *native* Storybook Controls panel (the "Controls" tab visible when browsing any story directly, outside the Docs page) has no equivalent override in this Storybook version — `parameters.controls.sort` is typed `'none' | 'alpha' | 'requiredFirst'` only, no custom comparator. Its row order instead comes from react-docgen's own extraction of the component's *Props type declaration*: a prop explicitly declared (with its own JSDoc) directly on the component's own `*Props` interface renders in that interface's declared position; a prop that's only ever inherited via `extends ComponentPropsWithoutRef<...>` and never redeclared gets extracted through a separate pass whose position isn't controllable from the interface, the stories file's `argTypes` object, or its key order — confirmed on `Button` (`disabled`/`onClick`, both undeclared-inherited, rendered out of sequence) and `Checkbox` (`disabled`, same). **The fix is to explicitly redeclare the prop directly on the component's own `*Props` interface** (real JSDoc, positioned where the intended order wants it — same pattern as redeclaring `aria-*` props for Properties-table visibility, §4 item 3, just applied for ordering instead of visibility this time), not to reorder `meta.argTypes` in the stories file (tried first, no effect on its own). **A full dev-server restart is required to see the fix take effect — Vite HMR and Storybook's own "Reload story" button do not invalidate docgen's cache for a changed type file**, confirmed by testing the identical code change against a live server (no change) versus after `preview_stop`/`preview_start` (fixed). Any future ordering fix must restart the dev server before concluding it didn't work. **Side effect to check for afterward (found live on Button's own `onClick`, same day):** redeclaring a function-typed prop this way can make Storybook's control-type inference resolve a real (non-`unknown`) type for it, which can flip its Controls-panel row from correctly showing no control at all to an inert "Set object" placeholder — the exact failure mode §5 already warns against. After redeclaring any prop for ordering, re-check its actual rendered control, not just its position, and add an explicit `control: false` if it's a function/handler prop. `Avatar`'s own `onClick` had this same gap (found while diagnosing Button's, fixed the same day at explicit direction — see `guidelines/component-reviews/Avatar.md`) — its `argTypes` already had `control: false` set from Avatar's original review, so the control-regression side effect didn't recur there.

**`docs.css`'s `.sbdocs-content h1/h2/h3` rules can silently override a component's *own* real `h1`-`h6` output (found 2026-09-06, via `Heading`, user-reported).** Those three rules exist to style the MDX page's own `##`/`###` prose section headings ("Playground", "Properties", etc.) — but a plain descendant combinator (`.sbdocs-content h2`) matches *any* `h1`/`h2`/`h3` under `.sbdocs-content`, prose or not, at (0,1,1) specificity — higher than any single-class rule a component's own CSS Module can produce (e.g. `._size4xl_...` at (0,1,0)). Every component before `Heading` was accidentally safe from this only because none of them render a real semantic heading as their own output (divs/spans/buttons don't collide with an `h1`-`h3` selector) — `Heading` is the first one whose entire purpose is rendering real `h1`-`h6` elements inside its own Canvas. Confirmed live: a real `<h2 class="_size4xl_...">` inside a Playground's Canvas computed to this rule's own `font-size`/`font-weight`/`border-block-end` instead of its own class's real values — explaining three symptoms at once (a font-size that didn't match the selected control, an unwanted border-bottom on some instances but not others depending on which tag they happened to render as, and a `weight` control that looked entirely dead). **Fixed by scoping all three rules to exclude anything inside `.sbdocs-preview`** (addon-docs' own stable Canvas wrapper, confirmed via the rendered DOM): `.sbdocs-content h2:not(.sbdocs-preview h2)`, and the equivalent for `h1`/`h3`. `:not()`'s specificity is that of its own argument, so this is *more* specific than before for genuine prose headings (still wins) while not matching at all for anything nested inside a Canvas, regardless of how deep a component's own render nests it. **Any future component whose own rendered output includes a real `h1`-`h6` (or, by the same logic, any other bare element selector this file might ever add for `.sbdocs-content`) should be spot-checked against this same collision** — the fix above covers `h1`/`h2`/`h3` specifically since those are the only bare-element selectors this file currently has; a new one would need the identical `:not(.sbdocs-preview ...)` treatment. Full incident: `guidelines/component-reviews/Heading.md`.

## 5. Per-component checklist

Applied to every component, in this order:

**Component correctness**
- [ ] Re-verify full definition-of-done (`05-component-api-conventions.md` §8) — don't assume it still holds
- [ ] Feature-completeness pass against comparable components in comparable production component libraries for the same role — name any concrete gap before adding anything, described in this system's own terms without naming the library it came from (existing guardrail, `06-engineering-standards.md` §8–§9)
- [ ] Required/recommended props present and sensibly defaulted
- [ ] Zero hardcoded values — grep-verify every CSS value traces to a token
- [ ] JSDoc complete on the component and every prop

**Storybook**
- [ ] `title` corrected to the taxonomy in §3
- [ ] Docs page per the §4 template, first in the group, using the shared visual-presentation blocks from §4.1 (`ComponentHeader`, `Callout`, `TokenRow`, `RelatedCard`, `PropertiesTable`) rather than plain `<Title />`/`<ArgTypes>`/markdown — verified visually in a running Storybook instance, not just typechecked
- [ ] `PropertiesTable`'s `order` prop lists every prop in a sequence that actually reads sensibly (content prop → core visual props → behavioral/state props → advanced/escape-hatch props last) — don't assume docgen's default order is already sensible, it usually isn't (see §4 item 4). Every `Canvas` in the Variants section has its own `###` subheading directly above it, matching the story's display name.
- [ ] Playground story, second in the group — every prop wired through `args`/`argTypes`, nothing hardcoded via a bare `render`
- [ ] Every controllable prop has an explicit value in the Playground's top-level `args`, matching its real component default — an arg left `undefined` renders as an inert "Set boolean"/"Set string"/"Set object" placeholder button instead of a live, interactive control (confirmed empirically on `Button` — `isLoading`/`loadingText`/`fullWidth` all showed as placeholders until given explicit defaults)
- [ ] Every enum-like prop gets an explicit `select`/`radio` control; non-controllable props (icon references, refs, and any inherited native prop Storybook's docgen can't cleanly infer — e.g. `Button`'s native `type` fell back to a broken "Set object" control) get `control: false` explicitly — check the full rendered Properties table for stray placeholders, not just the props you deliberately typed
- [ ] Every story's Controls panel is checked live, not just the Playground's — actually toggle a control and confirm the canvas changes. A custom `render` that doesn't accept `args` (`render: () => <Component prop="x" />`) makes every control silently do nothing, with no visual sign anything's wrong (found 2026-08-16 on Avatar: the `as` control showed "span" while the canvas showed a real `<button>`, and `colorful` did nothing on the colorful-family story — see `06-engineering-standards.md` §9 for the full checklist wording). For a multi-instance story where one prop is the whole point (e.g. "all sizes"), suppress only that prop's control, not the whole panel — every other shared prop across the grid should stay wired and controllable (also 06-engineering-standards.md §9; a same-day whole-panel-disable attempt at Avatar's matrix stories was reverted for being too blunt). Also check that each story's shown/effective `args` actually match what's rendered — not just that a control moves something, but that it starts at the right value.
- [ ] Every explicitly-redeclared native prop (`className`, `style`, `id`, `data-testid`, the relevant `aria-*` props — see `05-component-api-conventions.md` §3) actually appears in the rendered Properties table with its description, not just in the source. **Confirmed real bug on `Button`, 2026-07-27:** Storybook's default docgen (`react-docgen`, babel/AST-based — `@storybook/react-vite`'s default, not the TS-checker-based `react-docgen-typescript`) silently dropped `aria-label`/`aria-labelledby`/`className`/`id`/`data-testid` from the extracted table even though each had its own local JSDoc'd declaration in the `*Props` interface — while a sibling redeclared prop (`type`) showed up fine, for reasons that didn't reduce to one clean rule under inspection. JSDoc on the type alone is not sufficient evidence of a working Properties table entry — visually check the rendered table (per the §4.1 verification requirement) for every prop you expect to see. When docgen drops one, the reliable fix is the same pattern already used for `icon`/`trailingIcon`/`type`: add an explicit `argTypes` entry in the story file with its own `description` (and `control: false` for props like `id`/`data-testid`/`className` that aren't meaningfully live-editable).
- [ ] Every row in the rendered Properties table has a non-empty Description — a different failure mode than the previous bullet (the row exists, but docgen extracted no JSDoc text for it). Confirmed on `Button`/`Box`: plain native props (`children`, `disabled`, `onClick`, `style`) commonly come through with an empty description even though the row itself renders fine. Fix the same way — an explicit `description` in the story file's `argTypes`.
- [ ] Docs page has the visually-hidden `<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>` before `<ComponentHeader>` (see §4 item 1), `### Import` nested under it (not its own `##` section), and every other template section's `##` heading text matches §4's list verbatim — the TOC (§4.1) is generated from these headings, so a typo'd or reworded section title silently breaks "the same tabs on every page." `<PlaygroundControls exclude={[...]}>` in the Playground lists every prop with a non-editable control (see §4 item 2) — check the rendered Playground for stray "–" rows, which mean something was missed.
- [ ] At least one `play`-function interaction story for interactive components
- [ ] Remaining showcase stories (`AllVariants`, etc.) audited — kept where they add value as static references, converted to args-driven where feasible, removed if redundant with the Playground/Docs gallery
- [ ] Visual correctness spot-check across all 4 themes (both brands × light/dark)
- [ ] Dead/redundant stories cleaned up, consistent naming

## 7. Foundations pages (added 2026-07-27)

A second top-level Storybook sidebar group, **`Foundations`**, sorted to appear *before* `Atoms` (see the `groupPriority` array in `preview.tsx`'s `storySort` — top-level group order isn't alphabetical by default, so this needs to be forced explicitly). Ten standalone reference pages — no components, no stories, pure documentation — covering every token category shipped in `packages/tokens`, organized the way mature production design systems converge on: one page per token category, Color and Typography given the most detail since they're the highest-leverage/most-consulted categories.

**Page list, in reading order** (`packages/components/src/foundations/*.mdx`, each a standalone `<Meta title="Foundations/X" />` page — no `of=` prop, since there's no component/story behind them): Overview, Color, Typography, Spacing, Radius, Shadows, Motion, IconSizes, Miscellaneous (border width + opacity + z-index, grouped — each alone would be a near-empty page), Breakpoints. The explicit `foundationsOrder` array in `storySort` keeps this exact sequence, since alphabetical would scatter `Overview` into the middle.

**Data source — read live, never retyped by hand:** every value on every Foundations page comes directly from `@dbm-design-system/tokens`'s built JS export (`import { primitives } from "@dbm-design-system/tokens"`) rather than being copied from the JSON source or hardcoded in the MDX. This means the pages can never drift from the real token values — if a token changes, these pages reflect it automatically on the next build. Semantic (per-theme) tokens use the same `var(--dbm-{token})` CSS-custom-property mechanism `TokenRow` already established for component docs (§4.1), so they're live-reactive to the Brand/Mode toolbar exactly like every other themed swatch in this project.

**Caveat found 2026-08-15 (adding the `bg.*-subtle-hover` tokens): "live, never retyped by hand" covers each token's *value*, not *which tokens appear at all*.** `Color.mdx`'s `<SemanticSwatchGrid tokens={[{ token: "bg.brand", usage: "..." }, ...]} />` arrays are a hand-maintained list — `SemanticSwatchGrid` itself resolves whatever token names it's given generically (no code change needed to support a new token), but a newly-added semantic token doesn't appear on the Color page automatically; someone has to add its `{ token, usage }` entry to the right array, in the right position. **When adding a new semantic token, also add it to `Color.mdx`'s matching category array** (`bg.*`/`text.*`/`border.*`/`icon.*`), positioned immediately after the token it's most related to (e.g. a new `-hover` variant goes right after its base token) — matching the semantic JSON file's own key order, not appended at the end.

**This got missed anyway (2026-08-16):** the four `border.*-subtle` tokens added for Avatar's `colorful` border-matching shipped without their `Color.mdx` entries, exactly the failure mode this note already warned about — a written reminder alone wasn't enough. Fixed by adding a real enforcement mechanism instead of a stronger reminder: see §10's Foundations token-coverage check. Every *other* Foundations page (Radius/Spacing/Shadows/Motion/IconSizes) has no equivalent gap and needs no such check — each renders its scale by iterating `primitives.*` directly at render time (`RadiusScale`/`SpacingScale`/etc. in `.storybook/blocks/foundations/`), so a new primitive step appears there for free. Color's semantic tokens are the one category that can't work that way, because each entry pairs a token name with a hand-written `usage` description a script can't author on its own.

**Order check, not just presence (caught 2026-08-16, same session as `border.warning`/`success`/`info`):** the coverage check above only verifies a token is *somewhere* in `Color.mdx` — it says nothing about *where*. The four `border.*-subtle` tokens initially landed all four together, positioned before `border.danger` itself (grouped as "the new tokens," not interleaved with what already existed) — this reads wrong: it separates a family's own base/subtle pair. Order in each `SemanticSwatchGrid` array must match the family-grouped pattern `bg.*` already establishes (base, base-hover, subtle, subtle-hover, *then* the next family) and the semantic JSON source's own key order:
- **Group by family, not by "when it was added."** `border.danger` immediately followed by `border.danger-subtle`, then `border.warning`/`border.warning-subtle`, then `success`, then `info` — not all four bases together followed by all four `-subtle`s, and not the new tokens clustered at the end regardless of family.
- **The semantic JSON files (`packages/tokens/src/semantic/*.json`) must use this same order** — they aren't just a value lookup, their key order is the reference `Color.mdx`'s array order is supposed to mirror. Reorder the JSON source first, then match `Color.mdx` to it, not the other way around.
- **This is a manual check** (unlike presence, which §10's script enforces) — re-read the surrounding entries in both files before adding a new token, don't just append.

**Shared blocks** (`.storybook/blocks/foundations/*.tsx`, separate from the component-docs blocks in `.storybook/blocks/` directly, imported via `.storybook/blocks/foundations`): `ColorScaleGrid`/`ColorSwatch` (primitive color scales), `SemanticSwatchGrid` (theme-reactive semantic color tokens), `SpacingScale` (bar-chart visualization), `RadiusScale` (rounded-box visualization), `ShadowScale` (elevation cards on a light/dark-matched background), `MotionScale` (replayable animated demo, isolating the duration axis and easing axis separately rather than a combinatorial grid of both), `TypeSpecimen` (font-size scale at real rendered size), `IconSizeScale` (the real `Icon` atom at each size step), `TokenReferenceTable` (generic Name/Value/Usage table, reusing `.dbm-proptable` styling for the small non-visual scales).

### 7.1 `<ThemeSync />` — a real bug, not a nice-to-have

**Every Foundations page must render `<ThemeSync />`** (from `.storybook/blocks/foundations`) once, anywhere in the file. Without it, every semantic-token swatch, every `RelatedCard` border, anything referencing `var(--dbm-bg-*)`/`text-*`/`border-*`/`icon-*` on that page silently resolves to nothing.

**Root cause:** `preview.tsx`'s `withTheme` decorator — the thing that sets `document.documentElement.dataset.theme` from the Brand/Mode toolbar globals, which is what makes the theme-scoped semantic CSS (`:root[data-theme="..."] { ... }`) resolve at all — only runs when Storybook renders an actual **story**. Every component's `ComponentName.mdx` embeds at least one `<Canvas>`, so the decorator fires there as a side effect and the attribute ends up set for the whole page (it's a shared `document.documentElement` mutation, not scoped to the Canvas). A Foundations page has zero `<Canvas>`/`<Story>` blocks — pure prose and custom React components — so the decorator never runs, and `data-theme` is simply never set. Confirmed by checking `getComputedStyle(document.documentElement).getPropertyValue('--dbm-border-default')` on a Foundations page before this fix: empty string.

**Fix (`.storybook/blocks/foundations/ThemeSync.tsx`) — two real, separately-diagnosed bugs, not a first-try success:**
1. Listening for `GLOBALS_UPDATED` (the natural-sounding choice) doesn't work — that confirmation event only round-trips back through the channel once the preview's story-rendering machinery has an active story to apply the globals change to, which a story-less page never has. `UPDATE_GLOBALS` (the *command* the manager UI sends on every toolbar interaction, imported from `storybook/internal/core-events`) fires reliably regardless of any story — but only carries the *changed* keys (e.g. `{ mode: "dark" }`, not the full globals object), so it has to be merged onto a running snapshot rather than treated as a full replacement.
2. That running snapshot can't live in a plain `useState`/`useRef`-from-a-hardcoded-default — a globals change re-renders the whole Docs container (so embedded previews elsewhere on the page pick up the new globals too), which **remounts** `ThemeSync`, which reset the snapshot straight back to its hardcoded default and silently clobbered the change that had just been applied one render earlier. Diagnosed by logging mount/event order directly (`console.log` in the effect, temporarily) and seeing mount → event received → **immediate remount** → theme visibly reverts. Fixed by bootstrapping the snapshot by reading `document.documentElement.dataset.theme` back off the DOM on mount instead of a fixed default — the attribute itself survives the remount even though this component's own React state doesn't.

Both bugs were invisible to `tsc`/`eslint`/`vitest` — the only way either surfaced was live browser verification (capturing real channel events via `window.__STORYBOOK_ADDONS_CHANNEL__` and checking the resolved custom property value), reinforcing the standing rule in §4.1: visually verify in a running Storybook instance, don't infer correctness from a clean typecheck.

### 7.2 `<VisuallyHidden asChild><h2>Intro</h2></VisuallyHidden>` (added 2026-08-08)

**Every Foundations page must render this heading too**, immediately after `<ThemeSync />` and before the page's real `# Title`, mirroring the component-docs pattern in §4 item 1: it gives the TOC (§4.1) an "Intro" entry that scrolls to the very top of the page, and — same mechanism as §4.1's `.sbdocs-content h2` note above — makes the page's real first visible section (e.g. "Primitive scales" on the Color page) benefit from the same `:first-of-type`-collision workaround that component pages already got for free from their own hidden heading. Import: `import { VisuallyHidden } from "../atoms/VisuallyHidden";` (relative to `src/foundations/`).

## 8. Token usage in Storybook-only code (audited 2026-08-08)

Everything under `.storybook/` and every `*.stories.tsx`/Foundations `*.mdx` file is Storybook tooling, not shipped component code — but per `CLAUDE.md`'s token-first rule, it should still reference `var(--dbm-*)` tokens wherever a token exists, rather than hardcoding. A full audit (2026-08-08) found and fixed ~140 hardcoded values across `.storybook/blocks/`, Foundations docs pages, and component story demo wrappers — border widths and sizes that matched an existing token exactly, plus a few real bugs (`theme.ts`'s `appBorderRadius`/`inputBorderRadius` were mislabeled, off by 2px from the tokens their own comments named).

Three standing exceptions, not oversights:
- **`.storybook/theme.ts`** — Storybook's `theming/create()` API takes a literal JS object read by the manager UI, which runs outside our CSS entirely; every hex/px value there is traced to its source token in an inline comment instead.
- **CSS media-query breakpoints** (`docs.css`) — `var()` cannot appear inside an `@media` condition; these stay literal, cross-referenced to the matching `breakpoint.*` token in a comment.
- **Story-file demo-wrapper container sizing** (`width`/`maxWidth`/`height` on a story's outer wrapper `<div>`, e.g. `maxWidth: "24rem"` around an Input demo) — the `space.*` scale tops out at `space.32` (8rem) and is calibrated for gaps/padding/margins, not arbitrary layout container widths; forcing these onto the nearest token would visibly cramp story layouts. Left as literals — a deliberate scope boundary, not a gap to close later.

## 9. Manager-chrome customizations are version-fragile — re-verify after any Storybook upgrade

`.storybook/manager.ts`'s sidebar/mobile-drawer customizations (brand logo layout, Settings-gear repositioning, the mobile popover, Close-button position, theme-sync via the addons channel) rely on Storybook internals that are not a stable public contract, not the official theming API:
- `SET_GLOBALS`/`UPDATE_GLOBALS` imported from `storybook/internal/core-events` — the `/internal/` path is explicitly unstable.
- CSS overrides keyed to `aria-label`/DOM structure discovered by inspecting rendered output (`.sidebar-header`, `button[aria-label="Settings"]`, `a[aria-label="About Storybook"]`, etc.), not documented Storybook API.
- The mobile popover's capture-phase click interception, which depends on how Storybook currently wires its own click handling.

**After merging any Storybook version bump (Dependabot PR or manual), manually re-verify in the browser, both desktop and mobile viewports, both light/dark:** the brand logo layout, the Settings gear popover (desktop) and its mobile-popover equivalent, the mobile drawer's Close-button position, and Brand/Mode theme-sync across the sidebar/toolbar/panel/Foundations pages. A clean `pnpm install`/build passing is not sufficient evidence these still work — they can silently stop matching without any error.

**Version history:** pinned at `10.5.2` through Phase 4.75/4.9. Bumped to `10.5.7` on 2026-08-12 (`^10.5.6` in `package.json`, resolved to the latest available patch) — the first real exercise of the re-verification checklist above, done in full (both viewports, both brands, both modes, plus the mobile popover added the same week). Nothing broke; the checklist worked as intended.

## 10. CI & build reliability (added 2026-08-12)

Standing infrastructure that didn't exist before this pass — none of it changes what ships in `@dbm-design-system/components`, it's entirely CI/tooling hardening around the Storybook build itself:

- **`pnpm audit` in CI** (`ci.yml`) — previously only run manually/ad hoc (see `02-tech-stack-and-structure.md` §3.1's remediation pattern). Now a standing step on every push/PR.
- **`pnpm build-storybook` in CI** (`ci.yml`) — the static production build (`storybook-static/`) was never built anywhere before this; the Playwright visual-regression suite (`test:visual`) targets the `storybook dev` dev server, not the static build, so a broken static build could previously ship undetected. Relevant given public Storybook hosting is a Phase 9 goal.
- **Bundle-size tripwire** (`packages/components/scripts/check-storybook-bundle-size.mjs`, run in CI right after the build step above) — zero new dependencies, checks total `storybook-static/` size and the largest single Vite-bundled chunk under `assets/` against a budget. Deliberately excludes `sb-manager/`/`sb-addons/` (Storybook/addon-owned bundles, not ours to fix) from the per-chunk check. See `06-engineering-standards.md` §4 for the separate, now-also-closed per-component bundle-size check (`check-component-bundle-size.mjs`) — that one measures the published `@dbm-design-system/components` package itself, not Storybook, so it isn't part of this section's own scope.
- **`.storybook/**` now type-checked** — previously excluded from TypeScript entirely (`packages/components/tsconfig.json` only ever included `src`). `.storybook/tsconfig.json` (new) + a `typecheck:storybook` script chained onto `lint` closed this. Doing so surfaced several real, previously-invisible type bugs (a theme-object type that didn't actually structurally match all 4 brand/mode themes, a dead unreachable branch in a token-name lookup, `noUncheckedIndexedAccess` catching a couple of unsafe array-index fallbacks) — all fixed, not suppressed. One narrow, explained exception: `preview.tsx`'s `storySort` function can't be given real type annotations at all, confirmed by testing — its source is statically extracted and `eval`'d by Storybook as plain JS before any TypeScript transpilation, and real inline types broke `build-storybook` outright (`SyntaxError: Unexpected token ':'`). Uses a commented `@ts-expect-error` instead.
- **`storybook-static/**` added to the shared ESLint ignore list** (`packages/eslint-config/base.js`) — found while verifying the bundle-size work: a local `build-storybook` followed by `pnpm lint` fed ~21,000 bogus errors from minified output into ESLint, since the ignore list had never needed to account for this directory existing before.
- **Storybook telemetry disabled** (`core.disableTelemetry: true` in `main.ts`) — matches the project's free/OSS-only, no-phone-home posture (`CLAUDE.md`).
- **Foundations token-coverage check** (`packages/components/scripts/check-foundations-token-coverage.mjs`, added 2026-08-16, run in CI right after the `pnpm build` step) — reads every semantic token (`bg.*`/`text.*`/`border.*`/`icon.*`) from the built `@dbm-design-system/tokens` package (unioned across all 4 brand/mode theme exports) and diffs it against every `token: "..."` referenced in `Color.mdx`, failing with the exact missing/stale list if they don't match. See §7's caveat above for why only Color needs this — every other Foundations page self-updates from `primitives.*` by construction.
