# DBM Design System — Token Spec

Companion to `packages/tokens/src/` (the actual generated token files in W3C Design Tokens Community Group format — ready to feed into Style Dictionary and, later, the Tokens Studio Figma plugin for design-file sync).

## Architecture: 3 layers

1. **Primitive** (`primitive/*.json`) — raw values, no meaning. Color scales, spacing steps, radii, shadows, etc.
2. **Semantic** (`semantic/*.json`) — contextual meaning, references primitives via `{color.purple.600}`-style aliases. **One file per theme** (brand × mode). This is where multi-brand and light/dark actually live — the token *names* (`bg.brand`, `text.primary`) stay identical across every theme file; only what they resolve to changes.
3. **Component** (`component/*.json`, populated starting 2026-08-12) — component-scoped tokens for values a specific component needs that don't belong in the shared primitive/semantic scales. See "Component-layer tokens" below.

Status/neutral tokens (red, amber, green, blue, gray) are **shared across both brand themes** — success is always green, danger is always red, regardless of which brand is active. Only the "brand" slots (bg.brand, text.link, border.focus, icon.brand) swap per theme. This is a deliberate consistency principle, not an oversight — status meaning shouldn't be reinterpreted by theme.

## What's in each primitive file

| File | Contents |
|---|---|
| `color.json` | 11-step (50–950) scales for `purple`, `emerald`, `gray`, `red`, `amber`, `green`, `blue`, plus `neutral.white`/`neutral.black` |
| `typography.json` | Font families (Nunito primary, Lora secondary, mono system stack for Code/Kbd — added Phase 4.5 continuation, no extra font loading), weights, fluid font-size scale, line-heights, letter-spacing |
| `spacing.json` | 4px-base numeric scale, `0` through `32` (=128px) |
| `radius.json` | **Redefined 2026-07-27** to increment in step with `spacing.json` rather than its own curve: `none`(0) → `xs`(2) → `sm`(4) → `md`(8) → `lg`(12) → `xl`(16) → `2xl`(24) → `3xl`(32) → `full`(9999, pills/circles, deliberately outside the linear ladder) |
| `shadow.json` | Layered elevation shadows, **separate light/dark values** — dark-mode shadows are higher-opacity black, not a naive inversion, and should pair with a subtle border on raised surfaces |
| `breakpoint.json` | `sm`(640) → `3xl`(1920, for enterprise dashboard monitors) |
| `motion.json` | Duration scale (120ms–600ms) + 5 easing curves — `standard`/`decelerate`/`accelerate`, an "emphasized" expo-out curve for premium micro-interactions, and `linear` (added 2026-08-16, Skeleton's wave shimmer — a cubicBezier token equivalent to the CSS `linear` keyword, added so a constant-rate curve goes through the same build pipeline as the others instead of being hardcoded) |
| `other.json` | Icon sizes (paired with Phosphor, 12–48px), border widths, opacity scale, z-index layering scale |

## Color scale generation

**Re-derived in OKLCH in Phase 4 (2026-07-18)**, replacing the original HSL-based generation. Scales are generated by `packages/tokens/scripts/generate-color-scales.mjs` using `culori` (MIT-licensed, devDependency scoped to `packages/tokens` — never shipped to consumers): an 11-step OKLCH lightness curve, shared across all 7 scales, gives perceptually even steps (unlike HSL lightness, which isn't perceptually uniform — this is what caused the pre-Phase-4 `text.success` AA failure below). Chroma tapers toward both ends of each scale, gamut-clamped via `culori.clampChroma` so every generated value is a valid, displayable sRGB hex.

- **`purple-600` (`#5548A4`) and `emerald-600` (`#2E8A7D`) stay exact** — the two brand-mandated anchors (`01-vision-and-goals.md`'s decisions log). Every other step in those two scales is the shared canonical L curve shifted by a constant offset so it passes exactly through the anchor's own OKLCH `L` at 600, preserving the curve's spacing while still hitting the required color.
- **`gray`, `red`, `amber`, `green`, `blue` regenerate fully** — no anchor requirement, so every step (including 600) comes from the canonical curve directly, using each scale's previous 600 value only to pick a matching hue so the scale keeps its color identity (red stays red, etc.).
- Re-run the script whenever a scale needs re-deriving — e.g. adding a 3rd brand theme reuses the same anchored-scale logic with a new brand hex.

**Every contrast pairing changed as a result** (75 of 77 primitive values shifted) and was re-verified from scratch — see the running log below.

## Fluid typography

Built with the standard "Utopia" clamp() formula: two type scales (ratio 1.2 at 320px viewport, 1.25 at 1440px viewport) interpolated with `clamp(min, preferred, max)`. One deliberate deviation from a textbook fluid scale: **sizes at/below the base step (`xs`, `sm`, `base`) are fixed, not fluid** — scaling small UI text down further on large screens adds nothing and risks going under comfortable reading size. Fluid scaling kicks in from `md` upward, where it actually creates a meaningfully improved heading hierarchy across screen sizes.

Note: `font-size-xs` originally computed to ~11px, below the common 12px practical floor for body-adjacent text. **Fixed in Phase 2** — floored at `0.75rem` (12px exactly).

## Contrast verification (done, not assumed)

I ran actual WCAG contrast checks on the semantic pairings rather than eyeballing them. Running log, in the order each was found:

**Phase 1 planning:**
- **White text on `emerald-600` (light mode):** 4.16:1 — fails normal-text AA (needs 4.5:1). **Fixed** by moving the light-mode `bg.brand` solid-fill token to `emerald-700` (4.55:1, passes).
- **White text on `emerald-500` (dark mode):** 2.39:1 — fails badly. **Fixed** by using dark text (`gray-950`) instead of white for `text.on-brand` in the emerald dark theme (6.92:1, passes).

This is why `text.on-brand` is defined per-theme rather than as a single global "white" constant — the right foreground color for a solid brand fill depends on how light that specific brand color is, and emerald sits at a very different perceptual lightness than purple even at the same numeric step.

**Phase 3 (building Button/Badge/Avatar surfaced more gaps — the token set wasn't as complete as the Phase 1 pass assumed):**
- **No `text.on-danger` existed** (only `text.on-brand`, calibrated for brand colors specifically). Computed directly: white on `red.600` (light themes) = 6.12:1, white on `red.500` (dark themes) = 4.74:1 — both pass AA. Added to all 4 themes.
- **No `bg.danger-hover` existed.** Mirroring `bg.brand-hover`'s dark-mode-lightens pattern (`red.400`) only gives white text 3.24:1, failing AA. Used `red.600` instead (darker, breaking the brand-hover directionality convention specifically because `red.400` isn't safe here) — 6.12:1. Light-theme hover (`red.700`) mirrors the brand pattern fine at 8.1:1.
- **Real pre-existing bug:** `text.success` on `bg.success-subtle` was **4.08:1, failing AA** — shipped in Phase 2 undetected, a symptom of green's steps not being as evenly spaced as red's under the HSL-derived scales (see the OKLCH re-derivation item below). Fixed by moving `text.success` from `green.700` to `green.800` (6.01:1) in both light themes; dark themes were already passing.
- **No neutral/offline status-tone fill existed** (Avatar's offline status dot was reusing `border.strong`, a border-purposed token, as a fill — and that reuse also failed WCAG 1.4.11 non-text contrast: 2.74:1 light / 2.36:1 dark against `bg.surface`, needs 3:1). Added `bg.neutral` = `gray.500`, which uniquely passes both light (4.24:1) and dark (3.12:1) against `bg.surface` — a single shared value across all 4 themes.

**Post-Phase-3 review pass (auditing for workarounds before Phase 4 turned up two more real gaps):**
- **`text.tertiary` failed AA as text:** it's used both as a non-text icon color (Input's affix icons, 3:1 floor — fine at the original `gray.500`) and as literal text color (`Text` component's `color="tertiary"`, `Divider`'s label, `Input`'s placeholder — 4.5:1 floor). The original `gray.500` was 4.24:1 light / 3.12:1 dark against `bg.surface`, failing the text bar despite passing the icon bar. Fixed: `gray.600` for light themes (5.60:1), `gray.400` for dark themes (4.82:1) — both still correctly more muted than `text.secondary`.
- **Badge's solid variant needed a fuller token set than `text.on-danger` alone:** computed `text.on-info` (white, 6.01:1/4.56:1, passes as one shared value), `text.on-success` and `text.on-warning` (white fails badly on both — 2.33–3.30:1 — used `gray.950` instead, 5.02–7.99:1, matching the dark-text precedent from `text.on-brand`'s emerald-dark override), and a dedicated `bg.neutral-strong` (`gray.600`) + `text.on-neutral` (white, 5.60:1) since `bg.neutral` (verified only for the 3:1 non-text case) fell short of 4.5:1 with either white (4.24:1) or dark (3.9:1) text — the least accessible possible host for text, sitting near the perceptual midpoint of the gray scale.

**Phase 4 (OKLCH re-derivation, 2026-07-18) — full re-verification, since 75 of 77 primitive values changed:**
- Re-ran every pairing above plus a systematic sweep (25 pairings × 4 themes = 100 checks: all `text.*`/`bg.*` combinations, `bg.neutral`, `border.focus`, `icon.default`, `icon.brand`). 6 categories of regression found and fixed:
  - `text.on-success` / `text.on-warning`: white/gray.950 no longer cleanly passed against the regenerated `green.600`/`amber.600`. Light themes: `bg.success` moved to `green.700` (white text, 6.50:1); `text.on-warning` moved to white (4.78:1 against unchanged `amber.600`). Both tokens are now **theme-specific** (light = white, dark = gray.950) rather than shared.
  - `text.on-danger` / `text.on-info` (dark themes): white against the regenerated `red.500`/`blue.500` dropped to 3.48:1/3.26:1. Fixed by making both **theme-specific** (dark = gray.950: 5.22:1/5.56:1; light keeps white).
  - `bg.danger-hover` (dark themes): now `red.400` (lighter than base, restoring the normal dark-mode "brighten on hover" direction) instead of the Phase 3 `red.600` — that darker value was only needed because dark-mode `text.on-danger` used to be white; now that it's gray.950, red.400 works and the more intuitive hover direction is restored.
  - `bg.brand-hover` (purple-dark only): `purple.400` dropped to 3.41:1 with white text. Moved to `purple.600` (darker, 7.37:1) — deliberately breaks the "lighten on hover in dark mode" convention here, same class of exception as `bg.danger-hover`'s original Phase 3 fix.
  - `text.link`: purple-dark's `purple.400` (4.13:1) → `purple.300` (5.80:1); emerald-light's `emerald.600` (4.16:1, the brand anchor) → `emerald.700` (6.08:1). The emerald one is a **pre-existing gap unrelated to the regen** — same anchor hex before and after Phase 4, it just hadn't been checked as literal text color until this sweep.
  - `border.focus` (emerald-light only): `emerald.500` fell to 2.92:1 against the 3:1 non-text floor. Moved to `emerald.600` (4.16:1).
  - `icon.secondary` (light themes): found failing 3:1 (`gray.400` = 2.32:1) while auditing the remaining icon tokens — not a regression (this token isn't referenced by any shipped Phase 3 component yet) but a real gap, fixed pre-emptively. Moved to `gray.500` (3.25:1).
- All fixes verified against the full 100-check sweep plus a Storybook visual pass (both brands × both modes) before merging. See individual `$description` fields in each `semantic/*.json` file for exact per-token numbers.

**Phase 4.75 (comprehensive atom completion, 2026-07-26):**
- **New token, deliberately exempt from contrast checking:** `bg.overlay` (added for the `Backdrop` atom — the dimming scrim behind Dialog/Drawer/overlays), shared across all 4 themes as `{color.neutral.black}`. No text is ever rendered directly on it, so it isn't a WCAG contrast pairing in the way every other `bg.*`/`text.*` combination above is — opacity is applied compositionally at the component layer via the existing `opacity.*` scale rather than baked into the token, keeping color and opacity in their own separate token categories everywhere.

**Phase 5 (Foundations Color page review, 2026-07-27) — anchored-scale light end read as gray, not a light tint:**
- **Root cause:** `purple-600`'s OKLCH `L` (0.46) sits well below the canonical curve's own 600 midpoint (0.56), so the constant `lOffset` used to shift the rest of purple's/emerald's steps dragged purple's light end down toward mid-gray territory too. Confirmed empirically — user-flagged (screenshot comparison against `red`/`green`/`blue`'s 50–200, which are unshifted free scales and read as clean light tints).
- **First fix:** `purple`/`emerald` steps 50/100/200 made fully unshifted (use the canonical `L` directly, like the free scales). Fixed 50–200, but left a real discontinuity: the 200→300 `L` gap became 0.171, nearly double every other gap in the scale (~0.09) — a hard on/off cutoff rather than a smooth curve.
- **Follow-up (same day):** user separately flagged `purple.300` as still reading gray. Root cause was that discontinuity, not a new issue — 300 sat perceptibly darker than an evenly-spaced curve would put it. **Real fix:** replaced the on/off cutoff with `OFFSET_BLEND`, ramping the anchor's `lOffset` linearly from 0 at step 200 to 1 (full offset) at step 600, instead of snapping it on at 300. Restores an even `L` curve (gaps now 0.088–0.114 throughout, no cliff) while keeping 50–200 unshifted and 600 exact.
- Fixed at the generation-script level (`packages/tokens/scripts/generate-color-scales.mjs`), not by hand-editing `color.json`, so the fix survives regeneration.
- New purple 50–500: `#F9F9FF`, `#EFEFFC`, `#DBDAFC`, `#B9B7EF`, `#9691E0`, `#746BC6` (600 anchor `#5548A4` unchanged; 700–950 unchanged). Emerald 50–500 shifted by the same negligible-to-small amount as a side effect of the same code path.
- Re-verified every real consumer of the changed steps: `text.link` (purple-dark, `purple.300`) improved 5.80:1 → 7.45:1; `border.focus` (purple-light, `purple.500`) still comfortably passes at 4.98:1 non-text; `text.link` (emerald-dark, `emerald.400`) still passes at 6.49:1. No regressions, all still AA+.

**Phase 6 (`bg.canvas`/`bg.subtle` swap + new tokens, 2026-07-27):**
- `bg.canvas`/`bg.subtle` swapped in both light themes (`gray.100`/`gray.50`, was `gray.50`/`gray.100`) at the user's explicit request: canvas should be the more visibly distinct page-level gray so white surface cards pop off it; subtle should be the barely-there tint closest to white, used for hover fills/zebra striping on those cards. Dark mode intentionally left unchanged (`canvas` = `gray.950`, `subtle` = `gray.800`) — tried mirroring with `subtle` at `gray.700` to also fix a pre-existing `subtle`/`surface-raised` collision (both `gray.800`), but that failed AA for the real `text.secondary`-on-`bg.subtle` pairing (Tag/Badge `subtleNeutral`): 4.00:1, needs 4.5:1. `gray.600` is worse (2.73:1). No primitive step exists between 800 and 900 to fix the collision without breaking contrast, so dark `subtle` stays at `gray.800` — a real but lower-priority visual nit, not a WCAG failure.
- **`bg.warning-hover` / `bg.success-hover` / `bg.info-hover` added** (previously only `brand`/`danger` had hover states) — same one-step-darker (light) / one-step-lighter (dark) pattern as the existing hover tokens. All verified AA-safe: light themes 6.93–9.56:1 (white text), dark themes 7.76–8.23:1 (gray.950 text).
- **`bg.overlay` re-verified, not changed:** user asked whether it should carry opacity. It's correct as-is — opacity is composited separately at the component layer (`Backdrop.tsx`'s `opacity` prop, defaulting to `60` i.e. `var(--dbm-opacity-60)` = 0.6), not baked into the color token, matching the token's own `$description`. Confirmed via the component source and its tests (`Backdrop.test.tsx`); the Foundations page's raw-swatch rendering (opaque black) doesn't reflect the composited runtime result, which is what caused the question.
- **`text.brand` and `border.brand` added.** Originally requested as literal `brand.600` / `brand.100` in every theme; both failed real contrast checks in most theme/mode combos (`text.brand`=600: 1.92:1 dark-purple, 4.16:1 emerald-light, 3.39:1 dark-emerald, all failing the 4.5:1 floor; `border.brand`=100: 1.14–1.13:1 in both light themes, failing the 3:1 non-text floor badly). Flagged to the user, who initially chose to reuse the already-verified precedents instead: `text.brand` took the same resolved values as `text.link` per theme/mode; `border.brand` took the same resolved values as `border.focus`.
- **`border.brand` revised same day** — user overrode the contrast-driven value and asked for the literal `brand.100` in every theme after all, on the basis that this token is for decorative UI accents rather than a border that identifies a component/state boundary, so WCAG 1.4.11 (which governs borders/graphics required to identify UI components and states) doesn't apply the same way here. Now `purple.100`/`emerald.100` literally in all 4 themes (light: 1.13–1.14:1, deliberately below 3:1; dark: 12.38–12.46:1, far above it as a side effect of primitive.100 sitting near-white against a near-black surface). `border.focus` and `border.danger` remain contrast-verified per-theme, since those genuinely are state-identifying borders under 1.4.11. `text.brand` was not revisited and still uses the `text.link`-matched, contrast-verified values.

**Phase 7 (`bg.canvas` moved lighter in light mode only, 2026-08-08):**
- `bg.canvas` moved from `gray.100` to `gray.50` in both light themes, at explicit user direction, reopening the Phase 6 canvas/subtle swap: `bg.subtle` is already `gray.50` in light mode, so this makes `bg.canvas` and `bg.subtle` byte-identical — an accepted tradeoff, confirmed with the user before applying (flagged that it undoes Phase 6's stated rationale for the swap), not an oversight or a missed collision.
- Dark mode's `bg.canvas` was briefly moved from `gray.950` to `gray.900` (mirroring the light-mode move, landing on the same value as `bg.surface`) the same day, then reverted back to `gray.950` at the user's explicit follow-up instruction. Dark mode's `bg.canvas` therefore nets out **unchanged** — still the scale's terminal/most-extreme dark step, still distinct from `bg.surface`. Only light mode actually changed.
- Contrast re-verified for the real pairing this token has (Storybook manager chrome's sidebar text, via `theme.ts`'s `appBg`/`textColor`/`textMutedColor` — `bg.canvas` itself is a page-background-only token, not referenced by any published component): light mode `text.primary`/`text.secondary` on the new `gray.50` measure 13.53:1 / 6.59:1 (were 12.41:1 / 6.05:1 on `gray.100` — improved, since a lighter background only helps contrast against dark text). Dark mode's pairing is unaffected, reverting to its already-verified `gray.950` values (17.38:1 / 10.55:1).

**Phase 8 (`bg.code`/`text.code`/`border.code` added, 2026-08-08):** Found while auditing the Foundations pages after the Phase 7 `bg.canvas` change: `docs.css`'s `.dbm-tokentable code` pill (the "Token" column in the Breakpoints/Miscellaneous reference tables) used `bg.subtle`/`text.primary`, which visually blended into the table's own zebra stripes once `bg.canvas` moved to equal `bg.subtle` in light mode — the pill lost its distinctness. User asked for a blue-tinted pill instead (`blue.50` background, `blue.100` border, `text.secondary`) — the *original* treatment this exact pill had before an earlier same-day fix moved it away from blue, because a *fixed* `blue.50` paired with *reactive* `text.secondary` measures only 1.64:1 in dark mode.
- Rather than reintroduce that fixed/reactive mismatch, added three new **reactive** semantic tokens — `bg.code`, `text.code`, `border.code` — instead of pairing a fixed primitive with a reactive token again. Values mirror `bg.info-subtle`/`text.info`'s exact, already-verified lightness-curve pairing (`blue.50`/`blue.700` light, `blue.950`/`blue.300` dark) under new names, since a plain code/token reference isn't a status and reusing the `info` tokens directly would misleadingly imply one (same reasoning `docs.css` already documented for why `blue-50` was never promoted to `bg.info-subtle` for this purpose in the first place). `border.code` added as a fourth companion token (`blue.100` light / `blue.900` dark).
- Shared across all 4 themes (brand-independent), matching every other blue/gray-family token in this system.
- Contrast: `text.code` on `bg.code` measures **6.63:1 light / 10.51:1 dark** (identical to the already-verified `text.info`/`bg.info-subtle` numbers, since the values are the same). `border.code` on `bg.code` measures 1.09:1 light / 1.28:1 dark — well under the 3:1 WCAG 1.4.11 floor, but accepted since this is a purely decorative pill border, not one that identifies a component/state boundary (same accepted class as `border.brand`).
- Not currently consumed by any published component — the real `Code.tsx` atom uses `bg.subtle`/`text.primary` (see `Code.module.css`), unaffected by this change. `bg.code`/`text.code`/`border.code` are Storybook-docs-only for now (`docs.css`'s `.dbm-tokentable code`), though nothing prevents `Code.tsx` from adopting them later if the two are meant to look the same.

**Phase 9 (`bg.surface`/`bg.surface-raised`/`bg.subtle`/`bg.canvas` usages redefined and re-valued, 2026-08-08):** All four tokens' usage descriptions were rewritten at explicit direction, and three of the four values changed with them:
- `bg.surface`: usage → "page, card, sheet and drawer background" (broader than the prior "card/panel surface"). Value: light unchanged (`white`); dark reverted `neutral.black` → `gray.800` (see below for why `neutral.black` didn't stick). Contrast re-verified dark: `text.primary` 9.66:1, `text.secondary` 5.86:1, `text.tertiary` 4.34:1 (all still clear AA at the `gray.300`/`gray.400` values live at the time — see Phase 10 for their own later move).
- `bg.surface-raised`: usage description added ("an elevated surface, paired with a shadow"). Value unchanged both modes (`white` light, `gray.800` dark) — now byte-identical to `bg.surface` in dark mode specifically, so elevation there relies on the paired shadow rather than a background difference.
- `bg.subtle`: usage → "hover fill for tertiary/ghost controls, dashboard panel, neutral accent" (broader than hover-fill/zebra-striping alone). Value: light unchanged (`gray.50`); dark moved `gray.800` → `gray.900`, which also resolves the long-standing `bg.subtle`/`bg.surface-raised` collision noted in that token's own history (both were `gray.800`). Contrast re-verified: `text.secondary`-on-`bg.subtle` (Tag/Badge subtleNeutral) 8.21:1, `text.primary` 13.53:1.
- `bg.canvas`: usage narrowed to "canvas and playground container" — a specific Storybook live-preview/demo surface, not the general page background it meant before. Value: light `neutral.white` → `gray.100`; dark `neutral.black` → `gray.700`. In dark mode this puts `bg.canvas` (`gray.700`) one step *lighter* than the reverted `bg.surface` (`gray.800`) — an intentional inversion of the usual dark-mode elevation cue (raised content is normally lighter than the canvas behind it), confirmed at explicit direction given the narrower Storybook-specific usage. This is also what reopened the AA gap Phase 10 exists to close: `text.secondary`/`text.tertiary` (at their pre-Phase-10 values) measured 4.00:1/2.96:1 against the new `bg.canvas`, both failing.
- Side effect: reverting `bg.surface` off `neutral.black` back to `gray.800` recreated a `border.default`/`bg.surface` collision (both `gray.800`, 1.00:1) that the `neutral.black` value had incidentally fixed a few edits earlier — `docs.css`'s table-border and section-divider rules were reverted from `border.default` back to `border.subtle` (`gray.900`, 1.40:1 against the new `bg.surface`) to compensate.
- Two more collisions flagged but not fixed, since nothing currently renders either pairing: `border.subtle`/`bg.canvas` in light mode (both now `gray.100`) and `border.subtle`/`bg.subtle` in dark mode (both now `gray.900`).

**Phase 10 (`text.secondary`/`text.tertiary` dark-mode values raised, 2026-08-08):** Direct follow-up to Phase 9's `bg.canvas` move, which left `text.secondary`/`text.tertiary` failing AA against it.
- `text.secondary` dark: `gray.300` → `gray.200`, at explicit direction. Was 4.00:1 against `bg.canvas` (fails the 4.5:1 text floor); now 5.10:1 (passes). Improves against every other `bg.*` pairing too: 7.47:1 on `bg.surface` (was 5.86:1), 10.47:1 on `bg.subtle` (was 8.21:1).
- `text.tertiary` dark: `gray.400` → `gray.300`, at explicit direction, same motivation. Still doesn't clear the 4.5:1 text floor against `bg.canvas` (4.00:1) — it does clear the 3:1 non-text floor there, but this token's own literal-text uses (`Text` `color="tertiary"`, Divider label, Input placeholder) need 4.5:1, the same standard that ruled out `gray.500` originally. No primitive step between `gray.300` and `gray.400` exists to close that last gap without also moving past `text.secondary`'s own new `gray.200`. Against this token's actual intended surfaces it's comfortably clear: 5.86:1 on `bg.surface`, 8.21:1 on `bg.subtle`.
- **Rule: `text.tertiary` must never be used as literal text directly on `bg.canvas`** (any mode/brand) — it's below the AA text floor there and no available primitive step closes the gap without disturbing other, currently-passing pairings. Enforced by convention/review, not by a build-time check.

**Phase 11 (`text.link` on `bg.brand-subtle` logged, 2026-08-14):** Found undocumented while reviewing Avatar (`.content`'s default background/text pairing). Not a new value or a regression — both tokens are unchanged from their existing, already-established values; this is closing a gap in the verification log itself, re-computed directly from the built theme output rather than assumed: **purple-light 7.03:1, purple-dark 7.45:1, emerald-light 5.83:1, emerald-dark 6.49:1** — all comfortably clear of the 4.5:1 AA text floor. The two dark-theme numbers match the `$description` already recorded on each theme's own `bg.brand-subtle` token (Phase 9's `purple-dark`/`emerald-dark` move to `gray.900`); the two light-theme numbers hadn't been stated anywhere before this entry.

**Phase 12 (`bg.{brand,danger,warning,success,info}-subtle-hover` added, 2026-08-15):** New tokens for Avatar's hover state (`as="button"`-style interactive mode) — a subtle-background fill needed its own hover step, one primitive scale step past `-subtle` in this system's standard hover direction (darken in light mode, lighten in dark). All 5 reuse an already-generated scale step (each family's `-subtle` value from *before* its own 2026-07-27 one-step move), rather than needing a new primitive — light themes get each family's `.100` step back, dark themes get `.900` (or `gray.800` for `brand-subtle-hover` specifically, since dark `brand-subtle` itself is `gray.900`, not a brand hue — see Phase 9). Every text token that already pairs with each `-subtle` background was re-checked against the new `-subtle-hover` value directly from the built theme output:

| Pairing | Light | Dark |

**Phase 17 (disabled-state contrast, verified 2026-08-16 — closes what was previously logged as "not yet checked"):** confirmed real, computed numbers for every component with a disabled state, rather than leaving the WCAG exemption asserted but unmeasured. Two distinct mechanisms exist in this codebase:

- **Opacity-composited (9 components — `Button`, `IconButton`, `CloseButton`, `Avatar`, `Checkbox`, `Switch`, `Input`, `Textarea`, `Select`):** `opacity: var(--dbm-opacity-40)` applied to the whole element. Modeled as a real alpha composite (`0.4×foreground + 0.6×page-background`, `bg.surface` as the representative page background every prior phase's own checks already use) rather than assumed. One representative pairing per component's own default appearance, computed for all 4 themes — full range across every theme was **1.02:1 to 2.96:1** (`Switch`'s track fill was tightest, `Input`/`Textarea`/`Select`'s value text was closest to clearing a floor). `CloseButton` excluded — its icon color is `color: inherit`, context-dependent by design, no single number applies.
- **Direct tokens, not opacity-derived (`text.disabled`, `icon.disabled` — consumed by `FieldLabel`, `FieldHelperText`, `Heading`, `Text`, `Icon`, `Spinner`):** used as literal resolved colors, no compositing involved. `text.disabled` measured **2.14–2.32:1** against `bg.surface` across all 4 themes; `icon.disabled` measured **1.46–1.72:1**.

Every number sits below both the 4.5:1 text floor and the 3:1 non-text floor, in every theme, with no surprises (nothing measured near-zero/fully-invisible either — `Switch`'s 1.02:1 is the closest, still visually present via its own shape and the paired `cursor: not-allowed`, not relying on color alone). This confirms the existing exemption is correctly applied, not just asserted: WCAG 2.1 success criteria 1.4.3 (Contrast Minimum) and 1.4.11 (Non-text Contrast) both explicitly exclude **inactive/disabled user interface components** from their contrast requirements — a disabled control reading as visibly muted is the correct, spec-sanctioned behavior, not a gap to close by raising these numbers. Nothing was changed as a result of this phase; it's a verification-only entry, matching this log's own standing rule of confirming rather than assuming.

## Multi-theme structure going forward

Adding a third brand theme later = one more pair of semantic JSON files (`{brand}-light.json`, `{brand}-dark.json`) referencing a new primitive color scale, following the exact same token names as the existing two. No changes needed to component code, since components should only ever reference semantic tokens, never primitives directly.

## Component-layer tokens

**First populated 2026-08-12 (Avatar's size scale), extended 2026-08-13 (Avatar's status-size scale, same file — `component/avatar.json` now holds two token families, `avatar.size.*` and `avatar.status-size.*`)** — the pattern below is now established, not just planned.

- **File convention:** one file per component, `component/{component-name}.json`, self-namespaced under that component's own top-level key (e.g. `avatar.json` → `{ "avatar": { ... } }`) — same unwrapped convention as `typography.json`/`other.json`, so no entry in `dbm/namespace-primitives`'s `NAMESPACE_BY_FILENAME` map is needed.
- **Theme-independent by default.** Unlike semantic tokens, component tokens aren't split per brand/mode — they're built once into `component-tokens.css`/`component-tokens.ts` and loaded globally (`:root`, no `data-theme` scoping), alongside `primitives.css`. A component token *can* alias a primitive (e.g. a future color override) if it ever needs one — the build includes the primitive source for reference resolution — but plain literal values (dimensions, etc.) are just as valid and don't require an alias.
- **When to reach for this layer, in order of preference:**
  1. Use an existing semantic token if one already fits.
  2. If a component needs a numeric value on an existing primitive scale (spacing, icon-size, etc.) that just isn't the value currently in use, prefer that existing scale over inventing something new.
  3. Only add a component-layer token when the component's design genuinely calls for a value with **no home on any existing primitive scale** — reach for this layer instead of hardcoding the literal value directly in component CSS, which the "tokens are the single source of truth" rule in `CLAUDE.md` forbids regardless of layer.
- **Precedent — Avatar's size scale:** requested pixel values were 36/40/44/48/52px. Only 40 and 48 matched existing tokens (`space-10`, `space-12`); 36/44/52 matched nothing on any scale. Rather than distort the shared spacing scale to fit one component's needs, or silently snap to the nearest existing values (changing the requested design), `component/avatar.json` was created with `avatar.size.{xs,sm,md,lg,xl}` as literal dimension values, scoped only to Avatar.
- **Build wiring:** `style-dictionary.config.js`'s `buildComponents()` runs a dedicated Style Dictionary instance (source: primitives + `component/*.json`, filtered to component-namespaced tokens via `token.filePath` rather than a hardcoded namespace list, so a new `component/*.json` file needs no config change) — same shape as the existing primitives-only and per-theme passes.

## Build pipeline decisions (Phase 2)

Style Dictionary 5's actual behavior diverged from a few of the phase brief's assumptions. Documented here so these don't get "fixed" as bugs in a later session — each was audited post-Phase-3 and confirmed to be the correct, standards-conforming response to a real SD5 constraint, not a shortcut.

- **Built-in transforms cover fontFamily/cubicBezier.** SD5 ships `fontFamily/css` and `cubicBezier/css` out of the box — no custom transform code needed, contrary to the original assumption. Used directly in `style-dictionary.config.js`'s `CSS_TRANSFORMS`.
- **Primitive files aren't self-namespaced.** `radius.json` and `breakpoint.json` both use bare `sm`/`md`/`lg`/`xl` at the top level, which collide on a naive merge. A custom parser (`dbm/namespace-primitives`) wraps each file's content under the namespace its DTCG aliases already expect (`color.json` → `color`, `spacing.json` → `space`, etc.); `typography.json` and `other.json` need no wrapping since their internal groups are already distinct.
- **The built-in size/rem transform can't handle `clamp()`.** Confirmed empirically — it throws `Invalid Number` on fluid typography values. `CSS_TRANSFORMS` deliberately excludes any dimension-unit transform; all dimension `$value`s (spacing, radius, fluid font sizes) are pre-authored as final, correctly-unitted CSS strings (`"0.25rem"`, `"4px"`, `"clamp(1.2rem, 1.186rem + 0.071vw, 1.25rem)"`) at the source, so they pass through the pipeline verbatim instead of being computed by a transform.
- **`shadow.json`'s `_note` key is stripped during parsing.** DTCG parsing expects every leaf to resolve to a `$value`; the human-readable `_note` annotation isn't a token, so the custom parser deletes it, scoped narrowly to that one file/key.
- **Each theme is built as a separate Style Dictionary instance**, not as one config with multiple platforms. The four semantic theme files (`purple-light`, `purple-dark`, `emerald-light`, `emerald-dark`) all use identical top-level token paths (`bg.canvas`, etc.) — loading more than one into a single dictionary at once collides. `style-dictionary.config.js` builds 5 instances total: one primitives-only pass plus one per theme, each sourcing the shared primitives plus exactly one semantic file.
- **Motion easing gets two parallel TS exports, decided 2026-08-16 (previously an open question in `01-vision-and-goals.md` §12).** `motion.easing.*` (unchanged) stays a CSS `cubic-bezier()` string — the form the built-in `cubicBezier/css` transform produces, and what the Foundations Motion page's own interactive demo (`MotionScale.tsx`) already builds a `transition` shorthand string from. A new sibling, `motion.easingArray.*`, additionally exports the same value as the raw `[x1,y1,x2,y2]` array — the form the `motion` library's own `easing` prop wants, and the one no export previously covered. Implemented generically in `dbm/typescript-const`'s `buildNestedObject` (reads `token.original.$value` for any `$type: "cubicBezier"` token, not hardcoded to `motion` specifically) rather than as a one-off — additive only, so the existing string export and its one real consumer are unaffected. No component uses the `motion` package yet (still zero imports of it anywhere in `packages/components`), so this remains unexercised until that integration actually happens — but the export shape no longer blocks it from starting.
